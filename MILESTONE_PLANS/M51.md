# Objective

Plan the full-stack operation that deletes specific todos.

# Included

- Add `POST /todos/batch-delete`. The body is `{ ids }`.
- Accept 1 to 100 ids. Every id is a UUID. Duplicate ids are refused.
- Delete every listed todo in one database transaction. Either all are deleted or none are.
- When any id does not exist, roll back and answer `409` with the missing ids.
- Add the request and response schemas to the contracts package. Reuse `batchConflictErrorResponseSchema` for the conflict.
- Test the schemas, the repository, and the route against a real database.
- Add a browser API adapter and a mutation hook for the new endpoint.
- In selection mode, add a "Delete 3 selected todos" button to the selection bar. The wording and style mark it as destructive. A note says the deletion cannot be undone.
- Show a pending state. Every selection control and row checkbox is locked. A polite status names the deletion.
- On success, refetch the list and the summary, clear the selection, keep selection mode on, announce the count, and move focus.
- On a conflict, refetch, remove the missing ids from the selection, and explain that nothing was deleted. Offer a retry with the remaining ids.
- On any other failure, keep the selection, refetch, and show an alert with a retry.
- Document the endpoint in `README.md`.


# Not included

- A confirmation dialog or undo.
- Soft delete or a trash view.
- Partial success. A batch never deletes some rows and skips others.
- Optimistic removal of the visible rows.
- Selecting more than 100 todos, or every todo across all pages.
- Changes to `PATCH /todos/batch`, `DELETE /todos`, or `DELETE /todos/:todoId`.

- `apps/web/src/api/todo.api.ts` `updateSelectedTodos` parses the input first and turns a `409` into `TodoApiError` type `batch_conflict` with `missingIds`.

- `apps/web/src/module/todo.batchCompletion.ts` has `getBatchRetryIds`, which drops `missingIds` on a conflict and keeps every id otherwise. Its messages are about marking, not deleting.
- `apps/web/src/module/todo.selection.ts` has `clear` and `remove_ids`.
- `apps/web/src/components/TodoSelectionBar.tsx` takes `isPending`, `input`, `result`, `error`, `onMarkSelected`, and `onRetry` for the mark buttons. It locks every control while `isPending`.
- `apps/web/src/routes/index.tsx` `markSelected` dispatches `clear` on success and `remove_ids` on a conflict. On success it sets `pendingSelectionFocus` to `page_button` unless `list_emptied` already chose `empty_heading`. Row checkboxes are locked with `batchMutation.isPending`.
- `apps/web/src/module/todo.clearCompleted.ts` uses the wording "Clearing completed todos" and "Cleared 3 completed todos."
- `e2e/tests/update-selected-todos.spec.ts` mocks `/todos` with an in-memory list.

# Acceptance criteria

## API

[ ] `POST /todos/batch-delete` with `{ ids: [a, b] }` returns `200` with `{ deletedCount: 2 }`. Both rows are gone.

[ ] Todos not in `ids` are not deleted.

[ ] An empty `ids` array returns `400`.

[ ] 101 ids return `400`. 100 ids return `200`.

[ ] Duplicate ids return `400` with the issue "ids must be unique".

[ ] A non-UUID id returns `400`.

[ ] A missing body or a missing `ids` returns `400`.

[ ] When one or more ids do not exist, the response is `409` with `{ error: { type: "batch_conflict", missingIds } }`. No row is deleted, including the rows that exist.

[ ] Sending the same request twice returns `200` and then `409` with every id missing.

[ ] A database failure returns `500` with the internal error body. No row is deleted.

## Frontend

[ ] In selection mode, the bar shows a delete button. Its label names the count: "Delete 1 selected todo" or "Delete 3 selected todos". At 0 selected it reads "Delete selected todos".

[ ] The button uses the red destructive style. A note under it reads "Deleted todos cannot be restored." The button is described by the note.

[ ] The button is `aria-disabled` and ignores clicks when nothing is selected.

[ ] Clicking it sends one `POST /todos/batch-delete` with the selected ids.

[ ] While it is pending, the delete button, both mark buttons, "Select this page", "Clear selection", "Done", and every row checkbox are `aria-disabled` and ignore input. Escape does nothing.

[ ] While it is pending, a polite status reads "Deleting 3 todos".

[ ] On success, the list and the summary refetch. The selection is cleared. Selection mode stays on. A polite status reads "Deleted 3 todos." or "Deleted 1 todo."

[ ] On success, focus moves to "Select this page" when rows remain. When the list is empty, focus moves to the empty heading, as it does today.

[ ] On a `409`, the list refetches. The missing ids leave the selection. The other ids stay. An alert reads "2 selected todos no longer exist. They were removed from the selection. Nothing was deleted."

[ ] After a `409` with ids left, the alert has a "Retry" button. It deletes the remaining ids.

[ ] After a `409` with no ids left, the alert reads "None of the selected todos exist anymore. Nothing was deleted." It has no "Retry" button.

[ ] On a network error, a `400`, a `500`, or a bad response, the list refetches. The selection is kept. An alert reads "Could not delete the selected todos. Nothing was deleted." with a "Retry" button that sends the same ids.

[ ] On any failure, focus stays on the delete button.

[ ] Only one batch message shows at a time. Starting a delete clears the last mark message, and starting a mark clears the last delete message.

[ ] The alert clears on the next batch request, on "Clear selection", on "Done", and on a scope change.

[ ] Keyboard: Tab reaches the delete button. Enter and Space activate it. The focus ring is visible.


## Expected failures

| **Failure** | **When it happens** | **How it is represented** |
| --- | --- | --- |
| Bad body | `ids` is missing, empty, over 100, has a duplicate, or has a non-UUID. | `400` with `validationErrorResponseSchema`. The service returns `request_validation`. |
| Missing ids | One or more ids have no row when the delete runs. | The transaction rolls back. `409` with `batchConflictErrorResponseSchema`. The repository returns `BatchConflictError`. |
| Conflict in the browser | The adapter gets a `409`. | `TodoApiError` type `batch_conflict` with `missingIds`. |
| Other failure in the browser | Network error, `400`, `500`, or a body that fails the response schema. | The existing `TodoApiError` types. |

## Unexpected failures

A database error inside the transaction rolls it back. The route logs it and returns `500` with the internal error body. In the browser, an error that is not a `TodoApiError` is logged with `console.error`, as in the other hooks, and shown with the generic alert.

# Design decisions

- **Route path:** `POST /todos/batch-delete`. A `DELETE` with a body is poorly supported by proxies and clients. `POST` has no `:todoId` route, so nothing can shadow it.
- **One request, one transaction:** `deleteSelectedTodos` copies the `updateSelectedTodos` shape. Inside `db.transaction`, one `delete from todos where id in (...) returning id`. If the returned ids are fewer than the input, it records the missing ids and calls `tx.rollback()`. The rollback maps to `BatchConflictError`. Any other throw maps to `DatabaseError`.
- **No pre-check select:** The `returning` list already shows which ids matched. A separate select adds a query and a race window.
- **Reuse the conflict:** `BatchConflictError`, `batchConflictErrorResponseSchema`, and the adapter's `batch_conflict` type already exist. No new error type.
- **Shared ids schema:** `selectedTodoIdsSchema` holds the 1 to 100, UUID, and unique rule once. `updateSelectedTodosSchema` uses it with no change in behavior.
- **Not idempotent:** A repeated delete returns `409`, like `DELETE /todos/:todoId` returns `404`. Nothing is deleted twice. The client never retries on its own.
- **Adapter:** `deleteSelectedTodos(input)` in `todo.api.ts` follows `updateSelectedTodos`. It parses the input first. A bad input throws `request_validation` and sends nothing. A `409` throws `batch_conflict`.
- **Hook:** `useDeleteSelectedTodosMutation` follows `useUpdateSelectedTodosMutation`. It uses `retry: 0` and invalidates `todoListQueryKey` on success and on error.
- **Messages:** New `todo.batchDelete.ts` holds `getBatchDeleteLabel`, `getBatchDeletePendingMessage`, `getBatchDeleteResultMessage`, and `getBatchDeleteErrorMessage`. It reuses `getBatchRetryIds` from `todo.batchCompletion.ts`. The wording follows "Cleared 3 completed todos."
- **Destructive wording:** The label says "Delete" and names the count, so the user sees what goes before clicking. The note says the deletion is permanent. A red border and red text set it apart from the mark buttons. No dialog, matching "Clear completed".
- **Bar props:** `TodoSelectionBar` gains `deleteInput`, `deleteResult`, `deleteError`, `onDeleteSelected`, and `onRetryDelete`. `isPending` becomes true when either batch is pending. The page resets the other mutation before it starts one, so only one status or alert shows.
- **Locking:** Row checkboxes lock when either batch is pending. This keeps the ids on screen equal to the ids in flight.
- **Focus:** On success, the deleted rows leave the list. Focus moves to "Select this page" through `pendingSelectionFocus`. When the list empties, the existing `list_emptied` path sets `empty_heading` first and wins. When the page goes past the last page, the existing redirect runs and focus lands once the target renders. On failure, focus stays on the delete button so "Retry" is one Tab away.
- **Retry:** "Retry" sends `getBatchRetryIds(deleteError, deleteInput.ids)`, not the live selection.

# Certainty checks

### 1. What information enters the system?

A JSON body with `ids` on `POST /todos/batch-delete`. In the browser, the selected ids from the reducer.

### 2. How will you check that information?

The service parses the body with `deleteSelectedTodosSchema`. It checks 1 to 100 ids, UUID format, and uniqueness. The browser adapter runs the same schema before it sends.

### 3. What will the operation return when it succeeds?

`200` with `{ deletedCount }`, equal to the number of ids.

### 4. What expected failures can happen?

A bad body, ids that do not exist, a network error, a server error, and a response that fails the schema.

### 5. How will each expected failure be represented?

A bad body is `400` with issues. Missing ids are `409` with `missingIds`. In the browser, a `409` becomes `TodoApiError` type `batch_conflict`. The rest use the existing error types and show the generic alert.

### 6. Where will the route, business rules, and database or UI work live?

The route and response mapping live in `todo.routes.ts`. Body parsing lives in `todo.service.ts`. The transaction lives in `todo.repository.ts`. The browser request lives in `todo.api.ts`. The text lives in `todo.batchDelete.ts`. The bar draws the controls. `HomePage` wires them.

### 7. What tests will you write before implementation?

Contract, repository, route, adapter, hook, message, bar, page, and browser tests. They are listed below.

### 8. How will you prove the whole operation works through its real boundaries?

The API route tests call `app.inject` against a disposable Postgres database. They check the response and then read the rows back, including after a `409`. A Playwright test drives the full browser flow against a mocked `/todos` with an in-memory list, as the other browser tests do.

### 9. Does this change multiple records or call another system? If yes, how will failure be handled safely?

Yes. It deletes up to 100 rows. One transaction holds the delete. A missing id or a database error rolls it back, so no row is lost. The client never retries on its own. A manual retry sends only ids that still existed, and a repeat is refused with `409`.

### 10. If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?

Ready: the delete button with its count and note. Empty selection: the button is `aria-disabled`. Pending: every selection control locked and a polite status. Success: a polite status, a cleared selection, and focus on "Select this page" or the empty heading. Conflict: an alert with the removed count and, when ids remain, a retry. Error: an alert with a retry. Accessibility: a named button described by the note, `aria-disabled` that keeps focus, a polite status, an alert, and a visible focus ring.
