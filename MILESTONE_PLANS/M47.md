# Objective

Plan explicit selection without confusing selection with completion.

# Included

- Add a "Select todos" button that turns selection mode on. Add a "Done" button that turns it off.
- In selection mode, each row shows a selection checkbox. The completion checkbox, Edit, and Delete are hidden. The row keeps its "Active" or "Completed" badge.
- Add a "Select this page" button that adds every visible row to the selection. When every visible row is already selected, it reads "Unselect this page" and removes them.
- Add a "Clear selection" button that empties the selection and keeps selection mode on.
- Show a selected count: "3 selected" or "1 selected".
- Limit the selection to 100 todos. A change that would go over 100 is refused as a whole and explained.
- Keep the selection while the user moves between pages and changes the page size. The selection belongs to one status and one search.
- Clear the selection when the status or the search changes, when the user leaves selection mode, when the user reloads, and when the list becomes empty.
- Hide toggle-all and "Clear completed" in selection mode.
- Hold the selection in a reducer with explicit states and actions.
- Give every control a clear label, and move focus on entry and exit.
- Test the reducer, the selection bar, the list in selection mode, the route, and the browser flow.

# Not included

- Any action on the selected todos. Batch complete, batch delete, and their API come in a later milestone.
- Backend, API contract, or database changes.
- Keeping the selection in the URL or in browser storage.
- Selecting every todo across all pages in one action.
- Changes to toggle-all, "Clear completed", search, filters, or pagination rules outside selection mode.

# Current repository evidence

- `packages/contracts/src/index.ts` has no batch or selection schema. `todoPageSizeQuerySchema` and `todoListResponseSchema.pageSize` cap a page at 100. The 100-item limit matches this cap, so one full page can always be selected.
- `apps/api/src/module/todo.routes.ts` has no endpoint that takes a list of ids. Selection is frontend state only.
- `apps/web/src/router.tsx` allows only `status`, `search`, `page`, and `pageSize` in the URL. Any other key redirects to the canonical URL. The selection cannot live in the URL without changing this.
- `apps/web/src/routes/index.tsx` `HomePage` reads `filter`, `search`, `page`, and `pageSize` from the URL. It renders `TodoToggleAll` above the list and `TodoClearCompleted` below it. It already computes `rowMutationPending` and `bulkPending`.
- `apps/web/src/components/TodoList.tsx` `TodoListItem` renders the completion checkbox with the label "Mark {title} as completed" or "Mark {title} as active". It renders Edit and Delete buttons and keeps their refs for delete focus.
- `apps/web/src/components/TodoList.tsx` `TodoItems` renders the empty heading with `tabIndex={-1}` when the page has no items.
- `apps/web/src/hooks/useTodoListQuery.ts` keys each page by `{ status, search, page, pageSize }` and uses `keepPreviousData`. Rows from the last page stay on screen while the next page loads.
- `apps/web/src/module/todo.state.ts` `getTodoListViewState` gives `ready`, `refreshing`, `loading_query`, `initial_loading`, and error states. Only states with `items` can be selected.
- `e2e/tests/toggle-all-todos.spec.ts` and `e2e/tests/clear-completed-todos.spec.ts` mock `/todos` with an in-memory list and read `status`, `search`, `page`, and `pageSize`.

# Contracts

## Input

Clicks and keys on the selection controls. The selected todo ids come from the rows on screen. They are UUIDs already checked by `todoListResponseSchema`. No request is sent.

The scope comes from the URL: `{ status, search }`. `page` and `pageSize` are not part of the scope.

## Success

The reducer returns the next selection state. The view shows the count, the checked rows, and the bar labels from that state.

## Expected failures

| **Failure** | **When it happens** | **How it is represented** |
| --- | --- | --- |
| Over the limit | A row check or "Select this page" would make the selection larger than 100. | The reducer keeps the selection and sets `notice: "limit"`. A polite status shows the limit message. |
| View changed | The status or the search changes while selection mode is on. | The reducer empties the selection and sets `notice: "scope_changed"`. A polite status shows the message. |
| List empties | The list refetches with `totalItems` 0 while selection mode is on. | The reducer returns `off`. Focus moves to the empty heading. |
| List fails | The list query fails while selection mode is on. | Selection mode stays on with its selection. The rows are hidden by the existing error state. The bar stays so the user can leave with "Done". |

## Unexpected failures

An unknown action type is a type error at build time. The reducer uses an exhaustive `match`. No runtime path can throw.

# Design decisions

- **One checkbox per row:** In selection mode, the row shows only the selection checkbox. The completion checkbox is hidden, not disabled. A click on a row checkbox can never change completion. The badge still shows the completion state as text.
- **Separate names:** The selection checkbox is named "Select {title}". The completion checkbox keeps "Mark {title} as completed". A screen reader never hears one name for both jobs.
- **Explicit entry:** Selection mode starts only from "Select todos". A row checkbox never starts it. This keeps the standard view the same as M46.
- **Reducer states:** `todo.selection.ts` exports `selectionReducer`. The state is `{ mode: "off" }` or `{ mode: "on", scope, selectedIds, notice }`. `scope` is `{ status, search }`. `selectedIds` is a `ReadonlySet<string>`. `notice` is `null`, `"limit"`, or `"scope_changed"`.
- **Reducer actions:** `enter`, `exit`, `toggle_row`, `select_page`, `unselect_page`, `clear`, `scope_changed`, and `list_emptied`. In `off`, every action except `enter` returns the same state.
- **Limit:** `SELECTION_LIMIT = 100`. `toggle_row` and `select_page` compute the next set. If its size is over 100, they keep the old set and set `notice: "limit"`. A partial add is never made, so the user is never left guessing which rows went in.
- **Query-scoped persistence:** `HomePage` dispatches `scope_changed` from an effect when `status` or `search` differs from the stored scope. The reducer keeps the same set if the scope is equal and empties it if not. Page and page size are not in the scope, so the set survives paging.
- **Memory only:** The state lives in `useReducer` in `HomePage`. It is not in the URL and not in storage. A reload starts in `off`.
- **Clearing rules:** "Done", Escape, a scope change, and an empty list clear the selection. "Clear selection" empties it and stays in `on`. A create, a refetch, or a page change does not clear it.
- **Hidden standard batch controls:** `HomePage` does not render `TodoToggleAll` or `TodoClearCompleted` in `on`. Their mutations cannot start, so no bulk write can run while a selection is held.
- **Entry lock:** "Select todos" is `aria-disabled` while any row or bulk mutation is pending. This keeps a pending row action from finishing under a row that has lost its controls.
- **Page button label:** `getSelectPageState` returns `select` when any visible row is not selected and `unselect` when all are. The label is "Select this page" or "Unselect this page". The button is `aria-disabled` when the page has no rows.
- **Count:** "{n} selected" in a `role="status"` region with `aria-live="polite"`. The notice is a second polite region under it, so a limit or scope message does not replace the count.
- **Bar:** New `TodoSelectionBar` component. A `div` with `role="group"` and `aria-label="Selection"`. It replaces "Select todos" in the same spot above the list.
- **Focus:** On entry, focus moves to "Select this page". After "Clear selection", focus moves to "Select this page", because the clear button becomes `aria-disabled`. On exit, focus moves to "Select todos". When the list empties, focus moves to the empty heading through the existing `emptyHeadingRef`.
- **Escape:** A `keydown` handler on a wrapper around the bar and the list dispatches `exit` on Escape. The edit form is not rendered in selection mode, so its Escape handler never competes.
- **Stale ids:** The client sees one page at a time. A selected todo on another page can be deleted by another client. The id stays in the set and the count includes it. The later batch action must report missing ids.

# Certainty checks

### 1. What information enters the system?

Clicks and keys on the selection controls, the ids of the visible rows, and the `status` and `search` values from the URL.

### 2. How will you check that information?

The ids come from a list response already parsed by the contract. The reducer only accepts ids passed by the view. The scope comes from the route search, which the router already validates.

### 3. What will the operation return when it succeeds?

The next selection state. The view shows the count and the checked rows from it.

### 4. What expected failures can happen?

A change over the 100-item limit, a status or search change, an empty list after a refetch, and a list query failure.

### 5. How will each expected failure be represented?

The limit and the scope change set a `notice` and show a polite message. The empty list returns `off` and moves focus. A list failure keeps the selection and shows the existing error.

### 6. Where will the route, business rules, and database or UI work live?

`todo.selection.ts` holds the rules and text. `TodoSelectionBar` draws the bar. `TodoList` draws the row checkboxes. `HomePage` wires the reducer, the scope, and focus. The API and database do not change.

### 7. What tests will you write before implementation?

Tests for the reducer and helpers, the bar, the list in selection mode, and the route, then a Playwright test. They are listed below.

### 8. How will you prove the whole operation works through its real boundaries?

A Playwright test seeds todos across two pages, enters selection mode, selects rows on both pages, changes the page size, hits the limit, changes the filter, and exits. It checks that no write request is sent and that the badges never change.

### 9. Does this change multiple records or call another system? If yes, how will failure be handled safely?

No. Selection changes no record and calls no system. Toggle-all and "Clear completed" are hidden in selection mode, so no bulk write can run while a selection is held.

### 10. If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?

Loading: "Select todos" is hidden. Empty: "Select todos" is hidden, and an empty refetch leaves selection mode. Ready: "Select todos", or the bar and row checkboxes. Error: the bar stays with "Done" over the existing list error. Pending: "Select todos" is `aria-disabled` while any mutation runs. Accessibility: a labelled group, a polite count, a polite notice, one named checkbox per row, Escape to leave, and focus moved on entry, clear, exit, and empty.
