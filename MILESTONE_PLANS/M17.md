#### Objective:
Plan full replacement of a todo's mutable fields.

## Included
- A PUT /todos/:todoId route in the API.
- Path param validation.
- Body validation.
- 200 with the updated todo on success, the same shape as todoSchema.
- 404 when the id is well-formed but no row exists.
- 400 when the id is malformed, and a separate 400 when the body is malformed.
- 500 for repository database errors and stored-row validation errors.
- The database write, including bumping the existing `updated_at` column.
- Route-level mapping tests plus integration tests through app.inject.

## Not included
- PATCH or any partial-update route. Omitting a field is a 400, not "leave it unchanged."
- Upserting: PUT never creates a row at a client-chosen id.
- Exposing `updatedAt` in the response body or in todoSchema.
- Changes to GET /todos, GET /todos/:todoId, or POST /todos.
- Delete.
- Frontend integration or UI.

## Current repository evidence
What files, commands, or existing patterns did you inspect before making this plan?
- apps/api/src/db/schema.ts:3-9: `todos` has `id`, `title`, `completed`, `createdAt`, and `updatedAt`. `updatedAt` is `.defaultNow()`, which only fires on insert. Nothing in the codebase currently writes to it on update, because nothing updates a row yet.
- packages/contracts/src/index.ts:3-8: `todoSchema` is `{ id, title, completed, createdAt }`. `updatedAt` is not part of the contract today, and this milestone does not add it.
- packages/contracts/src/index.ts:12: `createTodoSchema = todoSchema.pick({ title: true })` is the existing precedent for deriving a request-body schema from `todoSchema` instead of writing field rules twice.
- apps/api/src/module/todo.repository.ts: `createTodo` and `getTodoById` share a private `toRow` helper that re-validates a raw DB row against `todoSchema` and returns `Result<Todo, ValidationError>`. There is no `updateTodo`/`replaceTodo` function yet. `getTodoById` is the closest existing pattern for turning "no row" into `err({ type: "not_found", id })`, but it does it with a plain `select`, not an `update ... returning`.
- apps/api/src/module/todo.service.ts: `createTodoService` is the only service function. It parses a raw request body with a contract schema first, short-circuiting to a `RequestValidationError` before ever calling the repository. This is the pattern a body-carrying write route should follow, not the route-level `request.query`/`request.params` casting used by the read routes.
- apps/api/src/module/todo.routes.ts:267-289: `GET /todos/:todoId` already has `parseTodoId(rawId)` (reusing `todoIdParamSchema`) and validates the path param at the route level, before any database call. PUT can reuse `parseTodoId` as-is for its own path param.
- apps/api/src/module/todo.routes.ts:203-217: the `POST /todos` handler shows the shape a body-validating write route takes: call the service, map `RequestValidationError` to 400 without logging it, log everything else, then hand the result to a `to*Response` mapper.

## Acceptance criteria
- PUT /todos/:todoId with an existing todo's id and a valid `{ title, completed }` body returns 200 with the updated todo, matching `todoSchema` exactly.
- The 200 body reflects the new `title` and `completed` values, not the old ones.
- `id` and `createdAt` never change, even if the client sends different values for them in the body.
- A todo not touched by the request is completely unaffected: its title, completed, and createdAt stay exactly what they were.
- PUT /todos/:todoId with a well-formed UUID that matches no row returns 404 with a `notFoundErrorResponseSchema` body. No row is created.
- PUT /todos/abc (malformed id) returns 400 with a `validationErrorResponseSchema` body, and neither the body nor the database is touched.
- PUT with a missing `title`, missing `completed`, a `title` under 6 or over 100 characters after trimming, or a `completed` that isn't a boolean, returns 400 with `validationErrorResponseSchema`, and no database write happens.
- When both the id and the body are invalid, the response is the id's 400, and the body is never parsed. The two 400 cases are never combined into one response.
- A repository `DatabaseError` maps to 500 with `internalErrorResponseSchema`.
- A repository `ValidationError` (the row returned by the update fails todoSchema) maps to 500, not 200 and not 404.
- The `updated_at` column changes on a successful update. It is verified directly against the database in a test, since the response body does not expose it.
- Adding the route does not break GET /todos, GET /todos/:todoId, or POST /todos. All existing tests for those routes still pass unchanged.

## Contracts
### Input
#### What information enters the operation?
Two things: the `todoId` path parameter and a JSON body with exactly two meaningful fields, `title` and `completed`. Both fields are required; there is no default for either. Any other body field is silently ignored, the same way `createTodoSchema` already ignores extra fields on create.

### Success
#### What exact value or visible result means success?
HTTP 200 with a body matching `todoSchema`: `{ id, title, completed, createdAt }`, where `title` and `completed` are the values from the request body, and `id`/`createdAt` are unchanged from before the request. The body is the todo itself, unwrapped, matching GET /todos/:todoId and POST /todos.

### Expected failures
| Failure | When it happens | How it is represented |
|---------|------------------|------------------------|
| Malformed id | todoId is not a well-formed UUID | HTTP 400, validationErrorResponseSchema body |
| Malformed body | `title` missing, too short, too long, or not a string; `completed` missing or not a boolean | HTTP 400, validationErrorResponseSchema body |
| Todo not found | todoId is a well-formed UUID but no row has that id | HTTP 404, notFoundErrorResponseSchema body |
| Repository database error | the update query rejects | HTTP 500, internalErrorResponseSchema body |
| Repository validation error | the row returned by the update fails todoSchema | HTTP 500, internalErrorResponseSchema body |

### Unexpected failures
Not applicable

| Layer | Responsibility |
|-------|-----------------|
| Contract | packages/contracts owns `replaceTodoSchema`, derived from `todoSchema.pick({ title: true, completed: true })`, and `ReplaceTodoInput`. `todoIdParamSchema`, `todoSchema`, and the three response schemas are reused as-is |

## Certainty checks
### What information enters the system?
A path parameter, `todoId`, and a JSON body with `title` and `completed`.

### How will you check that information?
The id reuses the existing `parseTodoId`/`todoIdParamSchema` exactly as GET /todos/:todoId does. The body gets a new `replaceTodoSchema.safeParse`, run inside `updateTodoService`, following the same "parse first, short-circuit to `RequestValidationError`" shape `createTodoService` already uses for POST /todos.

### What will the operation return when it succeeds?
HTTP 200 with the updated todo.

### What expected failures can happen?
A malformed id is a 400. A malformed body is a separate 400. A well-formed id with no matching row is a 404. A database failure or a stored row that fails validation is a 500. See the Expected failures table.

### How will each expected failure be represented?
`parseTodoId` runs first at the route level and short-circuits to 400 with `validationErrorResponseSchema` before the body is touched. Past that point, `updateTodoService` parses the body: a `RequestValidationError` becomes 400 the same way `toCreateTodoResponse` handles it. A `not_found` from the repository becomes 404 with `notFoundErrorResponseSchema`. `validation` and `database` both become 500 with `internalErrorResponseSchema`.

### Where will the route, business rules, and database work live?
Path validation lives in the route. Body validation lives in `updateTodoService` in todo.service.ts. The schema lives in packages/contracts/src/index.ts. The database write is a new `replaceTodoById` in apps/api/src/module/todo.repository.ts.

### Does this change multiple records or call another system?
No.

## Design decisions
This section spells out the mechanics the sections above only reference.

- **Both `title` and `completed` are required, not optional**: this is a PUT, which HTTP treats as replacing the whole resource representation, not a partial patch. `id` and `createdAt` are server-controlled, so a todo's only mutable fields are `title` and `completed` — "the whole representation" means both of them. Making either optional would silently reintroduce PATCH semantics under a PUT route and create ambiguity: if `completed` is omitted, does the server keep the old value or reset it? Requiring both removes that question entirely. A PATCH route, if ever added, is where partial updates belong.
- **PUT never creates a missing todo (no upsert)**: standard PUT semantics allow "create at a client-chosen URI" if the server opts in. This API doesn't: every id is server-generated, and the only place a todo is created is POST /todos, which relies on that default. Letting PUT create a row at an arbitrary client-supplied id would add a second, inconsistent id-generation path with no default-generation logic behind it. A well-formed id with no match is a 404, full stop.
- **Atomic `UPDATE ... RETURNING`, not check-then-write**: `replaceTodoById` issues one `db.update(todos).set(...).where(eq(todos.id, id)).returning()` call. If `returning()` comes back empty, that means no row matched, so it's `not_found`. A separate `SELECT` before the `UPDATE` would add a second round trip and a race window for no benefit, the same reasoning `getTodoById` already applies to a single `SELECT`.
- **`updated_at` is bumped explicitly, using the database's clock**: Drizzle's `.defaultNow()` on `updatedAt` only fires on insert, never on update, so a plain `.set({ title, completed })` would leave `updated_at` stuck at creation time forever. `replaceTodoById` sets it explicitly with `sql\`now()\``, matching how `createdAt` already gets its value from the database rather than the Node process, so both columns come from the same clock. The response body does not expose this field today, since todoSchema has no `updatedAt`, so this is purely a data-integrity concern, not a contract change. Flagged for review since it's a write with no visible effect from the client's side.
- **Id is validated before the body is even parsed**: the route calls `parseTodoId` first, exactly like GET /todos/:todoId. If the id is malformed, the handler returns 400 immediately and never reads `request.body`. This means a request with both a bad id and a bad body always gets the id's 400 — the two validation failures are never merged into one response, and a client fixing only the id will see the body error on their next attempt, not both at once.
- **Body validation lives in a service function, not the route**: `POST /todos` already proves the pattern (`createTodoService`) for a route that must parse a request body before touching the database. `updateTodoService` follows the same shape rather than inlining a `safeParse` call into the route handler, keeping `todo.routes.ts` focused on HTTP concerns (params, status codes) and `todo.service.ts` focused on request-shape rules.
- **`replaceTodoSchema` is derived, not hand-written**: `todoSchema.pick({ title: true, completed: true })`, the same technique `createTodoSchema` already uses for `{ title: true }`. This guarantees the title length rule can never drift between create and replace.
- **Extra body fields are silently ignored**: a client sending `{ title, completed, id: "...", createdAt: "..." }` has the stray fields stripped by `replaceTodoSchema`, the same as `createTodoSchema` already does. This is not a 400, matching existing precedent rather than introducing a stricter rule only for this route.
- **Response is unwrapped**: 200 returns the todo object directly, consistent with GET /todos/:todoId and POST /todos.
- **Success validation**: `toReplaceTodoResponse` re-parses the repository's returned value with `todoSchema` before sending 200, the same defensive step every other mapper in this file takes. A row that fails that parse becomes a 500, not a 200 with a malformed body.
- **`getTodoById`, `listTodos`, `createTodo`, and `createTodoService` are untouched**: this milestone adds one new repository function and one new service function; it does not change anything the existing GET/POST routes rely on.

## Risks and assumptions
- Assumes the path is `PUT /todos/:todoId`, reusing the existing `/todos/:todoId` route depth rather than a separate collection.
- Assumes both `title` and `completed` are required on every PUT, with no partial-update path. If product wants "toggle just `completed`" as a common client operation, that's a future PATCH milestone, not a relaxation of this one.
- Assumes PUT never creates a missing todo. Flagging for review since plain HTTP PUT semantics permit upsert-by-client-id; this API deliberately opts out because ids are always server-generated.
- Assumes `updated_at` should be written correctly even though nothing reads it yet. Flagging for review since it's effort spent on a column with no visible effect until a later milestone exposes it.
- Assumes a malformed id always wins over a malformed body when both are wrong, so the client only ever sees one 400 at a time. Flagging for review since some APIs try to report all validation problems in one response.
- Assumes extra/unknown body fields (a client-sent `id` or `createdAt`) are silently dropped rather than rejected, matching `createTodoSchema`'s existing behavior.
- Assumes a stored row failing `todoSchema` after the update is a 500, matching how GET and the list route already treat that case.
- Assumes `replaceTodoById`'s single `UPDATE ... RETURNING` is race-safe enough for this API's needs (no concurrent-edit conflict detection, no optimistic locking). Two clients replacing the same todo at once will just have the later write win, which is out of scope here.
