#### Objective: Add page-number pagination to the filtered and searched list

## Included
- page and pageSize query params on GET /todos.
- Defaults when page and/or pageSize are omitted.
- A hard maximum on pageSize, rejected with 400 when exceeded.
- Rejecting non-integer, zero, or negative page/pageSize values with 400.
- Handling a duplicate page or pageSize query param.
- A total count of matching rows (after status filter and search are applied), returned as response metadata.
- Total page count, derived from the total count and pageSize.
- Defined behaviour for a page number beyond the last page.
- Pagination applied on top of the existing status filter and search, not replacing them.
- Database query changes: a COUNT query plus a LIMIT/OFFSET query, both scoped by the same filter/search condition.
- Regression tests so existing unfiltered, status-filtered, and searched list behaviour still passes, updated for the new response shape.

## Not included
- Cursor-based or keyset pagination.
- Frontend integration or UI.
- Configurable/unbounded pageSize.

The route test at todo.routes.test.ts:205 asserts expect(response.json()).toEqual({ items: [] }), an exact match with no other keys.

## Acceptance criteria
- GET /todos with no page/pageSize returns page 1 with the default pageSize, status 200.
- GET /todos?page=2&pageSize=5 returns the second slice of 5 matching todos (items 6-10 in sort order), status 200.
- The response body includes items, page, pageSize, totalItems, and totalPages.
- totalItems is the count of rows matching the current status filter and search term, independent of pagination.
- totalPages is ceil(totalItems / pageSize), or 0 when totalItems is 0.
- GET /todos?page=<beyond the last page> returns 200 with an empty items array and accurate totalItems/totalPages metadata. It does not 404.
- GET /todos?page=0, ?page=-1, ?page=1.5, ?page=abc all return 400 with a validationErrorResponseSchema body. No query hits the database.
- GET /todos?pageSize=0 and ?pageSize=<over the cap> both return 400. pageSize is never silently clamped to the cap.
- GET /todos?page=1&page=2 (duplicate) and ?pageSize=5&pageSize=10 (duplicate) both return 400.
- GET /todos?status=active&search=foo&page=1&pageSize=5 applies status and search first, then paginates over that filtered/matched set - totalItems reflects only active todos matching "foo", not the whole table.
- Sort order (createdAt asc, id asc) is unchanged and stays stable across page boundaries: no item is skipped or duplicated between consecutive pages.
- All existing unfiltered, status-filtered, and search tests still pass, updated for the new response/return shape.

## Certainty checks
### What information enters the system?
An optional status string, an optional search string, an optional page integer, and an optional pageSize integer. Four independent query params.

### How will you check that information?
A pure function, parsePagination(rawPage, rawPageSize), runs alongside the existing parseStatusFilter/parseSearchQuery. It explicitly checks that each raw value is either undefined or a single string (an array, from a duplicate param, is rejected outright, the same way parseStatusFilter and parseSearchQuery already reject non-string values, rather than relying on how JavaScript would coerce an array to a number). A string is then checked against the contract schema: a positive integer, and for pageSize, no greater than the cap.

### What will the operation return when it succeeds?
HTTP 200 with the extended body described in the Success section above.

### What expected failures can happen?
Invalid or duplicate page/pageSize returns 400, on top of the existing invalid/duplicate status/search checks. A repository DatabaseError or ValidationError returns 500. See the Expected failures table.

### How will each expected failure be represented?
parseStatusFilter, parseSearchQuery, and parsePagination all run before any database call, checked in that order. The first one that returns an error short-circuits the route to a 400 with a validationErrorResponseSchema body. Database and row-validation errors still go through the existing internalErrorResponseSchema path.

### Where will the route, business rules, and database work live?
Query validation lives in apps/api/src/module/todo.routes.ts's parsePagination, plus new schemas in packages/contracts/src/index.ts. Counting and paginating live in apps/api/src/module/todo.repository.ts's listTodos.

### What tests will you write before implementation?
Check "Tests to write first" below.

### How will you prove the whole operation works through its real boundaries?
Route-level tests via app.inject, using real query strings against a disposable Postgres database. They cover pagination alone, pagination combined with status and search, defaults, the last partial page, an out-of-range page, and every invalid-input case.

## Pagination design decisions
This section spells out the mechanics the sections above only reference.

- **Defaults**: page defaults to 1, pageSize defaults to 20, when the param is omitted. GET /todos with no query params at all still returns a paginated response (page 1, pageSize 20, plus totals), not the old unpaginated shape.
- **Limits**: page has no upper bound (an unreachable page is not an error, see "Out-of-range pages" below). pageSize has a hard maximum of 100. A pageSize above 100 is rejected with 400, never silently clamped down to 100, same philosophy as the existing search length limit, which rejects rather than truncates.
- **Total counting**: totalItems is computed with a COUNT(*) query that applies the exact same status/search and() condition as the page query, so it always reflects "how many rows match the current filter," not the whole table. This is a second, separate query, run before the page query, rather than one combined query with a window function, simpler to read and test, at the cost of one extra round trip per request. Flagged as a possible future optimization if it ever matters at this table's size.
- **Order of operations**: within the route, validate status, then search, then page/pageSize, in that order, short-circuiting to 400 on the first failure - no query reaches the database until all four inputs are valid. Within the repository, build the shared status/search condition first, run the count query, compute totalPages from the count, then run the page query with limit/offset using the same condition and the existing sort order.
- **Out-of-range pages**: if page is beyond the last page (e.g. page=5 when only 2 pages of results exist), the response is still HTTP 200, with items: [] and totalItems/totalPages reflecting the true totals. This is not a 400 or 404 - an out-of-range page number is not an invalid request, it is simply a page with nothing on it, the same way scrolling past the end of a list doesn't error. page=1 on zero matching rows is likewise 200 with items: [] and totalPages: 0.
- **Response metadata**: page, pageSize, totalItems, and totalPages are returned as flat top-level fields alongside items, not nested under a pagination key - this keeps the shape a minimal, additive change on top of today's { items }.
- **Database queries**: offset = (page - 1) * pageSize. The page query is db.select().from(todos).where(condition).orderBy(asc(todos.createdAt), asc(todos.id)).limit(pageSize).offset(offset). The count query is db.select({ value: count() }).from(todos).where(condition), using drizzle-orm's count() helper (already available at the installed version), read back as Number(rows[0].value).
- **Regression tests**: listTodos's return type changes from Todo[] to { items, page, pageSize, totalItems, totalPages }. Every existing repository test that reads listed.value as an array directly must be updated to read listed.value.items. Every existing route test that asserts an exact response body (notably the { items: [] } check at todo.routes.test.ts:205) must be updated to include the new default pagination fields. This is expected churn, not a sign something is wrong.

## Risks and assumptions
- Assumes the query params are named page and pageSize, matching the milestone's "page-number pagination" framing, rather than limit/offset. Flagging this for review rather than deciding it unilaterally.
- Assumes defaults of page=1 and pageSize=20 when omitted, so an unqualified GET /todos still returns a bounded, paginated response rather than the whole table.
- Assumes a hard pageSize cap of 100, enforced by rejecting with 400, not silently clamping, consistent with how the search term length limit already behaves.
- Assumes page/pageSize must be positive integers; anything else (zero, negative, decimal, non-numeric, duplicate) is a 400, never coerced to a nearest valid value.
- Assumes a page beyond the last page is a normal, successful request: 200 with an empty items array and accurate totals, not a 404. Flagging this for review since some APIs choose to 404 or clamp to the last valid page instead.
- Assumes pagination metadata is flat on the response body (page, pageSize, totalItems, totalPages alongside items), not nested under a pagination key. Flagging this for review.
- Assumes the total count is fetched via a separate COUNT(*) query rather than a single windowed query, trading one extra round trip per request for simpler, more readable code. Not expected to matter at this table's current size.
- Assumes pagination is not opt-in: every GET /todos call is now paginated, even with no query params at all. This changes listTodos's return type from a bare array to an object, which is a breaking change to every existing call site and test, not just an additive one.
- Assumes sort order (createdAt asc, id asc) stays exactly as-is, since it must stay stable for page boundaries to be meaningful.
