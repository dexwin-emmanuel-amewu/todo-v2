# Objective

Plan the full-stack operation that marks specific todos complete or active.

# Included

- Add `PATCH /todos/batch`. The body is `{ ids, completed }`.
- Accept 1 to 100 ids. Every id is a UUID. Duplicate ids are refused.
- Update every listed todo in one database transaction. Either all change or none change.
- When any id does not exist, roll back and answer `409` with the missing ids.
- Add the request, response, and conflict schemas to the contracts package.
- Test the schemas, the repository, and the route against a real database.
- Add a browser API adapter and a mutation hook for the new endpoint.
- In selection mode, add "Mark selected as completed" and "Mark selected as active" buttons to the selection bar.
- Show a pending state. The bar buttons and row checkboxes are locked. A polite status names the change.
- On success, refetch the list and the summary, clear the selection, keep selection mode on, and announce the count.
- On a conflict, refetch, remove the missing ids from the selection, and explain that nothing changed. Offer a retry with the remaining ids.
- On any other failure, keep the selection, refetch, and show an alert with a retry.
- Test the adapter, hook, reducer, bar, route, and browser flow.

# Not included

- Batch delete.
- Changing titles in a batch.
- Partial success. A batch never updates some rows and skips others.
- Optimistic updates of the visible rows.
- Undo or a confirmation dialog.
- Selecting more than 100 todos, or every todo across all pages.
- Changes to `PATCH /todos` (toggle-all) or `DELETE /todos` (clear completed).

# Acceptance criteria

## API

[ ] `PATCH /todos/batch` with `{ ids: [a, b], completed: true }` returns `200` with `{ updatedCount: 2 }`. Both rows are completed.

[ ] `completed: false` marks the listed rows active.

[ ] Rows already in the target state are counted and still return `200`.

[ ] Todos not in `ids` do not change.

[ ] An empty `ids` array returns `400`.

[ ] 101 ids return `400`. 100 ids return `200`.

[ ] Duplicate ids return `400` with the issue "ids must be unique".

[ ] A non-UUID id returns `400`.

[ ] A missing or non-boolean `completed` returns `400`.

[ ] When one or more ids do not exist, the response is `409` with `{ error: { type: "conflict", missingIds } }`. No row changes, including the rows that exist.

[ ] A database failure returns `500` with the internal error body. No row changes.

[ ] `PATCH /todos/batch` is never handled by `PATCH /todos/:todoId`.

## Frontend

[ ] In selection mode, the bar shows "Mark selected as completed" and "Mark selected as active".

[ ] Both buttons are `aria-disabled` and ignore clicks when nothing is selected.

[ ] Clicking one sends one `PATCH /todos/batch` with the selected ids and the matching boolean.

[ ] While it is pending, both buttons, "Select this page", "Clear selection", "Done", and every row checkbox are `aria-disabled` and ignore input. Escape does nothing.

[ ] While it is pending, a polite status reads "Marking 3 todos as completed" or "Marking 3 todos as active".

[ ] On success, the list and the summary refetch. The selection is cleared. Selection mode stays on. A polite status reads "3 todos marked as completed" or "1 todo marked as active". Focus moves to "Select this page".

[ ] On a `409`, the list refetches. The missing ids leave the selection. The other ids stay. An alert reads "2 selected todos no longer exist. They were removed from the selection. Nothing was changed."

[ ] After a `409` with ids left, the alert has a "Retry" button. It sends the remaining ids with the same boolean.

[ ] After a `409` with no ids left, the alert reads "None of the selected todos exist anymore. Nothing was changed." It has no "Retry" button.

[ ] On a network error, a `400`, a `500`, or a bad response, the list refetches. The selection is kept. An alert reads "Could not update the selected todos. Nothing was changed." with a "Retry" button that sends the same ids and boolean.

[ ] The alert clears on the next batch request, on "Clear selection", on "Done", and on a scope change.

[ ] Keyboard: Tab reaches both new buttons. Enter and Space activate them. The focus ring is visible.

# Contracts

## Input

`PATCH /todos/batch` with a JSON body.

```ts
export const updateSelectedTodosSchema = z.object({
  ids: z
    .array(z.uuid())
    .min(1)
    .max(100)
    .refine((ids) => new Set(ids).size === ids.length, { message: "ids must be unique" }),
  completed: z.boolean(),
});

export type UpdateSelectedTodosInput = z.infer<typeof updateSelectedTodosSchema>;
```

## Success

`200` with:

```ts
export const updateSelectedTodosResponseSchema = z.object({
  updatedCount: z.number().int().min(1).max(100),
});
```

`updatedCount` always equals `ids.length`, because a batch either updates every id or none.

## Expected failures

| **Failure** | **When it happens** | **How it is represented** |
| --- | --- | --- |
| Bad body | `ids` is empty, over 100, has a duplicate, or has a non-UUID. `completed` is missing or not a boolean. | `400` with `validationErrorResponseSchema`. The service returns `request_validation`. |
| Missing ids | One or more ids have no row when the update runs. | The transaction rolls back. `409` with `{ error: { type: "conflict", missingIds: string[] } }`. The repository returns `{ type: "conflict", missingIds }`. |
| Conflict in the browser | The adapter gets a `409`. | `TodoApiError` with type `conflict` and `missingIds`. |
| Other failure in the browser | Network error, `400`, `500`, or a body that fails the response schema. | The existing `TodoApiError` types. |

New contract schema:

```ts
export const conflictErrorResponseSchema = z.object({
  error: z.object({
    type: z.literal("conflict"),
    missingIds: z.array(z.uuid()).min(1),
  }),
});
```

## Unexpected failures

A database error inside the transaction rolls it back. The route logs it and returns `500` with the internal error body. In the browser, an error that is not a `TodoApiError` is logged with `console.error`, as in the toggle-all hook, and shown with the generic alert.

# Design decisions

- **Route path:** `PATCH /todos/batch`. Fastify matches static paths before parametric ones, so `:todoId` never sees "batch". A route test proves it.
- **One request, one transaction:** `updateSelectedTodos` runs `db.transaction`. Inside it, one `update todos set completed, updated_at = now() where id in (...) returning id`. If the returned ids are fewer than the input, it records the missing ids and calls `tx.rollback()`. The repository maps that rollback to `ConflictError`. Any other throw maps to `DatabaseError`.
- **No pre-check select:** The `returning` list already shows which ids matched. A separate select would add a query and a race window.
- **Same-state rows count:** The update sets `completed` on every listed row, even if it already has that value. This keeps `updatedCount === ids.length` and makes a retry safe.
- **Unique ids at the boundary:** Duplicates are refused, not removed. The client never sends them, so a duplicate means a bug. Refusing it keeps the count exact.
- **Limit of 100:** It matches `SELECTION_LIMIT` and the page size cap. The contract is the single check on the server. The client already cannot select more.
- **New error type:** `ConflictError = { type: "conflict"; missingIds: string[] }` in `db/errors.ts`. `toUpdateSelectedTodosResponse` maps it to `409` with an exhaustive `match`.
- **Adapter:** `updateSelectedTodos(input)` in `todo.api.ts` parses the input with the contract first. A bad input throws `request_validation` and sends nothing. A `409` is parsed with `conflictErrorResponseSchema` and throws `TodoApiError` type `conflict` with `missingIds`. `TodoApiErrorType` gains `conflict`.
- **Hook:** `useUpdateSelectedTodosMutation` follows `useSetAllTodosCompletedMutation`. It uses `retry: 0` and invalidates `todoListQueryKey` on success and on error, so the list and the summary refetch either way.
- **Reducer:** Add one action, `remove_ids`, which deletes the given ids and keeps the mode and scope. Success uses the existing `clear`. Conflict uses `remove_ids` with `missingIds`.
- **Locking:** `TodoSelectionBar` and `TodoList` take a `locked` prop. While the batch is pending, every selection control is `aria-disabled`. Escape is ignored. This keeps the ids on screen equal to the ids in flight.
- **Retry:** The failure state in `HomePage` stores `{ kind, completed, retryIds }`. For a generic failure, `retryIds` is the sent ids. For a conflict, it is the sent ids minus `missingIds`. "Retry" sends `retryIds`, not the live selection.
- **Messages:** `todo.batchCompletion.ts` holds the text helpers: `getBatchPendingMessage`, `getBatchSuccessMessage`, and `getBatchFailureMessage`. Plurals follow the existing "1 todo" and "3 todos" style.
- **Live regions:** The pending and success text goes in one polite status in the bar. The failure goes in a `role="alert"` in the bar, as in `TodoToggleAll`.
- **Focus:** On success, focus moves to "Select this page", because both batch buttons become `aria-disabled`. On failure, focus stays on the clicked button so the alert's "Retry" is one Tab away.

# Certainty checks

### 1. What information enters the system?

A JSON body with `ids` and `completed` on `PATCH /todos/batch`. In the browser, the selected ids from the reducer and the button the user clicks.

### 2. How will you check that information?

The service parses the body with `updateSelectedTodosSchema`. It checks 1 to 100 ids, UUID format, uniqueness, and a boolean. The browser adapter runs the same schema before it sends.

### 3. What will the operation return when it succeeds?

`200` with `{ updatedCount }`, equal to the number of ids.

### 4. What expected failures can happen?

A bad body, ids that do not exist, a network error, a server error, and a response that fails the schema.

### 5. How will each expected failure be represented?

A bad body is `400` with issues. Missing ids are `409` with `missingIds`. In the browser, a `409` becomes `TodoApiError` type `conflict`. The rest use the existing error types and show the generic alert.

### 6. Where will the route, business rules, and database or UI work live?

The route and response mapping live in `todo.routes.ts`. Body parsing lives in `todo.service.ts`. The transaction lives in `todo.repository.ts`. The browser request lives in `todo.api.ts`. The text lives in `todo.batchCompletion.ts`. The bar draws the controls. `HomePage` wires them.

### 7. What tests will you write before implementation?

Contract, repository, route, adapter, hook, reducer, message, bar, list, route page, and browser tests. They are listed below.

### 8. How will you prove the whole operation works through its real boundaries?

The API route tests call `app.inject` against a disposable Postgres database. They check the response and then read the rows back, including after a `409`. A Playwright test drives the full browser flow against a mocked `/todos` with an in-memory list, as the other browser tests do.

### 9. Does this change multiple records or call another system? If yes, how will failure be handled safely?

Yes. It changes up to 100 rows. One transaction holds the update. A missing id or a database error rolls it back, so no row changes. The client never retries on its own. A manual retry is safe because the update sets a fixed value.

### 10. If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?

Ready: both batch buttons in the bar. Empty selection: both buttons `aria-disabled`. Pending: every selection control locked and a polite status. Success: a polite status, a cleared selection, and focus on "Select this page". Conflict: an alert with the removed count and, when ids remain, a retry. Error: an alert with a retry. Accessibility: named buttons, `aria-disabled` that keeps focus, a polite status, an alert, and a visible focus ring.
