#### Objective:
Plan partial update of one todo.

## Included
- A PATCH /todos/:todoId route in the API.
- Path param validation, reusing `parseTodoId`/`todoIdParamSchema` exactly as GET and PUT already do.
- Body validation accepting any non-empty subset of `{ title, completed }`.
- Rejecting an empty body `{}` with 400.
- `title`, when present, validated with the same rule as `todoSchema` (string, 6-100 chars after trimming).
- `completed`, when present, validated as a boolean.
- 200 with the full updated todo on success, the same shape as `todoSchema`.
- A field omitted from the request body is left exactly as it was; PATCH never resets an unspecified field to a default.
- 404 when the id is well-formed but no row exists.
- 400 when the id is malformed, and a separate 400 when the body is malformed or empty.
- 500 for repository database errors and stored-row validation errors.
- The database write, including bumping `updated_at`, only for the columns actually supplied.
- Route-level mapping tests, service tests, repository tests, and integration tests through `app.inject`, including live tests that PATCH and PUT the same todo the same way and assert their status codes and effects differ where the spec says they must.

## Not included
- Exposing `updatedAt` in the response body or in `todoSchema`.
- Changes to GET /todos, GET /todos/:todoId, or POST /todos.
- Delete.
- Concurrency control (optimistic locking, conflict detection between two simultaneous updates).
- Frontend integration or UI.

## Acceptance criteria
- PATCH /todos/:todoId with an existing todo's id and `{ title: "New title" }` returns 200 with the updated todo; `completed` is unchanged from before the request.
- PATCH /todos/:todoId with an existing todo's id and `{ completed: true }` returns 200 with the updated todo; `title` is unchanged from before the request.
- PATCH /todos/:todoId with `{ title: "New title", completed: true }` returns 200 and updates both fields.
- The exact same `{ title: "New title" }` body sent to PUT /todos/:todoId for the same todo returns 400, because PUT requires `completed` too. This is the concrete PATCH-vs-PUT distinction, verified with both routes live.
- `id` and `createdAt` never change, regardless of what the client sends.
- A todo not touched by the request is completely unaffected: its title, completed, and createdAt stay exactly what they were.
- PATCH /todos/:todoId with `{}` returns 400 with a `validationErrorResponseSchema` body, and no database write happens.
- PATCH /todos/:todoId with a body containing only unrecognized fields (e.g. `{ "notes": "x" }`) returns the same 400 as an empty body, since those fields are stripped before the emptiness check.
- PATCH with a `title` present but under 6 or over 100 characters after trimming, or not a string, returns 400 with `validationErrorResponseSchema`, and no database write happens.
- PATCH with a `completed` present but not a boolean returns 400 with `validationErrorResponseSchema`, and no database write happens.
- PATCH /todos/:todoId with a well-formed UUID that matches no row returns 404 with a `notFoundErrorResponseSchema` body. No row is created.
- PATCH /todos/abc (malformed id) returns 400 with a `validationErrorResponseSchema` body, and neither the body nor the database is touched.
- When both the id and the body are invalid (or the body is empty), the response is the id's 400, and the body is never parsed. The two 400 cases are never combined into one response.
- A repository `DatabaseError` maps to 500 with `internalErrorResponseSchema`.
- A repository `ValidationError` (the row returned by the patch fails `todoSchema`) maps to 500, not 200 and not 404.
- The `updated_at` column changes on a successful patch, even a single-field one. It is verified directly against the database, since the response body does not expose it.
- Adding the route does not break GET /todos, GET /todos/:todoId, POST /todos, or PUT /todos/:todoId. All existing tests for those routes still pass unchanged.

## Contracts
### Input
#### What information enters the operation?
Two things: the `todoId` path parameter and a JSON body containing zero, one, or both of `title` and `completed`. At least one of the two must be present after unrecognized fields are stripped; an empty or effectively-empty body is a validation failure, not a no-op.

### Success
#### What exact value or visible result means success?
HTTP 200 with a body matching `todoSchema`: `{ id, title, completed, createdAt }`. Any field present in the request body takes the new value; any field absent from the request body keeps its previous value. `id` and `createdAt` are always unchanged. The body is the todo itself, unwrapped, matching GET /todos/:todoId, POST /todos, and PUT.

### Expected failures
| Failure | When it happens | How it is represented |
|---------|------------------|------------------------|
| Malformed id | todoId is not a well-formed UUID | HTTP 400, validationErrorResponseSchema body |
| Empty body | body is `{}`, or contains only fields outside `{ title, completed }` | HTTP 400, validationErrorResponseSchema body |
| Malformed body | `title` present but too short, too long, or not a string; `completed` present but not a boolean | HTTP 400, validationErrorResponseSchema body |
| Todo not found | todoId is a well-formed UUID but no row has that id | HTTP 404, notFoundErrorResponseSchema body |
| Repository database error | the update query rejects | HTTP 500, internalErrorResponseSchema body |
| Repository validation error | the row returned by the update fails todoSchema | HTTP 500, internalErrorResponseSchema body |

### Unexpected failures
Not applicable

### Responsibilities
| Layer | Responsibility |
|-------|-----------------|
| Contract | packages/contracts owns `patchTodoSchema`, derived from `todoSchema.pick({ title: true, completed: true }).partial()` plus a refinement rejecting an empty parsed result, and `PatchTodoInput`. `todoIdParamSchema`, `todoSchema`, `replaceTodoSchema`, and the three response schemas are reused as-is |
| Route | apps/api/src/module/todo.routes.ts adds `toPatchTodoResponse` and registers `PATCH /todos/:todoId`. It reuses `parseTodoId` to validate the path param first, short-circuiting to 400 before the body is even parsed |

| Hook / View | Not applicable |

## Certainty checks
### What information enters the system?
A path parameter, `todoId`, and a JSON body with zero or more of `title` and `completed`.

### How will you check that information?
The id reuses the existing `parseTodoId`/`todoIdParamSchema` exactly as GET /todos/:todoId and PUT do. The body gets a new `patchTodoSchema.safeParse`, run inside `patchTodoFlow`, following the same "parse first, short-circuit to `RequestValidationError`" shape `createTodoFlow` and `replaceTodoFlow` already use. The schema strips unrecognized fields, then a refinement checks that at least one of `title`/`completed` survived.

### What will the operation return when it succeeds?
HTTP 200 with the updated todo, its unspecified fields carried over unchanged.

### What expected failures can happen?
A malformed id is a 400. An empty or all-unrecognized-fields body is a 400. A body with a present-but-invalid `title` or `completed` is a separate 400. A well-formed id with no matching row is a 404. A database failure or a stored row that fails validation is a 500. See the Expected failures table.

### How will each expected failure be represented?
`parseTodoId` runs first at the route level and short-circuits to 400 with `validationErrorResponseSchema` before the body is touched. Past that point, `patchTodoFlow` parses the body: a `RequestValidationError` (empty body or invalid field) becomes 400 the same way `toReplaceTodoResponse` handles it for PUT. A `not_found` from the repository becomes 404 with `notFoundErrorResponseSchema`. `validation` and `database` both become 500 with `internalErrorResponseSchema`.

### Where will the route, business rules, and database work live?
Path validation lives in the route. Body validation lives in `patchTodoFlow` in todo.service.ts. The schema lives in packages/contracts/src/index.ts. The database write is a new `patchTodoById` in apps/api/src/module/todo.repository.ts, which conditionally sets only the supplied columns.

### Does this change multiple records or call another system?
No.

## Design decisions
This section spells out the mechanics the sections above only reference.

- **`patchTodoSchema` makes every field optional, but forbids the empty result**: `todoSchema.pick({ title: true, completed: true }).partial()` makes both fields optional; a `.refine((data) => Object.keys(data).length > 0, { message: "At least one field must be provided" })` on top rejects a body where neither field survived parsing. This is checked on the *parsed* object, not the raw body, so a body like `{ "notes": "x" }` — which has content but no recognized field — is correctly treated as empty after stripping, not accepted as "the client sent something."
- **This is the load-bearing difference from PUT, and it is now directly testable**: `replaceTodoSchema` (already in the working tree) is `todoSchema.pick({ title: true, completed: true })` with both fields required. `patchTodoSchema` is the same pick with `.partial()` plus the empty-check refinement. Because PUT is now implemented and registered as a live route, the plan includes an integration test that sends the identical `{ title: "New title" }` body to both PATCH (200) and PUT (400) for the same todo, in the same test — a direct behavioral proof, not just a schema-level assertion.
- **The repository sets only the columns the client actually supplied**: `patchTodoById` builds its `set()` payload by checking `input.title !== undefined` and `input.completed !== undefined` individually, rather than spreading `input` directly like `replaceTodoById` spreads its two required fields. This avoids relying on whether zod's `.partial()` output omits an absent key entirely versus including it with value `undefined` — the explicit checks are correct either way. `updated_at` is always included in the `set()` payload, even for a single-field patch, since any accepted PATCH is a real write.
- **PATCH never creates a missing todo (no upsert)**: identical reasoning to PUT — every id is server-generated, the only creation path is POST /todos, and a well-formed id with no match is a 404, full stop.
- **Atomic `UPDATE ... RETURNING`, not check-then-write**: `patchTodoById` issues one `db.update(todos).set(...).where(eq(todos.id, id)).returning()` call, the same shape `replaceTodoById` already uses. An empty `returning()` means no row matched, so it's `not_found`.
- **`updated_at` is bumped explicitly, using the database's clock**: `.defaultNow()` only fires on insert. `patchTodoById` sets `updatedAt: sql\`now()\`` explicitly on every accepted patch, matching exactly what `replaceTodoById` already does, so both write paths share the same clock source.
- **Id is validated before the body is even parsed**: the route calls `parseTodoId` first, exactly like GET /todos/:todoId and PUT. If the id is malformed, the handler returns 400 immediately and never reads `request.body`. A request with both a bad id and an empty/invalid body always gets the id's 400.
- **Body validation lives in a flow function, not the route**: `patchTodoFlow` follows the same shape `createTodoFlow` and `replaceTodoFlow` already established, keeping `todo.routes.ts` focused on HTTP concerns and `todo.service.ts` focused on request-shape rules. The function is named `patchTodoFlow`, matching the `<verb>TodoFlow` convention the codebase already uses, not `patchTodoService`.
- **Extra body fields are silently stripped, not rejected outright**: consistent with `createTodoSchema` and `replaceTodoSchema`'s existing behavior. The only place "extra fields" becomes an error is indirectly, when stripping leaves nothing recognized behind and the empty-check refinement fires.
- **Response is unwrapped**: 200 returns the todo object directly, consistent with GET /todos/:todoId, POST /todos, and PUT.
- **Success validation**: `toPatchTodoResponse` re-parses the repository's returned value with `todoSchema` before sending 200, the same defensive step every other mapper in this file takes, including `toReplaceTodoResponse`. A row that fails that parse becomes a 500, not a 200 with a malformed body.
- **`getTodoById`, `listTodos`, `createTodo`, `createTodoFlow`, `replaceTodoById`, `replaceTodoFlow`, `toReplaceTodoResponse`, and the PUT route are untouched**: this milestone adds one new repository function, one new service function, and one new route; it does not change PUT's behavior or any of the existing GET/POST/PUT machinery.

## Risks and assumptions
- Assumes the path is `PATCH /todos/:todoId`, reusing the existing `/todos/:todoId` route depth.
- Assumes PATCH accepts any non-empty subset of `{ title, completed }`.
- Assumes an empty body, and a body containing only unrecognized fields, are both 400. Flagging for review: some APIs treat `{}` as a no-op 200 ("nothing to change, here's the todo unchanged"); this plan treats it as a client error instead, on the theory that a PATCH with nothing to patch is almost always a bug on the caller's side.
- Assumes PATCH never creates a missing todo (no upsert), matching PUT.
- Assumes malformed id always wins over an invalid or empty body when both are wrong, so the client only ever sees one 400 at a time.
- Assumes `updated_at` should be written correctly even though nothing reads it yet, and even for a single-field patch. Flagging for review since it's effort spent on a column with no visible effect until a later milestone exposes it.
- Assumes a stored row failing `todoSchema` after the patch is a 500, matching how GET, POST, and PUT already treat that case.
- Assumes `patchTodoById`'s single `UPDATE ... RETURNING` is race-safe enough for this API's needs (no concurrent-edit conflict detection, no optimistic locking). Two clients patching the same todo at once will just have the later write win, out of scope here.
- Assumes PUT's implementation from `feat/m18-replace-todo` (commit 0b6e58a: `replaceTodoSchema`, `replaceTodoById`, `replaceTodoFlow`, `toReplaceTodoResponse`, the PUT route) merges or rebases onto `feat/m20-update-todo` unchanged before PATCH work starts. Flagging for review: if that branch is rewritten, renamed, or merged with conflicts first, the "Current repository evidence" and test-33/34 comparisons in this plan should be re-verified against whatever actually lands on this branch.
- Assumes extra/unknown body fields are silently dropped rather than individually rejected, matching `createTodoSchema` and `replaceTodoSchema`'s existing behavior
