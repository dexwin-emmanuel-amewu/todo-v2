## Objective
Plan an atomic operation that removes every completed todo.

## Included
- A `DELETE /todos` route, separate from the existing `DELETE /todos/:todoId`.
- A required `?status=completed` selector.
- 400 for a bare `DELETE /todos`, `?status=all`, `?status=active`, any other value, a repeated `status`, or a `search`/`page`/`pageSize` param. Nothing is deleted.
- Once the selector passes, every row with `completed = true` is removed. No search, pagination, or id-list narrowing.
- One `DELETE FROM todos WHERE completed = true RETURNING id` statement, owned by the repository.
- 200 with `{ "deletedCount": number }`.
- Nothing to delete is 200 with `{ "deletedCount": 0 }`.
- 500 for repository database errors.
- Selector tests, mapper tests, repository tests, and `app.inject` integration tests.

## Not included
- Soft delete. Rows are gone, same as `DELETE /todos/:todoId`.
- Deleting active todos or the whole table. `?status=all` and `?status=active` are rejected, not implemented.
- Delete by id list or by search.
- Returning the deleted todos.
- A service function. This route reads no body.
- Changes to any existing route.
- Frontend work.

## Acceptance criteria
- With 2 completed and 3 active todos, `DELETE /todos?status=completed` returns 200 with `{ "deletedCount": 2 }` and leaves the 3 active todos unchanged.
- Afterwards `GET /todos?status=completed` reports `totalItems: 0` and `GET /todos?status=active` reports `totalItems: 3`.
- Afterwards `GET /todos/:todoId` for a deleted id returns 404.
- With nothing completed, or an empty table, the call returns 200 with `{ "deletedCount": 0 }`.
- Called twice, the first call's count is above 0 and the second is 0. Both 200.
- `DELETE /todos` with no query string returns 400 and deletes nothing.
- `?status=all`, `?status=active`, `?status=banana`, and a repeated `status` each return 400 and delete nothing.
- `?status=completed&search=oat` returns 400 and deletes nothing. Same for `page` and `pageSize`.
- A repository `DatabaseError` is 500 with `internalErrorResponseSchema`.
- Every existing route still behaves as before.

## Certainty checks
### What information enters the system?
One query param, `status`.

### How will you check that information?
`parseDeleteCompletedSelector(rawStatus, rawSearch, rawPage, rawPageSize)` in todo.routes.ts, before any database work. Ok only when `status` is the string `"completed"` and none of the other three is present. Everything else is a `request_validation` error naming what was wrong.

### What will the operation return when it succeeds?
200 with the number of todos deleted.

### What expected failures can happen?
Bad selector is 400, database failure is 500. See the table above.

### How will each expected failure be represented?
The parser short-circuits to 400 with `validationErrorResponseSchema` at the route, before the database. A `database` error becomes 500 with `internalErrorResponseSchema`.

### Where will the route, business rules, and database work live?
Selector validation in the route. Response schema in packages/contracts. The delete in `deleteCompletedTodos`.

### Does this change multiple records or call another system?
Yes. It removes zero or more rows in one statement.

## Design decisions
- **`DELETE /todos?status=completed`, not `POST /todos/clear-completed`**: `PATCH /todos` already set the collection-route precedent.
- **The selector is required**: a bare `DELETE /todos` is a 400, never a full wipe. This is the guard the whole route hangs on.
- **`status=completed` is the only accepted value**: `all` and `active` are refusals, not gaps. Reusing `parseStatusFilter` would default a missing `status` to `all`, which here means deleting everything on a typo.
- **`search`, `page`, `pageSize` are rejected, not ignored**: ignoring `?search=oat` would delete every completed todo while the caller expected a few. Stricter than the rest of the API. Flagging for review.
- **Scope is the whole collection**: the condition is the same `eq(todos.completed, true)` `listTodos` uses, so `GET /todos?status=completed` lists exactly what this removes.
- **The repository owns the transaction, as one statement**: one `DELETE ... RETURNING` is atomic in Postgres. There is no second query to wrap, so no `db.transaction()`. Same shape as `deleteTodoById` and `setAllTodosCompleted`.
- **The count comes from `RETURNING id`, not a separate `COUNT`**: a count before the delete could be stale by the time the delete runs.
- **200 with `{ deletedCount }`, not 204**: a bulk clear has a number worth reporting. `deletedCount` parallels `PATCH /todos`'s `updatedCount`. Flagging for review, since `DELETE /todos/:todoId` returns 204.
- **The deleted todos are not returned**: doesn't scale, and `GET /todos` gives the new state.
- **Nothing to delete is 200 with `deletedCount: 0`**: there is no id to miss, so no 404. This also makes a repeat call idempotent without special-casing.
- **Hard delete**: no `deleted_at` column, same as `DELETE /todos/:todoId`.
- **Two failure modes only**: bad selector (400), database error (500). No `not_found`, and no `ValidationError`, since the response is a count rather than a `Todo`.
- **No service function**: no body to parse, so the route calls the repository directly.
- **No concurrency handling**: Postgres row locking as-is.

## Risks and assumptions
- Assumes `DELETE /todos` with a required `?status=completed`, not an action-style path.
- Assumes a bare `DELETE /todos` deletes nothing. The whole route hangs on this. Flagging for review.
- Assumes `?status=all` and `?status=active` are rejected. A later milestone can implement them deliberately.
- Assumes `search`, `page`, and `pageSize` are rejected rather than ignored. Stricter than every other route here. Flagging for review.
- Assumes 200 with a count, not 204. Flagging for review, since `DELETE /todos/:todoId` returns 204.
- Assumes a hard delete. Deleted todos are not recoverable.
- Assumes nothing to delete is 200 with `deletedCount: 0`, so a repeat call is idempotent.
- Assumes one `DELETE ... RETURNING` is atomic enough on its own and `rows.length` is the authoritative count.
- Assumes no handling for a concurrent single-todo write racing this delete.
- Assumes Fastify turns a repeated `status` into an array. Test 7 checks this rather than trusting it.
