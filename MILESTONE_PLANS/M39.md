# Objective

Plan how a user searches todo titles.

# Included

- Add a search box above the list, next to the status controls.
- Keep the committed search in the URL as `?search=milk`. No search means no search param.
- Validate the text with `todoSearchQuerySchema` (trimmed, 100 characters at most). An empty or blank value means no search.
- Keep what the user is typing in local draft state. Commit it to the URL 300 ms after the last keystroke, or at once on Enter.
- Put the committed search in the query key, next to the status.
- Send the committed search to `GET /todos` as `search` through the browser API adapter.
- Reset the page when the search or the status changes.
- Combine search with the status filter. Both apply together.
- Keep the search when the status changes. Keep the status when the search changes.
- Add a Clear search button, and clear on Escape.
- Show a count and an empty message that name the search text.
- Keep the last list on screen while a new query loads. Show a loading message for it.
- Keep create, toggle, edit, and delete working in every search view.
- Test the adapter, query hook, search state, view state, components, route, and browser flow.

# Not included

- Backend, API contract, or database changes. `GET /todos?search=` already exists.
- Pagination controls. Only the page reset rule is planned here.
- Highlighting the matched text in rows.
- Search on fields other than the title.
- Saving the search in local storage.
- Clear completed and toggle all controls.

# Current repository evidence

- `packages/contracts/src/index.ts` defines `todoSearchQuerySchema` as `z.string().trim().max(100)`. It has no minimum.
- `apps/api/src/module/todo.routes.ts` reads `search` in `GET /todos`. A missing or empty value means no search. A value over 100 characters returns 400.
- `apps/api/src/module/todo.repository.ts` `listTodos` uses `ilike` with an escaped pattern. The match is case-insensitive and substring based. The search is joined to the status with `and`, and `totalItems` counts only the matching rows.
- `apps/web/src/api/todo.api.ts` `fetchTodoList(status)` takes only a status.
- `apps/web/src/hooks/useTodoListQuery.ts` builds the key as `["todos", "list", { status }]` with `staleTime: 30_000`. It has no `placeholderData`.
- `apps/web/src/module/todo.filter.ts` parses only `status` in `getTodoListSearch`.
- `apps/web/src/router.tsx` uses `validateSearch: getTodoListSearch`. Its `beforeLoad` compares `location.searchStr` with a string built from `status` only, and redirects with `replace: true` when they differ.
- `apps/web/src/components/TodoFilters.tsx` renders `Link`s with `search={{ status }}`. They would drop a search param today.
- `apps/web/src/module/todo.state.ts` has no state for a query change. A key change today gives `pending`, which shows "Loading todos" and removes the list.
- `apps/web/src/components/TodoList.tsx` keeps `emptyMessages` per status and shows a count through `countLabel(filter, totalItems)`.
- The create, completion, replace, and delete hooks invalidate `todoListQueryKey`. Prefix matching refreshes every searched key too.
- The web app has no pagination yet. No `page` param exists in the URL or the adapter.
- `e2e/tests/filter-todos.spec.ts` mocks `/todos` with a URL predicate and records each request.

# Acceptance criteria

[ ] A search box labelled "Search todos" sits above the list. It is a `search` landmark with a visible label.

[ ] Opening `/` shows an empty box and sends `GET /todos` with no search param.

[ ] Opening `/?search=milk` fills the box with `milk` and sends `GET /todos?search=milk`.

[ ] Typing sends no request on each keystroke. One request goes out 300 ms after the last keystroke.

[ ] Pressing Enter commits the search at once and cancels the pending timer.

[ ] Typing `  milk  ` commits `milk`. The URL and the request carry the trimmed value.

[ ] A blank box removes the search param and sends no search to the API.

[ ] Text over 100 characters shows "Search must be 100 characters or fewer." It is not committed, and no request is sent. The last good results stay visible.

[ ] Opening `/?search=<101 characters>` ignores the search and replaces the URL with `/`.

[ ] Opening `/?search=123` and `/?search=true` keeps the search as the strings `123` and `true`.

[ ] An old response never replaces a newer one on screen, because each query has its own key.

[ ] Each query uses its own key. Going back to an earlier query shows its cached list at once.

[ ] Search and status combine. `/?status=active&search=milk` sends both, and the count and rows match both.

[ ] Choosing a status keeps the search. Changing the search keeps the status.

[ ] Changing the search or the status removes any `page` param from the URL. The request sends no page.

[ ] Clear search empties the box, removes the param, keeps the status, and moves focus to the box. It is shown only when the box has text.

[ ] Escape in the box does the same as Clear search.

[ ] Browser back and forward restore the earlier search and fill the box with it. Typing is replaced in the URL, so each pause does not add a history entry.

[ ] While a new query loads, the last list stays visible, row actions are disabled, the count is hidden, and a status message says "Updating results".

[ ] The count shows `totalItems` and the search text, for example `2 todos matching "milk"` or `1 active todo matching "milk"`.

[ ] The empty message names the search: `No todos match "milk".` or `No active todos match "milk".` Without a search the existing messages stay.

[ ] The empty message for a search has a Clear search button.

[ ] A load failure shows the existing alert with retry. Retry refetches the current query. The box keeps the typed text.

[ ] Create, toggle, edit, and delete refresh the current searched list. A todo that no longer matches leaves the list after refresh.

# Contracts

## Input

The `search` param from the URL, and the draft text from the search box. Both are checked with `todoSearchQuerySchema`. The request is `GET /todos`, with `status` and `search` added only when they are not the defaults. There is no body.

## Success

The API returns 200 with a body that matches `todoListResponseSchema`. The adapter returns the parsed body. The page shows `items` and a count from `totalItems`. The box and the URL show the same committed search.

## Expected failures

| **Failure** | **When it happens** | **How it is represented** |
| --- | --- | --- |
| Bad URL search | The URL search is over 100 characters or not text. | The route drops the search and replaces the URL. No error is shown. |
| Bad draft | The box holds more than 100 characters after trimming. | An inline message under the box. The draft is not committed. No request is sent. |
| Bad adapter search | Code calls `fetchTodoList` with a search that fails the schema. | Reject with `TodoApiError` of type `request_validation`. Do not call `fetch`. |
| API rejects the search | The API returns 400. | `TodoApiError` of type `http` with status 400. Show the existing load alert. |
| Other HTTP failure | The API returns another non-2xx status, such as 500. | `TodoApiError` of type `http` with that status. Show the existing alert with retry. |
| Network failure | The browser cannot reach the API. | `TodoApiError` of type `network`. Show the existing alert with retry. |
| Bad response | The body is not JSON or does not match the contract. | `TodoApiError` of type `response_validation`. Show the existing alert with retry. |

## Unexpected failures

Any other thrown error goes through TanStack Query as the query error. The view shows the same safe alert and retry button. The raw error is never shown. A bad URL value never reaches the adapter because the route parses it first.

# Design decisions

- **Input validation:** One `normalizeSearch(text)` function trims the text and checks it with `todoSearchQuerySchema`. Blank means no search. The route, the box, and the adapter all use it. The box has no `maxLength`, so a long paste is flagged and not cut off. The route turns a number like `123` back into text before it validates.
- **Request timing:** The box keeps a draft. The draft is committed to the URL 300 ms after the last keystroke, or at once on Enter. The commit uses `replace`, so typing adds no history entries. An invalid draft is never committed. Requests are not aborted. React StrictMode mounts twice in development, and an abort signal would send the first request twice. A late response lands in its own cache entry and cannot replace a newer one.
- **Query identity:** The key is `["todos", "list", { status, search }]`. It uses only committed values, never the draft. Case is kept, so `Milk` and `milk` are two keys.
- **Page reset:** Every list link comes from `getTodoListSearchLink({ status, search })`. It never copies `page`, so any status or search change drops it.
- **Status combination:** Status links keep the current search. A search commit keeps the current status. The API applies both.
- **Clear search:** The button and Escape empty the draft, drop the search param right away, keep the status, and refocus the box. The empty-result message has the same button.
- **Loading and failure:** The hook uses `keepPreviousData`. A new `loading_query` state keeps the old items, shows "Updating results", hides the count, and disables row actions. A failure on a new query shows the existing alert, never the old list.
- **Draft and URL sync:** The box follows the URL when the URL search changes, so back and forward restore the text.

# Responsibilities

# Certainty checks

### 1. What information enters the system?

The search text from the box, and the `search` value in the URL.

### 2. How will you check that information?

`normalizeSearch` checks the draft. The route checks the URL value. The adapter checks it again. The API checks it last.

### 3. What will the operation return when it succeeds?

A `TodoListResponse` with the todos that match both the status and the search. `totalItems` counts them.

### 4. What expected failures can happen?

A draft that is too long, a bad URL value, a bad adapter value, a 400 or 500 from the API, a network failure, a bad response body.

### 5. How will each expected failure be represented?

A long draft shows an inline message. A bad URL value is dropped. A bad adapter value is a `request_validation` `TodoApiError`. Other failures use the existing `TodoApiError` types and the existing alert.

### 6. Where will the route, business rules, and database or UI work live?

The route parses the URL. `todo.search.ts` holds the search rules and links. The adapter makes the request. The hook owns the key and cache. The state module picks the view state. `TodoSearch`, `TodoFilters`, and `TodoList` draw the UI. The API and database do not change.

### 7. What tests will you write before implementation?

Tests for the search rules, adapter, hook, view state, components, and route, then a Playwright test. They are listed below.

### 8. How will you prove the whole operation works through its real boundaries?

A Playwright test types a search and checks the single request, the URL, the rows, and the count. It adds a status, clears the search, goes back, and opens a bad URL.

### 9. Does this change multiple records or call another system? If yes, how will failure be handled safely?

No. It only reads. A failed read shows the retry alert and the box keeps its text.

### 10. If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?

Loading: "Loading todos" at first, then "Updating results" over the old list. Empty: one message per status, with a search version. Ready: rows and count. Error: the existing alert with retry, plus the inline length message. Pending: unchanged. Accessibility: a labelled search form, a named Clear button, Escape to clear, focus back to the box after clear, and polite status regions. The box is never disabled.

# Risks and assumptions

- The router may parse a search such as `123` as a number. The plan converts it back to text and tests it.
- The current `beforeLoad` compares strings. A quoted search value could make it redirect in a loop. The plan compares parsed values and tests it.
- Adding `keepPreviousData` changes how a status change loads. The M38 tests and browser flow must be updated to match.
- A new todo that does not match the search will not appear in the searched list. This is expected.
- The 300 ms delay is a chosen default. It is one constant and easy to change.
- The pagination milestone will add the `page` param. This plan only fixes the reset rule.
