#### Objective:
Plan deletion of one todo.

## Included
- A DELETE /todos/:todoId route in the API.
- Path param validation, reusing `parseTodoId`/`todoIdParamSchema` exactly as GET, PUT, and PATCH already do.
- No request body is read or validated.
- 204 with an empty body on success.
- 404 when the id is well-formed but no row exists.
- 400 when the id is malformed.
- 500 for repository database errors.
- The database delete, implemented as a single atomic `DELETE ... RETURNING` so "no row matched" is detected without a separate `SELECT`.
- Route-level mapping tests, repository tests, and integration tests through `app.inject`, including a live GET-after-DELETE check and a repeated-DELETE check.

## Not included
- Soft delete. This is a hard delete: the row is gone from the table.
- Bulk delete (`DELETE /todos`, delete-by-filter, delete-all).
- Cascading effects on other resources (none exist yet).
- Returning the deleted todo in the response body.
- Changes to GET /todos, GET /todos/:todoId, POST /todos, PUT /todos/:todoId, or PATCH /todos/:todoId.
- Frontend integration or UI.

## Acceptance criteria
- DELETE /todos/:todoId with an existing todo's id returns 204 with an empty body.
- After a successful DELETE, `GET /todos/:todoId` for the same id returns 404.
- After a successful DELETE, `GET /todos` no longer includes the deleted todo, and `totalItems` reflects the removal.
- DELETE /todos/:todoId with a well-formed UUID that matches no row returns 404 with a `notFoundErrorResponseSchema` body.
- Deleting the same id a second time returns 404, not 204, since delete is not idempotent-success on repeat.
- DELETE /todos/abc (malformed id) returns 400 with a `validationErrorResponseSchema` body, and the database is never touched.
- A repository `DatabaseError` maps to 500 with `internalErrorResponseSchema`.
- Deleting one of two existing todos removes only that row; the other todo's id, title, completed, and createdAt are unchanged and it remains retrievable via GET.
- Adding the route does not break GET /todos, GET /todos/:todoId, POST /todos, PUT /todos/:todoId, or PATCH /todos/:todoId. All existing tests for those routes still pass unchanged.

## Certainty checks
### What information enters the system?
A single path parameter, `todoId`.

### How will you check that information?
The id reuses the existing `parseTodoId`/`todoIdParamSchema` exactly as GET/PUT/PATCH already do. No other input exists to check.

### What will the operation return when it succeeds?
HTTP 204 with an empty body.

### What expected failures can happen?
A malformed id is a 400. A well-formed id with no matching row is a 404. A database failure is a 500. See the Expected failures table.

### How will each expected failure be represented?
`parseTodoId` runs first at the route level and short-circuits to 400 with `validationErrorResponseSchema` before any database call. A `not_found` from the repository becomes 404 with `notFoundErrorResponseSchema`. `database` becomes 500 with `internalErrorResponseSchema`.

### Where will the route, business rules, and database work live?
Path validation lives in the route. There are no other business rules for a delete: no body-shape rules, no field-level rules. The database delete is a new `deleteTodoById` in apps/api/src/module/todo.repository.ts.

### Does this change multiple records or call another system?
No. A single row, by primary key.

## Design decisions
This section spells out the mechanics the sections above only reference.

- **No flow/service function**: DELETE carries no request body, so there is nothing to parse before calling the repository. This follows `GET /todos/:todoId`'s precedent (route calls the repository directly) rather than PUT/PATCH's (route calls a flow function that parses a body first). Adding an empty passthrough flow purely to match PUT/PATCH's shape would be ceremony with no behavior behind it.
- **Hard delete, not soft delete**: `todos` has no `deleted_at`/tombstone column, and adding one is out of scope here. A successful DELETE removes the row permanently. Flagging for review: some APIs prefer soft delete for auditability or recovery; that is a schema change belonging to its own milestone, not a default this plan assumes silently.
- **204 No Content, not 200 with a body**: matches conventional HTTP DELETE semantics, and there is nothing to usefully return once the row is gone. Flagging for review since it is a deliberate deviation from every other mutating route in this API, which all return 200 with the resource. Returning 200 with the now-deleted todo was considered and rejected, since echoing back data that no longer exists in the database is more confusing than useful.
- **Atomic `DELETE ... RETURNING`, not check-then-delete**: `deleteTodoById` issues one `db.delete(todos).where(eq(todos.id, id)).returning(...)` call, the same shape `replaceTodoById` and `patchTodoById` already use for `UPDATE ... RETURNING`. An empty `returning()` means no row matched, so it's `not_found`. A separate `SELECT` before the `DELETE` would add a round trip and a race window for no benefit.
- **`deleteTodoById` returns `Result<void, DatabaseError | NotFoundError>`**: no `ValidationError` in the union, since there is no row re-parsed against `todoSchema` on the way out, unlike `toRow`, which every other repository function uses because it returns a `Todo` to its caller.
- **Not idempotent-success on repeat**: a second DELETE of the same id is a 404, matching how GET treats a missing id, since after the first delete the row genuinely no longer exists. Flagging for review: an alternative, equally defensible design treats repeat DELETE as 204 ("already gone" counts as success) for idempotency; this plan picks the "tell the truth about what's in the database" option instead, consistent with how GET/PUT/PATCH already report 404 for a missing row rather than pretending otherwise.
- **Id is validated before anything else**, exactly like every other `:todoId` route: a malformed id returns 400 immediately, and the database is never touched.
- **No cascading or bulk delete**: single-row delete only. `DELETE /todos` (collection-level) and delete-by-filter are explicitly out of scope; there are no related resources to cascade to yet.
- **`toDeleteTodoResponse` mirrors the existing mappers' `match(result.error)` shape**, with a two-case union (`not_found`, `database`) instead of the larger unions `toReplaceTodoResponse`/`toPatchTodoResponse` need for their body-validation and row-validation cases.
- **`getTodoById`, `listTodos`, `createTodo`, `replaceTodoById`, `patchTodoById`, and their flows/routes are untouched**: this milestone adds one new repository function and one new route; it does not change anything the existing GET/POST/PUT/PATCH routes rely on.

## Risks and assumptions
- Assumes the path is `DELETE /todos/:todoId`, reusing the existing `/todos/:todoId` route depth.
- Assumes a hard delete with no soft-delete/tombstone column. Flagging for review: if product wants delete recovery or an audit trail later, that's a schema change and a separate milestone, not something this plan quietly forecloses but doesn't build.
- Assumes 204 No Content with an empty body on success, rather than 200 with the deleted todo. Flagging for review since it deviates from every other mutating route in this API, which all return 200 with a body.
- Assumes repeated DELETE on the same id is 404, not idempotent 204. Flagging for review since conventional HTTP DELETE idempotency arguments favor treating "already deleted" as still-204; this plan instead matches how GET/PUT/PATCH already report a missing row.
- Assumes no bulk delete or cascade handling is needed, since no related resources exist in this schema yet.
- Assumes a malformed id always short-circuits to 400 before any database work, matching every other `:todoId` route's precedent.
- Assumes `deleteTodoById`'s single `DELETE ... RETURNING` is race-safe enough for this API's needs: two concurrent deletes of the same id resolve as one 204 and one 404, with no error either way, and no additional concurrency handling is added.
