## Objective
Plan an atomic operation that marks the complete collection active or complete.

## Included
- A `PATCH /todos` route (collection-level, no `:todoId` segment), distinct from the existing `PATCH /todos/:todoId`.
- Request body validation: `{ "completed": boolean }`, where `completed` is required, not optional.
- Full-collection scope: the operation always targets every row in `todos`, with no `status`/`search`/pagination filtering carried over from `GET /todos`.
- One atomic `UPDATE ... WHERE completed IS DISTINCT FROM :completed RETURNING id` statement that owns its own transaction, touching only the rows whose `completed` value actually changes.
- 200 response with a count of the todos actually updated: `{ "updatedCount": number }`. The updated todos themselves are not returned.
- Empty-collection behaviour: an empty `todos` table (or one where every row already matches the target value) returns 200 with `{ "updatedCount": 0 }`, not 404 or 500.
- Idempotency as a natural consequence of the conditional `WHERE`: calling the route twice in a row with the same `completed` value returns `updatedCount: 0` on the second call, still with 200.
- 400 for a missing or non-boolean `completed`, including an empty body `{}`.
- 500 for repository database errors.
- Route-level mapping tests, flow tests, repository tests, and integration tests through `app.inject`, including empty-collection, mixed-starting-state, and repeat-call cases.

## Not included
- Filtered or partial bulk updates (by id list, by `status`, by `search`). This operation always applies to the entire collection.
- Deleting or creating todos.
- Returning the updated todos, or the full collection, in the response body.
- Changes to GET /todos, GET /todos/:todoId, POST /todos, PUT /todos/:todoId, PATCH /todos/:todoId, or DELETE /todos/:todoId.
- Frontend integration or UI.
- Concurrency control beyond the single atomic statement (no optimistic locking against a concurrent single-todo PUT/PATCH/DELETE racing the bulk update).

## Current repository evidence
What files, commands, or existing patterns did you inspect before making this plan?
- apps/api/src/module/todo.repository.ts:68-104 (`replaceTodoById`, `patchTodoById`): each issues a single `db.update(todos).set(...).where(eq(todos.id, id)).returning()` call and treats an empty `returning()` as `not_found`. The new `setAllTodosCompleted` keeps the one-statement shape but replaces `where(eq(todos.id, id))` with a collection-wide `where(ne/isDistinctFrom(todos.completed, completed))`, and drops the `not_found` case entirely, since there is no single id to miss.
- apps/api/src/module/todo.repository.ts:130-183 (`listTodos`): the only existing function that already reasons about `todos.completed` as a set-membership condition (`eq(todos.completed, false)` / `eq(todos.completed, true)`), which is the same column the bulk update writes to.
- apps/api/src/db/schema.ts:1-9: `completed` is `boolean().notNull().default(false)`; `updatedAt` is `.defaultNow()` and is only bumped explicitly by application code: `replaceTodoById` and `patchTodoById` both set `updatedAt: sql\`now()\`` on every write. `setAllTodosCompleted` follows the identical pattern, and only on rows it actually touches.
- apps/api/src/module/todo.routes.ts:393-415 (`PATCH /todos/:todoId`): validates `todoId` first, then calls a flow function, then maps the result. `PATCH /todos` (collection) skips the id-parsing step entirely, since there is no id in the path, and goes straight from `request.body` to a flow function.
- apps/api/src/module/todo.service.ts:42-57 (`patchTodoFlow`): parses the raw body with a schema and short-circuits to `RequestValidationError` on failure. The new flow function follows the same shape, but with a schema whose `completed` field is required rather than optional.
- packages/contracts/src/index.ts:20-27 (`patchTodoSchema`): the only existing schema with a `.refine()` guarding against an empty result, because both of its fields are optional. The collection-level schema needs no such refine, since `completed` is its only field and it is required, so `{}` already fails schema validation on its own.
- apps/api/src/db/errors.ts: `DatabaseError` already exists and is the only error type this route can produce. There is no id to miss (no `NotFoundError`), and the response is a count rather than a todo, so nothing is re-parsed against `todoSchema` (no `ValidationError`).
- README.md:68-84: the PATCH /todos/:todoId and DELETE /todos/:todoId entries are the most recently documented routes, and set the prose/curl-example format the new entry should follow.

## Acceptance criteria
- `PATCH /todos` with `{ "completed": true }`, when every todo is currently `completed: false`, returns 200 with `{ "updatedCount": <total number of todos> }`, and every todo in the table now has `completed: true`.
- `PATCH /todos` with `{ "completed": true }`, when some todos are already `completed: true` and some are `completed: false`, returns 200 with `updatedCount` equal only to the number that were `false` before the call; the already-`true` rows are left untouched, including their `updated_at`.
- `PATCH /todos` with `{ "completed": false }` behaves symmetrically, marking every todo active.
- Calling `PATCH /todos` twice in a row with the same `completed` value: the first call (from a mixed or opposite starting state) returns `updatedCount` greater than 0, and the second call returns `updatedCount: 0`. Both calls return 200.
- `PATCH /todos` on an empty `todos` table returns 200 with `{ "updatedCount": 0 }`, not 404 and not 500.
- `id`, `title`, and `createdAt` are unchanged for every todo after the call; only `completed` and `updated_at` are touched, and only on rows whose `completed` value actually changed.
- `PATCH /todos` with `{}` returns 400 with a `validationErrorResponseSchema` body, and no row is touched.
- `PATCH /todos` with `{ "completed": "true" }` (a string, not a boolean) returns 400 with `validationErrorResponseSchema`, and no row is touched.
- `PATCH /todos` with `{ "completed": true, "notes": "x" }` succeeds (200) and ignores `notes`, consistent with every other schema in this API stripping unrecognized fields.
- A repository `DatabaseError` maps to 500 with `internalErrorResponseSchema`.
- After a successful `PATCH /todos`, `GET /todos?status=active` and `GET /todos?status=completed` report `totalItems` consistent with the new state.
- Adding the route does not break GET /todos, GET /todos/:todoId, POST /todos, PUT /todos/:todoId, PATCH /todos/:todoId, or DELETE /todos/:todoId. All existing tests for those routes still pass unchanged.

## Certainty checks
### What information enters the system?
A single JSON body field, `completed`. No id, no query params.

### How will you check that information?
A new `setAllTodosCompletedSchema.safeParse`, run inside `setAllTodosCompletedFlow`, following the same "parse first, short-circuit to `RequestValidationError`" shape `createTodoFlow`, `replaceTodoFlow`, and `patchTodoFlow` already use. Unlike `patchTodoSchema`, there is no `.partial()` and no emptiness refine, since the single field is required by the schema itself.

### What will the operation return when it succeeds?
HTTP 200 with a count of how many todos were actually changed.

### What expected failures can happen?
A missing or non-boolean `completed` is a 400. A database failure is a 500. See the Expected failures table.

### How will each expected failure be represented?
`setAllTodosCompletedFlow` parses the body first; a `RequestValidationError` becomes 400 with `validationErrorResponseSchema`, the same way `toReplaceTodoResponse`/`toPatchTodoResponse` already handle it. A `database` error from the repository becomes 500 with `internalErrorResponseSchema`.

### Where will the route, business rules, and database work live?
Body validation lives in `setAllTodosCompletedFlow` in todo.service.ts. The schema lives in packages/contracts/src/index.ts. The database write is a new `setAllTodosCompleted` in apps/api/src/module/todo.repository.ts, which conditionally updates only the rows whose stored value differs from the target.

### Does this change multiple records or call another system?
Yes. It changes zero or more rows in `todos` in one statement.

## Design decisions
This section spells out the mechanics the sections above only reference.

- **Route is `PATCH /todos`, not a new action-style path**: `PATCH /todos/:todoId` already exists for a single row; `PATCH /todos` (no id segment) is the natural collection-level counterpart, using the same verb for the same kind of operation (update the `completed` field), just scoped differently. Fastify treats `/todos` and `/todos/:todoId` as distinct routes with no conflict. An alternative like `POST /todos/complete-all` was considered and rejected as an unnecessary departure from the resource-oriented shape the rest of this API already uses.
- **`completed` is required, not optional**: unlike `patchTodoSchema`, which makes both its fields optional and only forbids the fully-empty result, `setAllTodosCompletedSchema = z.object({ completed: z.boolean() })` has exactly one field and it must be present. There is no meaningful no-op version of "set all todos to some completed value" if the value itself is missing, so `{}` is a 400 by the schema's own required-field check, with no extra `.refine()` needed. Extra/unrecognized fields are still silently stripped, matching every other schema in this API.
- **Full-collection scope, not filtered**: the operation always targets every row in `todos`; it does not accept `status`/`search`/id-list scoping. Flagging for review: a plausible alternative reuses `GET /todos`'s `status`/`search` query params so a caller could scope the bulk update (e.g. "mark all active todos matching 'oat milk' as complete"). This plan rejects that scope for now, since the milestone objective is explicitly "the complete collection," and adding filter support duplicates `listTodos`'s query-parsing machinery for a use case nothing in the requirements asks for.
- **Transaction ownership: the repository, via one atomic statement, not an app-level `db.transaction()` wrapper**: `setAllTodosCompleted` issues exactly one `UPDATE ... RETURNING` statement covering every affected row. A single statement is already atomic in Postgres: either every matched row is updated and returned, or none are. There is no multi-statement sequence (no separate `SELECT` to decide what to touch, no separate `COUNT`) that would need an explicit transaction boundary to stay atomic. This mirrors `replaceTodoById`/`patchTodoById`/`deleteTodoById`'s existing precedent of one `UPDATE`/`DELETE ... RETURNING` call per operation; the only difference is the `WHERE` clause matches many rows by `completed` value instead of one row by id.
- **`WHERE completed IS DISTINCT FROM :completed`, not an unconditional update of every row**: only rows whose current `completed` differs from the target value are written. This keeps `updated_at` meaningful, since it changes only when a row's actual state changes, and makes the response count answer "how many todos changed," which is the number a caller almost always wants after a "mark all complete" action. Flagging for review: an alternative unconditionally updates every row (`UPDATE todos SET completed = :completed, updated_at = now()` with no `WHERE`) and returns the total row count regardless of prior state; this plan rejects that, since it would bump `updated_at` on rows that didn't actually change, which every other write in this API (PUT, single-todo PATCH) avoids by construction.
- **Response count, not the updated todos**: success is `{ "updatedCount": number }`, not a list of todos and not the full collection. Returning every updated todo (or the whole table) doesn't scale with collection size and isn't needed by the milestone's objective, which only asks for a completion signal. A caller that wants the new state calls `GET /todos` afterward.
- **Empty-collection behaviour is a success, not an error**: an empty `todos` table, or one where every row already matches the target value, is not a 404 or a 500. The `UPDATE` matches zero rows, `updatedCount` is `0`, and the response is still 200. There is no per-id "not found" concept for a collection operation the way there is for `PATCH /todos/:todoId`; "nothing needed changing" is a normal, successful outcome.
- **Only two failure modes exist**: a malformed body (400) and a repository database error (500). There is no `not_found` case (no id to miss) and no post-write `ValidationError` case (the repository never re-parses a row against `todoSchema`, since the response never needs to look like a `Todo`).
- **`setAllTodosCompletedFlow` mirrors `patchTodoFlow`'s shape** (parse the raw body, short-circuit to `RequestValidationError`, otherwise call the repository), and `toSetAllTodosCompletedResponse` mirrors the other mappers' `match(result.error)` structure, with a two-case union (`request_validation`, `database`) instead of the larger unions the id-scoped routes need.
- **Idempotent by construction, not by special-casing**: because the `WHERE` clause only ever touches rows that differ from the target, repeating the same call is naturally a no-op (`updatedCount: 0`) rather than requiring a separate idempotency check.
- **`getTodoById`, `listTodos`, `createTodo`, `replaceTodoById`, `patchTodoById`, `deleteTodoById`, and their existing flows/routes are untouched**: this milestone adds one new repository function, one new flow function, and one new route; it does not change anything the existing GET/POST/PUT/PATCH(id)/DELETE routes rely on.

## Risks and assumptions
- Assumes the path is `PATCH /todos` (collection-level, no id segment), not a separate action-style endpoint like `POST /todos/complete-all`.
- Assumes `completed` is required on every call, with no default and no partial/no-op form.
- Assumes the update only touches rows whose `completed` value actually differs from the target (conditional `WHERE`), not every row unconditionally. Flagging for review: an unconditional update is simpler to reason about (every row's `updated_at` reflects "the last time a bulk operation ran," not "the last time this row's data changed") but was rejected here in favor of `updated_at` staying meaningful per-row.
- Assumes the response is `{ updatedCount: number }`, not the updated todos or the full collection.
- Assumes an empty collection, and a no-op call where nothing needed changing, are both 200 with `updatedCount: 0`, not 404 or 204.
- Assumes no filtering, search, or pagination scoping is added to this endpoint; it always targets the entire `todos` table.
- Assumes a single `UPDATE ... RETURNING` statement is sufficiently atomic on its own, with no explicit `db.transaction()` wrapper needed.
- Assumes no special handling for a concurrent single-todo PUT/PATCH/DELETE racing the bulk update. Postgres's normal row-level locking during the single `UPDATE` statement is relied on as-is, with no additional optimistic-locking or conflict-detection logic added.
- Assumes extra/unknown body fields are silently stripped rather than individually rejected, matching `createTodoSchema`, `replaceTodoSchema`, and `patchTodoSchema`'s existing behavior.
