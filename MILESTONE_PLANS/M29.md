## Objective
Plan the frontend path for creating one todo.

## Included
- A title form on the home page, using the existing `createTodoSchema` rules (trimmed, 6–100 characters).
- A small API adapter function that posts the title and validates the returned todo.
- A TanStack Query mutation hook; submitting disables the form and prevents repeat submissions until the request settles.
- On success, clear the input, announce “Todo added.”, and refresh the existing todo list.
- On failure, keep the title so the user can retry and show a concise error message.
- Inline validation, pending, success, expected failure, unexpected failure, and focus behaviour.
- Adapter, form, mutation, and home-route tests.

## Not included
- Editing, completing, or deleting todos.
- Title length or validation rule changes, API changes, and new contract schemas.
- Optimistic list updates, a separate create page, or a general-purpose form framework.

## Current repository evidence
- `packages/contracts/src/index.ts`: `createTodoSchema` trims titles and requires 6–100 characters; `todoSchema` defines the returned todo.
- `apps/api/src/module/todo.routes.ts`: `POST /todos` already accepts the create input and returns 201 with the created todo.
- `apps/web/src/api/todo.api.ts`: owns `fetch`, API errors, and response parsing for the list; add the create call alongside it.
- `apps/web/src/hooks/useTodoListQuery.ts`: exports `todoListQueryKey`; use that key to refresh after a successful create.
- `apps/web/src/routes/index.tsx` and `apps/web/src/components/TodoList.tsx`: home page and list are already separate; place a focused form component above the list.
- `apps/web/src/main.tsx`: `QueryClientProvider` is already configured with one query retry. Mutations should not retry automatically, to avoid silently repeating a write.

## Acceptance criteria
- A blank or invalid title shows an inline validation message and sends no request.
- A valid title sends one `POST /todos` request with the trimmed title.
- While pending, the submit button is disabled and reads “Adding…”. Repeated clicks or Enter presses do not send another request.
- On success, the input is cleared, focus returns to the title input, “Todo added.” is announced, and the list refreshes to include the new todo.
- On expected API failure, the input remains, focus stays usable in the form, and an alert says “Could not add todo. Try again.”
- An unexpected failure is safely caught, logged for diagnosis, and shown using the same short user-facing error; it does not clear the input or break the page.
- The form has a programmatic label, validation is associated with the input, status messages are announced, and errors use `role="alert"`.
- Existing list loading, retry, and refresh behaviour continues to work.

## Contracts
### Input
One title string. The client validates with the shared `createTodoSchema` before sending; the API remains the final authority.

### Success
`POST /todos` returns 201 with a body matching `todoSchema`. The mutation invalidates `todoListQueryKey`; the existing query then loads the updated list.

### Expected failures
| Failure | Representation |
|---------|----------------|
| Invalid title | Inline validation message; no request |
| Network, HTTP, or invalid response | Typed `TodoApiError`; alert “Could not add todo. Try again.” |

### Unexpected failures
Any unrecognized error is caught at the form boundary, logged, and shown with the same safe alert. The title remains available for retry.

### Responsibilities
| Layer | Responsibility |
|-------|-----------------|
| Contract | Reuse `createTodoSchema` and `todoSchema`; no contract change |
| API adapter | `createTodo(title)` posts JSON, checks status, and validates the response |
| Hook | `useCreateTodoMutation` owns the mutation and invalidates `todoListQueryKey` on success |
| Form | Owns title input, inline validation, focus, pending, and user messages |
| Route | Renders the form above the existing list |

## Design decisions
- Validate with the shared schema so browser and API rules stay aligned; the server still validates independently.
- Disable submit while pending and rely on the mutation's pending state to block duplicate submissions.
- Keep the entered title after a failed request. Clear it only after confirmed success.
- Return focus to the input after success so another todo can be entered; keep focus within the form after validation or failure.
- Invalidate the existing list query after success instead of maintaining a second local list or optimistic update.
- Set mutation retries to zero so a failed create is never silently sent again by the query library.
- Treat adapter errors as expected operational failures. Catch unknown errors at the form boundary so the user sees a safe message.

## Tests to write first
1. Adapter sends `POST /todos` with JSON title and parses a valid 201 todo response.
2. Adapter turns network rejection, non-2xx response, and invalid 201 body into typed errors.
3. Form shows validation feedback and makes no request for blank, too-short, or too-long titles.
4. Form trims a valid title before submission.
5. While the request is pending, the button shows “Adding…” and is disabled; repeated submits call the adapter once.
6. On success, input clears, success status appears, focus returns to the input, and the list query is invalidated.
7. On expected failure, the entered title remains and the alert is shown.
8. On an unexpected thrown error, the form remains usable and shows the safe alert.
9. Home-route test exercises a successful create and confirms the refreshed list shows the new todo.
