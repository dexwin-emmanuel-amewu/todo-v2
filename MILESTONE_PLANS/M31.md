# Objective

Plan how a user changes one todo's completion state from the list.

# Included

- Add a labelled checkbox to each todo row.
- Send `PATCH /todos/:todoId` with `{ "completed": boolean }`.
- Validate the id and body with the existing schemas before sending.
- Keep the server's current state visible while the request is pending.
- Refresh the list after success.
- Show a row error and retry action if the update fails.
- Test the adapter, hook, row, route, and browser flow.

# Not included

- Editing titles, creating or deleting todos, or bulk completion.
- Optimistic updates, API changes, or database changes.
- Filters, pagination, or changes to list order.

# Current repository evidence

- `packages/contracts/src/index.ts` defines `todoIdParamSchema`, `patchTodoSchema`, and `todoSchema`.
- `apps/api/src/module/todo.routes.ts` already handles `PATCH /todos/:todoId`. It returns 200, 400, 404, or 500.
- `apps/api/src/module/todo.service.ts` validates the patch body and calls the repository.
- `apps/web/src/api/todo.api.ts` owns browser API requests and `TodoApiError`.
- `apps/web/src/hooks/useTodoListQuery.ts` exports the list query key.
- `apps/web/src/components/TodoList.tsx` renders each todo row and its completion badge.
- `apps/web/src/hooks/useCreateTodoMutation.ts` shows how mutations refresh the list.

# Acceptance criteria

☐ Each row has a checkbox that reflects the todo's current `completed` value.

☐ The checkbox name includes the todo title and the action, such as “Mark Buy oat milk as completed”.

☐ Changing a checkbox sends one PATCH request with the todo id and requested boolean.

☐ An invalid id or body is rejected before the browser sends the request.

☐ While the request is pending, checkboxes are disabled and the list stays visible and unchanged.

☐ On success, the list refreshes and shows the server-confirmed state.

☐ On failure, the previous list stays visible and the row offers a useful error and retry action.

☐ Unexpected errors are logged and shown safely without breaking the list.

☐ Screen readers can identify the checkbox action and hear pending and error messages.

# Contracts

## Input

The todo UUID in the path and `{ "completed": boolean }` in the body.

## Success

The API returns 200 with a todo that matches `todoSchema`. The list query refreshes and shows the new state.

## Expected failures

| **Failure**            | **When it happens**             | **How it is represented**                         |
| ----------------------- | ------------------------------- | ------------------------------------------------- |
| Invalid id or body      | Client validation fails         | Show validation feedback; do not send the request |
| Network or HTTP failure | Request fails or API returns an error | Keep the list; show a row error and retry action |
| Todo not found          | Another action removed the todo | Refresh the list and show an error if the row remains |
| Invalid response        | A 200 body fails `todoSchema`   | Keep the list; show a row error and retry action |

## Unexpected failures

Catch and log unknown errors. Keep the list visible and show a safe row error with a retry action.

# Certainty checks

1. **What information enters the system?** The todo UUID and the requested completion boolean.
2. **How will you check that information?** Use `todoIdParamSchema` and `patchTodoSchema` before sending; the API checks them again.
3. **What will the operation return when it succeeds?** A validated todo, followed by a refreshed list.
4. **What expected failures can happen?** Invalid input, network failure, HTTP errors including 404, and an invalid response.
5. **How will each expected failure be represented?** Client validation stops invalid requests. Other failures keep the list visible and show a row error with retry.
6. **Where will the route, business rules, and database or UI work live?** Existing API owns server rules and database work. The adapter owns HTTP; the hook owns mutation and refresh; the row owns UI feedback.
7. **What tests will you write before implementation?** Adapter tests, hook tests, row tests, route integration tests, and one browser test.
8. **How will you prove the whole operation works through its real boundaries?** A browser test will intercept requests and check the checkbox, pending state, server response, and refreshed list.
9. **Does this change multiple records or call another system? If yes, how will failure be handled safely?** It updates one record through the existing API. Failures keep the list visible and offer a retry.
10. **If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?** Existing list loading and empty states remain. Ready rows have labelled checkboxes. Pending disables the controls without changing the displayed state. Errors are announced and can be retried.

# Tests to write first

1. Adapter sends PATCH with the id and `{ completed }`, then parses a valid 200 todo.
2. Adapter rejects an invalid id or body without making a request.
3. Adapter maps network failure, non-2xx responses, and invalid response bodies to `TodoApiError`.
4. Mutation hook refreshes `todoListQueryKey` on success and does not retry automatically.
5. Row tests check the checked state and accessible action name for active and completed todos.
6. Pending row test confirms the checkbox is disabled and the visible state does not change early.
7. Success test confirms the refreshed list shows the server's state.
8. Failure test confirms the list stays visible and retry sends the same requested state.
9. Unexpected error test confirms logging and safe row feedback.
10. Route test confirms only the selected todo changes.
11. Browser test covers keyboard use, pending state, success refresh, and failure recovery.
