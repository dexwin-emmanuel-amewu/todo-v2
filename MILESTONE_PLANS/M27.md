## Objective
Plan the web application shell and read-only todo list.

## Included
- `@todo/contracts` added as a dependency of `apps/web`, so the browser parses responses with the same schemas the API produces them from.
- An API adapter, `apps/web/src/api/todo.api.ts`, owning the `fetch` call, the base URL, and response parsing.
- A typed adapter failure, `TodoApiError`, with three variants: `network`, `http`, `response_validation`.
- A query hook, `apps/web/src/hooks/useTodoListQuery.ts`, owning the query key and the TanStack Query options.
- An application-owned server state union, `TodoListViewState`, with five members: `initial_loading`, `initial_failure`, `ready`, `refreshing`, `refresh_failure`.
- A pure derivation function, `toTodoListViewState`, mapping a query snapshot to that union. No React, no QueryClient.
- A presentational view, `apps/web/src/components/TodoList.tsx`, that takes a `TodoListViewState` and renders it. No fetching.
- The route, `apps/web/src/routes/index.tsx`, wiring hook to derivation to view, and nothing else.
- The empty list as a render branch inside the three data-bearing states, with its own message and no list element.
- Initial loading, initial failure with a retry control, ready, refreshing with the previous list still visible, and refresh failure with the previous list still visible.
- Accessibility: one `<h1>`, a `<ul>`/`<li>` list, `aria-busy` while fetching, a polite `role="status"` for loading and refreshing, `role="alert"` for both failures, and a real `<button>` for retry.
- Adapter tests, derivation tests, view tests per state, a route integration test, and an updated e2e spec.
- Reference styling from TodoMVC, expressed in the Tailwind utilities `root.tsx` already uses.
- A Vite dev proxy for `/todos`, so the browser calls a same-origin relative URL and no CORS header is needed from the API.
- A `.env.example` for `apps/web` documenting `VITE_API_URL`.
- A README section for the frontend list.

## Not included
- Creating, editing, toggling, or deleting a todo. 
- The status filter, the search box, and pagination controls. 
- A single-todo detail route.
- Route-level data loading through TanStack Router loaders. The hook owns loading.
- Any change to `apps/api` or to the existing contract schemas.

## Acceptance criteria
- With the API up and 3 todos stored, visiting `http://localhost:5173/` shows a list of 3 items in `created_at` order, each with its title and a completed or active badge.
- Before the response arrives, the page shows the `<h1>` and a "Loading todos" status, and no list element.
- With the API up and an empty database, the page shows an empty-list message, no list element, and no error.
- With the API down, the page shows an error message with a retry button, and no list element.
- Pressing retry while the API is still down leaves the error in place. Pressing it after the API comes back shows the list.
- With a list already on screen, a refetch keeps the previous items visible, marks the list `aria-busy="true"`, and announces a refreshing status.
- With a list already on screen, a failed refetch keeps the previous items visible and adds an alert. The items are not replaced by the error.
- A 500 from `GET /todos` is treated as a failure, not as an empty list.
- A 200 whose body does not match `todoListResponseSchema` is treated as a failure, not rendered.
- Each item's completed state is available to a screen reader as text, not by colour or line-through alone.
- `toTodoListViewState` maps every query snapshot to exactly one state, provable without React.
- `pnpm --filter web test`, `pnpm typecheck`, `pnpm lint`, and `pnpm format:check` all pass. The existing e2e spec passes in its updated form.

## Contracts
### Input
#### What information enters the operation?
Nothing from the user.

### Success
#### What exact value or visible result means success?
The adapter resolves a `TodoListResponse`. The hook reaches `status: "success"`. The derivation returns `ready` or `refreshing`. The view renders one `<li>` per item, in server order, each with its title and a completed or active badge. When `items` is empty, the empty-list message and no `<ul>`.

### Expected failures
| Failure | When it happens | How it is represented |
|---------|------------------|------------------------|
| Network failure | `fetch` rejects: API down, DNS, CORS, offline | `TodoApiError` `{ type: "network" }`; `initial_failure` or `refresh_failure` |
| HTTP failure | response is not ok, in practice the API's 500 | `TodoApiError` `{ type: "http", status }`; `initial_failure` or `refresh_failure` |
| Unparseable body | 200 whose JSON is invalid, or fails `todoListResponseSchema` | `TodoApiError` `{ type: "response_validation", issues }`; `initial_failure` or `refresh_failure` |
| Empty list | 200 with `items: []` | `ready` with `items: []`, empty-list message |

### Unexpected failures
#### What unexpected failures can reach this boundary? How will they be made safe for the caller or user?
A render-time throw inside the view. The adapter converts every rejection into a `TodoApiError` before it leaves, and the derivation's fallback branch treats an unrecognised error as a failure.

### Responsibilities
| Layer | Responsibility |
|-------|-----------------|
| Contract | `packages/contracts` is reused unchanged. `apps/web` adds it as `workspace:*` and parses with `todoListResponseSchema`. |
| Route or page | `apps/web/src/routes/index.tsx` calls `useTodoListQuery`, passes the snapshot to `toTodoListViewState`, renders `<TodoList>`. |
| Service or flow | `apps/web/src/module/todo.state.ts` owns `TodoListViewState` and `toTodoListViewState`, the pure query-snapshot-to-state mapping. |
| Repository or API adapter | `apps/web/src/api/todo.api.ts` owns `TODO_API_BASE_URL`, `fetchTodoList`, `TodoApiError`. The only place `fetch` appears. |
| Hook | `apps/web/src/hooks/useTodoListQuery.ts` owns `todoListQueryKey` and the query options. The only place `useQuery` appears |
| View | `apps/web/src/components/TodoList.tsx` renders one `TodoListViewState`, plus `TodoListItem`. |

## Certainty checks
### What information enters the system?
The `GET /todos` response body, its status code, `fetch` rejections, and `VITE_API_URL`.

### How will you check that information?
`fetchTodoList` checks in a fixed order: a `fetch` rejection becomes `network`, a non-ok status becomes `http`, a JSON parse throw becomes `response_validation`, and `todoListResponseSchema.safeParse` decides the rest.

### What will the operation return when it succeeds?
A `TodoListResponse`: `items`, `page`, `pageSize`, `totalItems`, `totalPages`.

### What expected failures can happen?
Network, HTTP, and unparseable body.

### How will each expected failure be represented?
As a `TodoApiError` from the adapter, then `initial_failure` when no data has loaded and `refresh_failure` when it has.

### Where will the route, business rules, and database or UI work live?
`fetch` and parsing in the adapter. The query key and its options in the hook. State derivation in `todo.state.ts`. Markup in `TodoList.tsx`. Wiring in the route.

### What tests will you write before implementation?
Adapter tests against a stubbed `fetch`, derivation tests as plain function calls, view tests per state, and one route test with a `QueryClientProvider`.

### How will you prove the whole operation works through its real boundaries?
The route test drives the real hook and the real adapter with only `fetch` stubbed.

### Does this change multiple records or call another system? If yes, how will failure be handled safely?
It writes nothing.

### If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?
Loading is `initial_loading`. Empty is `ready` with `items: []`. Ready is `ready`. Error is `initial_failure` and `refresh_failure`. Pending is `refreshing`.

## Flow
1. The router renders `HomePage`. `QueryClientProvider` is already above it from `main.tsx`.
2. `useTodoListQuery()` runs. With no cached entry under `todoListQueryKey`, TanStack Query starts a fetch and reports `status: "pending"`.
3. The route builds a snapshot, `{ status, isFetching, data, error }`, and calls `toTodoListViewState`.
4. First pass, the snapshot is pending, so the state is `initial_loading`. The view renders the heading and a polite status message. No `<ul>`.
5. `fetchTodoList` resolves the URL from `TODO_API_BASE_URL`, calls `GET /todos`, and runs its four checks.
6. On success the query becomes `status: "success"` with `data`. The derivation returns `ready`, or `refreshing` while `isFetching` is still true. The view renders the list, or the empty-list message when `items` is empty.
7. On failure the adapter throws a `TodoApiError`. The query becomes `status: "error"`. With no `data` the derivation returns `initial_failure` and the view renders an alert and a retry button. Retry calls the `refetch` the state carries, and the query re-enters pending.
8. On a later refetch, a window refocus or a retry over existing data, `isFetching` is true with `data` present, so the state is `refreshing`. The list stays on screen with `aria-busy="true"`.
9. If that refetch fails, `data` is still present and `error` is set, so the state is `refresh_failure`. The previous list stays and an alert is added. The stale data is never swapped for an error screen.

## Application-owned server states
`TodoListViewState` is a discriminated union on `state`, exported from `apps/web/src/module/todo.state.ts`:

| State | Derived when | Carries | Rendered as |
|-------|--------------|---------|-------------|
| `initial_loading` | `status === "pending"` | nothing | Polite "Loading todos" status, no list |
| `initial_failure` | `status === "error"` and `data` is undefined | `error`, `retry` | `role="alert"` message plus a retry button, no list |
| `ready` | `status === "success"` and not fetching | `items` | The list, or the empty-list message when `items` is empty |
| `refreshing` | `status === "success"` and fetching | `items` | The same list, `aria-busy="true"`, polite "Refreshing" status |
| `refresh_failure` | `status === "error"` and `data` is defined | `items`, `error`, `retry` | The previous list plus a `role="alert"` message and a retry button |

## Design decisions
- **`@todo/contracts` in the browser**: the API already returns exactly `todoListResponseSchema`. A second declaration in `apps/web` would drift.
- **The client re-parses a body the server already validated**: the response crosses a network, where a proxy or a stale deploy can change it.
- **A typed `TodoApiError` with three variants**: matches the shape of `apps/api/src/db/errors.ts`. The view renders one message for all three this milestone. Flagging for review.
- **The adapter throws**: TanStack Query decides success against a rejected promise, so a `neverthrow` `Result` would be unwrapped and re-thrown inside the query function. `neverthrow` and `ts-pattern` stay out of `apps/web`. Flagging for review.
- **Status is checked before the body is read**: the API's 500 body would fail `todoListResponseSchema` and be reported as `response_validation`, hiding the real cause.
- **`toTodoListViewState`, not a `...Service`**: `...Service` is reserved for the service layer, which parses input and calls a repository. This function does neither.
- **The states are application-owned, derived once**: reading `isLoading`, `isError`, `isFetching`, and `data?.items.length` in the view produces branches that contradict each other. One union makes the five states mutually exclusive and testable without a renderer.
- **`refresh_failure` keeps the stale list**: a failed background refetch should not take away a working list.
- **Empty is a branch inside `ready`**: as its own state it would need an `empty_refreshing` and an `empty_refresh_failure` twin to stay exhaustive. The view branches on `items.length === 0` in one place.
- **No checkbox per row**: a disabled checkbox in a read-only list reads as broken. Completion shows as a text badge until the toggle milestone. Flagging for review.
- **The badge is text**: line-through and colour do not reach a screen reader. The item's accessible name states its state.
- **Retry is a `<button>` the state carries**: a failure state cannot be constructed without a way out of it.
- **`retry: 1` and `staleTime: 30_000` on the hook**: `main.tsx` uses a bare `new QueryClient()`, so the default is three retries with backoff, which makes the initial-failure state take seconds to appear. Setting them on the hook leaves global behaviour alone. Flagging for review.
- **The query key is exported from the hook**: the mutation milestones invalidate `todoListQueryKey` by name. The pagination milestone extends it to `["todos", "list", params]`.
- **A Vite dev proxy, with `VITE_API_URL` defaulting to empty**: the API sends no CORS headers, so an absolute `http://localhost:3000` fails the preflight. The proxy keeps this milestone frontend-only. `TODO_API_BASE_URL` is `import.meta.env.VITE_API_URL ?? ""`, the adapter requests the relative `/todos`, and `vite.config.ts` proxies `/todos` to the API. A deployment sets `VITE_API_URL` to the API origin. Flagging for review, since `@fastify/cors` is the other option.
- **No router loader**: a TanStack Router loader plus TanStack Query means two caches for one list. The hook owns loading.
- **`fetch` is stubbed in tests**: one `GET` does not justify adding MSW and a server lifecycle to the setup file.
- **The e2e spec asserts only the shell**: Playwright starts `web` alone and CI has no Postgres, so an e2e test expecting items would fail on the environment. The spec asserts the heading, then that the page settles into the list or the error state.


## Accessibility
- One `<h1>` per page, "Todo", kept from the placeholder. The e2e spec and the existing view test already assert it.
- The route renders a `<main>` landmark. It already does.
- The list is a `<ul>` of `<li>`. Each `<li>` is a single accessible string: title, then state, for example "Buy oat milk, completed". Not a `<div>` soup, and not a `role="list"` retrofit.
- Completion reaches assistive technology as the badge text. `line-through` and colour are decoration on top of it, never the only carrier.
- `initial_loading` and `refreshing` render a `role="status"` with `aria-live="polite"`, so a refresh does not interrupt what the user is reading.
- `initial_failure` and `refresh_failure` render `role="alert"`, which is assertive, because a failure is worth interrupting for.
- While fetching, the list container carries `aria-busy="true"`, so the stale list is announced as stale rather than as current.
- Retry is a real `<button type="button">` with the visible text "Retry": keyboard reachable, activated by both Enter and Space, with a visible `focus-visible` ring.
- The empty-list message is ordinary text in the card, not a `role="status"`. It is the steady state, not an event.
- No `aria-label` where visible text will do, and no `tabIndex` on anything non-interactive.
- Nothing in the read-only list is clickable, so there is no focus order to manage beyond the retry button.
