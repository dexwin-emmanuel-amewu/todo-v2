#### Objective: Add title search without adding pagination

## Included
- search query param on GET /todos: case-insensitive substring match against title.
- Trimming leading/trailing whitespace from the search term.
- A length limit on the search term, rejected with 400 when exceeded.
- Blank input handling. An empty or whitespace-only term counts as no search filter.
- Handling a duplicate search query param. For example, ?search=a&search=b.
- Combining search with the existing status filter. Both conditions apply together.
- Safe, parameterized database querying with LIKE-wildcard escaping.
- Regression tests.

## Not included
- Pagination, limit, or offset.
- Searching any field other than title.
- Frontend integration or UI.

## Current repository evidence
What files, commands, or existing patterns did you inspect before making this plan?
- apps/api/src/module/todo.routes.ts: GET /todos parses request.query.status through parseStatusFilter. That function defaults to "all" and rejects unknown or array values with 400. It passes the parsed filter to listTodos. request.query.search is currently ignored.
- apps/api/src/module/todo.repository.ts: listTodos(db, filter = "all") builds one optional where(eq(todos.completed)) condition with ts-pattern's match. It then runs db.select().from(todos).where(condition).orderBy(asc(todos.createdAt), asc(todos.id)).
- apps/api/src/db/schema.ts: todos.title is a non-null text column. It has no database-level length constraint. The max(100) limit lives only in the Zod contract.
- packages/contracts/src/index.ts: todoSchema.title is z.string().trim().min(6).max(100). todoStatusFilterSchema is the only query-param schema defined. No search schema exists yet.
- apps/api/src/module/todo.routes.test.ts and todo.repository.test.ts: existing tests cover listTodos(db) and listTodos(db, "active"/"completed"), plus GET /todos and GET /todos?status= with no search term involved.

## Acceptance criteria
- GET /todos with no search param returns exactly what it returns today: all todos, or status-filtered todos. Status 200.
- GET /todos?search=<term> returns only todos whose title contains term as a case-insensitive substring. Status 200.
- GET /todos?search= and GET /todos?search=%20%20 both count as blank. They return the same result as an omitted search param. Status 200.
- GET /todos?search=<term with leading/trailing spaces> matches as if the term were trimmed.
- GET /todos?status=active&search=<term> returns only active todos whose title matches term. This is AND, not OR.
- GET /todos?search=<term over the length limit> returns 400 with a validationErrorResponseSchema body. No query reaches the database.
- GET /todos?search=a&search=b sends a duplicate param. It returns 400 and is treated as invalid, not silently resolved to one of the two values.
- A search term containing a literal `%` or `_` is matched literally. It is not treated as a SQL wildcard.
- All existing unfiltered and status-filtered tests still pass.

## Contracts
### Input
#### What information enters the operation?
An optional search query string on GET /todos, combined with the existing optional status param. Any string up to the length limit is accepted. The limit is set out in Risks and assumptions below. The value is trimmed. A blank result after trimming is treated as absent. Anything else, including duplicates, is invalid.

### Success
#### What exact value or visible result means success?
HTTP 200. The body matches todoListResponseSchema. Items are filtered by status when status is given, and by a case-insensitive title substring match when search is given.

### Expected failures
| Failure | When it happens | How it is represented |
|---------|------------------|------------------------|
| Search term too long | trimmed search exceeds the length limit | HTTP 400, validationErrorResponseSchema body |
| Duplicate search param | the param is repeated, so Fastify parses search as an array | HTTP 400, validationErrorResponseSchema body |
| Unknown status value, already existing behavior | status is any string outside all/active/completed | HTTP 400, validationErrorResponseSchema body |
| Repository database error | listTodos resolves Err({ type: "database", cause }) | HTTP 500, internalErrorResponseSchema body |
| Repository validation error | a stored row fails todoSchema | HTTP 500, internalErrorResponseSchema body |

## Certainty checks
### What information enters the system?
An optional status query string and an optional search query string, independent of each other.

### How will you check that information?
A pure function, parseSearchQuery(rawQuery), does the work. It rejects non-string values. Arrays come from duplicate params. It rejects strings whose trimmed length exceeds the limit. It treats blank or whitespace-only strings as no search. Otherwise it returns the trimmed term. It runs alongside the existing parseStatusFilter.

### What will the operation return when it succeeds?
HTTP 200 with items filtered per the Success section above.

### What expected failures can happen?
Invalid or duplicate search returns 400. Invalid or duplicate status, already existing behavior, also returns 400. A repository DatabaseError or ValidationError returns 500. See the Expected failures table.

### How will each expected failure be represented?
parseSearchQuery and parseStatusFilter both run before any database call. If either returns an error, the route short-circuits to a 400 with a validationErrorResponseSchema body. Database and row-validation errors still go through the existing internalErrorResponseSchema path.

### Where will the route, business rules, and database work live?
Query validation lives in apps/api/src/module/todo.routes.ts, in a new parseSearchQuery function, plus a new schema in packages/contracts/src/index.ts. Filtering and search live in apps/api/src/module/todo.repository.ts's listTodos.

### What tests will you write before implementation?
Listed under "Tests to write first" below.

### How will you prove the whole operation works through its real boundaries?
Route-level tests via app.inject, using real query strings against a disposable Postgres database. They cover search alone, search combined with status, blank search, over-length search, and duplicate search.

### Does this change multiple records or call another system?
No.

## Tests to write first

2. Mapping unit test: parseSearchQuery(undefined) returns ok(undefined). That means no filter.
3. Mapping unit test: parseSearchQuery("") and parseSearchQuery("   ") both return ok(undefined). Blank counts as no filter.
4. Mapping unit test: parseSearchQuery("  milestone  ") returns ok("milestone"). The result is trimmed.
5. Mapping unit test: parseSearchQuery given a string over the length limit returns an err with a validation issue.
6. Mapping unit test: parseSearchQuery(["a", "b"]) returns an err. This is the shape Fastify produces for a duplicate param.
7. Repository test: listTodos(db, "all", "mile") matches a todo titled "Write the milestone plan". The match is a case-insensitive substring, not just a prefix.
8. Repository test: listTodos(db, "all", "MILE") matches the same todo. This confirms case-insensitivity.
9. Repository test: listTodos(db, "all", "zzz-no-match") returns an empty array.
10. Repository test: listTodos(db, "all", undefined) behaves exactly like listTodos(db, "all"). This is the regression check.
11. Repository test: a search term containing a literal `%` or `_` matches only titles containing those literal characters. It does not act as a wildcard.
12. Repository test: listTodos(db, "active", "mile") combines status and search with AND. Only active todos matching the term are returned.
13. Route integration test: GET /todos?search=milestone returns only matching todos, with status 200.
14. Route integration test: a blank GET /todos?search= returns the full unfiltered list, the same as an omitted search param, with status 200.
15. Route integration test: a search term over the length limit returns 400 with a validationErrorResponseSchema body.
16. Route integration test: GET /todos?search=a&search=b returns 400.
17. Route integration test: GET /todos?status=active&search=milestone returns only active, matching todos, with status 200.
18. Regression: existing GET /todos and GET /todos?status= route tests, run with no search param, still pass unchanged.

## Risks and assumptions
- Assumes the query param is named `search`, spelled out to match `status`, rather than a shorter `q`. Flagging this for review rather than deciding it unilaterally.
- Assumes a blank or whitespace-only search should behave like an absent param: 200, unfiltered by search. Not a 400. That's the natural result of a user clearing a search box.
- Assumes a hard length limit of 100 characters, matching title's own max length in todoSchema. Exceeding it is a 400. It does not silently truncate or fall back to an empty result.
- Assumes ASCII-range case-insensitive substring matching, via Postgres ILIKE, is sufficient. No unicode-aware locale folding is planned.
- Assumes search and status combine with AND. Never OR.
- Assumes no pagination is needed, even though a common search term could still return the entire table. The milestone objective explicitly excludes pagination.
