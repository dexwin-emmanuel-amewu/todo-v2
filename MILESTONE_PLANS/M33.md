# Objective

Plan how a user edits a todo title from its row and saves it through `PUT`.

# Included

- Add an Edit action to each todo row.
- Open one row in edit mode with its current title as the input value.
- Validate the title with the shared replacement schema.
- Send `PUT /todos/:todoId` with the edited title and the todo's current `completed` value.
- Support Save, Cancel, Enter to save, and Escape to cancel.
- Show pending and failure states without losing the draft.
- Refresh the list after a successful save.
- Set and restore focus at each step.
- Test the adapter, hook, row, route, and browser flow.

# Not included

- Editing completion state, or adding and deleting todos.
- Optimistic updates, API changes, or database changes.
- A separate edit page, modal, or reusable form framework.

# Current repository evidence

- `packages/contracts/src/index.ts` defines `replaceTodoSchema`, which requires a title and boolean `completed`; the title is trimmed and must be 6–100 characters.
- `apps/api/src/module/todo.routes.ts` already handles `PUT /todos/:todoId`. It returns the updated todo, 400 for invalid input, 404 if the id is missing, and 500 for server errors.
- `apps/api/src/module/todo.service.ts` validates the full replacement body and calls the repository.
- `apps/web/src/api/todo.api.ts` owns browser requests, response validation, and `TodoApiError`.
- `apps/web/src/hooks/usePatchTodoCompletionMutation.ts` shows how a write mutation refreshes the list.
- `apps/web/src/components/TodoList.tsx` renders todo rows and already handles completion mutation, pending, and row errors.
- `apps/web/src/routes/index.test.tsx` exercises list mutations through the home page.

# Acceptance criteria

☐ Edit opens an inline form with the current title already entered.

☐ Edit mode focuses the title input and selects its text.

☐ The PUT body includes the trimmed title and the todo's current `completed` value.

☐ Invalid titles show feedback and do not send a request.

☐ Enter saves and Escape cancels. Cancel sends no request and restores the displayed title.

☐ While saving, form controls are disabled and a pending message is announced.

☐ On success, the row shows the server's saved title, the list refreshes, and focus returns to that row's Edit action.

☐ On failure, edit mode and the draft remain. A useful error and retry action are available.

☐ Screen readers can identify the title input, its validation message, pending state, and any error.

# Contracts

## Input

The todo UUID and `{ "title": string, "completed": boolean }`. The browser checks them with `todoIdParamSchema` and `replaceTodoSchema`; the API checks them again.

## Success

`PUT /todos/:todoId` returns 200 with a todo matching `todoSchema`. The list query refreshes and displays the saved todo.

## Expected failures

| **Failure**            | **When it happens**          | **How it is represented**                         |
| ----------------------- | ---------------------------- | ------------------------------------------------- |
| Invalid title or id     | Client validation fails      | Show feedback; do not send the request           |
| Network or HTTP failure | Request fails or API rejects | Keep edit mode and draft; show error and retry    |
| Todo not found          | Another action removed it    | Refresh the list and show an error if row remains |
| Invalid response        | A 200 body fails `todoSchema`| Keep draft; show error and retry                 |

## Unexpected failures

Catch and log unknown errors. Keep the row and draft available, and show a safe error with a retry action.

# Responsibilities

# Certainty checks

1. **What information enters the system?** The todo UUID, edited title, and existing completion value.
2. **How will you check that information?** Use `todoIdParamSchema` and `replaceTodoSchema`; the API validates them again.
3. **What will the operation return when it succeeds?** A validated todo, followed by a refreshed list.
4. **What expected failures can happen?** Invalid title or id, network failure, HTTP errors including 404, and an invalid response.
5. **How will each expected failure be represented?** Invalid input stays in the form without a request. Other failures keep the draft and show an alert with retry.
6. **Where will the route, business rules, and database or UI work live?** The existing API owns server rules and database work. The adapter owns HTTP; the hook owns mutation and refresh; the row owns editing and feedback.
7. **What tests will you write before implementation?** Adapter tests, hook tests, row tests, route tests, and one browser test.
8. **How will you prove the whole operation works through its real boundaries?** A browser test will enter edit mode, use keyboard actions, inspect the PUT request, and verify the saved row.
9. **Does this change multiple records or call another system? If yes, how will failure be handled safely?** It updates one record through the existing API. Failures keep the unsaved draft so the user can retry or cancel.
10. **If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?** Existing list loading and empty states remain. Rows have read and edit modes. Pending disables the form and announces “Saving”. Errors preserve the draft and are announced. Input and buttons have clear labels and keyboard actions.

# Tests to write first

1. Adapter sends PUT with the todo id, trimmed title, and `completed` value; it parses a valid todo response.
2. Adapter rejects an invalid id, short title, long title, or invalid completion value without making a request.
3. Adapter maps network failure, non-2xx responses, and invalid response bodies to `TodoApiError`.
4. Mutation hook refreshes `todoListQueryKey` after success and does not retry automatically.
5. Row enters edit mode with the existing title, focuses and selects the input, and preserves `completed` in the request.
6. Invalid title shows feedback and does not call the adapter.
7. Enter submits once; Escape cancels, restores the title, and sends no request.
8. Pending state disables controls and announces “Saving”.
9. Success displays the returned title, refreshes the list, and restores focus to the Edit action.
10. Failure retains the draft and edit mode; retry sends the same title and completion value.
11. Unexpected failure is logged and shown safely without losing the draft.
12. Route test confirms the edited row changes and other todos remain unchanged.
13. Browser test covers edit, validation, keyboard actions, save, and failure recovery.
