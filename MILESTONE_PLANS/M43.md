# Objective

Plan how the standard TodoMVC control changes the complete collection.

# Included

- Add a toggle-all checkbox above the list, in the TodoMVC position before the rows.
- Choose the desired boolean from the whole collection, not from the visible page. If any todo in the collection is active, the control marks all as completed. If every todo is completed, it marks all as active.
- Read the whole-collection counts with a new summary query. It reads the total count and the active count from `GET /todos`.
- Send `PATCH /todos` with `{ completed }` through the browser API adapter.
- Use wording that names the whole collection: "Mark all 12 todos as completed" or "Mark all 12 todos as active".
- Show a short note when a status or a search is active: "Applies to all todos, not only this view."
- Show a pending state. The control stays focusable, is `aria-disabled`, and ignores clicks. Row actions are locked. A polite status reads "Marking all todos as completed".
- On success, refresh the current list page, the count, and the summary. Announce the result from `updatedCount`.
- On failure, show an alert next to the control with a retry button. Retry sends the same boolean.
- Hide the control when the collection is empty, while the summary loads, and when the summary fails.
- Lock the control while a row toggle, edit save, or delete is pending.
- Test the toggle rules, adapter, hooks, component, route, and browser flow.

# Not included

- Backend, API contract, or database changes. `PATCH /todos` and `setAllTodosCompletedSchema` already exist.
- Toggling only the todos in the current status, search, or page.
- Optimistic updates of the visible rows.
- Clear completed.
- A confirmation dialog before the change.
- Undo.

# Current repository evidence

- `apps/api/src/module/todo.repository.ts` `setAllTodosCompleted` runs one `UPDATE ... WHERE completed <> $1`. It touches every todo and ignores any filter. `updatedCount` counts only the rows that changed.
- `apps/api/src/module/todo.repository.ts` `listTodos` returns `totalItems` for the filter and search. `GET /todos?pageSize=1` gives the total count. `GET /todos?status=active&pageSize=1` gives the active count.
- `apps/web/src/api/todo.api.ts` has `fetchTodoList`, `patchTodoCompletion`, and `TodoApiError`. It has no bulk call.
- `apps/web/src/hooks/useTodoListQuery.ts` exports `todoListQueryKey = ["todos", "list"]`. Every mutation hook invalidates this prefix.
- `apps/web/src/hooks/usePatchTodoCompletionMutation.ts` returns the invalidation promise from `onSuccess`, so `isPending` stays true until the list refetches.
- `apps/web/src/routes/index.tsx` `HomePage` loads one page with the status, search, page, and page size. It builds `completion`, `replacement`, and `deletion` controls for `TodoList`.
- `apps/web/src/components/TodoList.tsx` locks row controls with `locked` and dims the list with `busy`. The count comes from the list `totalItems`, so it covers only the current view.
- `apps/web/src/module/todo.pagination.ts` `getPageRedirect` already moves to the last valid page when a page empties.
- `e2e/tests/paginate-todos.spec.ts` and `e2e/tests/search-todos.spec.ts` mock `/todos` with a URL predicate and record each request.

# Acceptance criteria

[ ] Opening `/` sends `GET /todos?pageSize=1` and `GET /todos?status=active&pageSize=1` for the summary, beside the list request.

[ ] With 12 todos and 3 active, the checkbox is unchecked and labelled "Mark all 12 todos as completed".

[ ] With 12 todos and 0 active, the checkbox is checked and labelled "Mark all 12 todos as active".

[ ] With 0 todos, the control is not rendered.

[ ] The choice uses the whole collection. On `/?status=completed`, with only completed rows visible and 3 active todos elsewhere, the checkbox is unchecked and marks all as completed.

[ ] The choice uses the whole collection across pages. On page 2, where every visible row is completed, the checkbox follows the summary and not the page.

[ ] With a status or a search in the URL, the note "Applies to all todos, not only this view." shows under the control. With neither, it is hidden.

[ ] Clicking the unchecked control sends `PATCH /todos` with the body `{"completed":true}`. Clicking the checked control sends `{"completed":false}`.

[ ] While the request is pending, the checkbox is `aria-disabled`, keeps focus, and ignores clicks. Only one request is sent for a double click.

[ ] While the request is pending, a polite status reads "Marking all todos as completed" or "Marking all todos as active". Row checkboxes, Edit, and Delete are disabled.

[ ] The checkbox does not change its checked value until the server answers and the summary refetches.

[ ] On success, the current list page, the count above the list, and the summary refetch. Pending ends only after they refetch.

[ ] On success, a polite status reads "Marked 3 todos as completed." from `updatedCount`. When `updatedCount` is 0, it reads "All todos were already completed." or "All todos were already active."

[ ] On success, focus stays on the checkbox.

[ ] On `/?status=active`, marking all as completed refreshes to the existing "No active todos." message. On a later page, the existing page redirect moves to page 1.

[ ] A 400, a 500, a network failure, and a bad response each show an alert next to the control with a safe message and a "Retry" button. The raw error is never shown.

[ ] Retry sends the same boolean as the failed request, even if the summary changed.

[ ] After any failure, the list and the summary refetch, so the view shows the server state.

[ ] The alert clears when a later toggle-all succeeds.

[ ] While a row toggle, edit save, or delete is pending, the control is `aria-disabled` and ignores clicks.

[ ] While the summary loads or after it fails, the control is hidden. The list still works.

[ ] Keyboard: Tab reaches the checkbox. Space toggles it. The focus ring is visible.

# Contracts

## Input

The click on the toggle-all checkbox. The desired boolean is `activeCount > 0`, read from the summary when the user clicks. The request is `PATCH /todos` with the body `{"completed": <boolean>}` and the `Content-Type: application/json` header. There is no query string.

The summary reads `GET /todos?pageSize=1` and `GET /todos?status=active&pageSize=1`. It uses only `totalItems` from each response.

## Success

The API returns 200 with a body that matches `setAllTodosCompletedResponseSchema`. The adapter returns `{ updatedCount }`. The hook invalidates `todoListQueryKey`, which refetches the current list page and the summary.

## Expected failures

| **Failure** | **When it happens** | **How it is represented** |
| --- | --- | --- |
| Bad adapter input | Code calls `setAllTodosCompleted` with a value that is not a boolean. | Reject with `TodoApiError` of type `request_validation`. Do not call `fetch`. |
| API rejects the body | The API returns 400. | `TodoApiError` of type `http` with status 400. Alert: "The todos could not be updated. Refresh and try again." |
| Server failure | The API returns 500 or another non-2xx status. | `TodoApiError` of type `http` with that status. Alert: "The server could not update your todos. Try again." |
| Network failure | The browser cannot reach the API. | `TodoApiError` of type `network`. Alert: "Could not reach the server. Your todos were not changed." |
| Bad response | The body is not JSON or does not match the contract. | `TodoApiError` of type `response_validation`. Alert: "The server returned an unexpected response. Refresh to see your todos." |
| Summary failure | Either summary request fails. | The summary query is in error. The control is hidden. The list is not affected. |

## Unexpected failures

Any other thrown error goes through TanStack Query as the mutation error. The hook logs it with `console.error`. The view shows "Something went wrong. Try again." with the retry button. The raw error is never shown.

# Design decisions

- **Desired boolean:** The visible rows are one page of one view, so they cannot tell if the whole collection is done. The summary query gives `totalCount` and `activeCount` for the whole collection. `getToggleAllState` returns `hidden` when `totalCount` is 0. Otherwise it returns `checked: activeCount === 0` and `desired: activeCount > 0`. This matches TodoMVC, where the control is checked only when every todo is completed.
- **Fixed at click time:** The desired boolean goes into the mutation variables when the user clicks. Retry sends `mutation.variables`. A summary refetch never changes a retry.
- **Summary source:** `fetchTodoSummary` calls `fetchTodoList({ pageSize: 1 })` and `fetchTodoList({ status: "active", pageSize: 1 })` in parallel and returns `{ totalCount, activeCount }`. This needs no API change. Both reads are small. A todo created between the two reads can skew one count for one refresh. The next invalidation corrects it.
- **Summary key:** The key is `["todos", "list", "summary"]`. It shares the `todoListQueryKey` prefix, so every existing mutation refreshes it with no change to those hooks. It never matches a list key, because list keys end with an object.
- **Wording:** The visible label is "Mark all as complete", as in TodoMVC. The accessible name says the scope and the action: "Mark all 12 todos as completed" or "Mark all 12 todos as active". The number is `totalCount`. One todo reads "Mark the 1 todo as completed". The note "Applies to all todos, not only this view." shows when a status or a search is set.
- **Control:** A native checkbox with a `label`. It is not `disabled` while pending, because a disabled control drops focus. It uses `aria-disabled` and returns early from `onChange`. The checked value comes from the summary only, so it never flips before the server answers.
- **No optimistic update:** The client holds one page, so it cannot update the rest of the collection. It waits for the server and refetches.
- **Pending:** `useSetAllTodosCompletedMutation` returns the invalidation promise from `onSuccess`, as the existing hooks do. `isPending` covers the request and the refetch. During pending, `TodoList` gets `bulkPending`, which sets `locked` and `busy` on every row.
- **Mutual lock:** The control is `aria-disabled` while a row toggle, edit save, or delete is pending. Row controls are disabled while toggle-all is pending. Two writes never race from this page.
- **Success:** The polite status reads from `updatedCount` and the desired boolean. "Marked 3 todos as completed." or "Marked 1 todo as active.". When `updatedCount` is 0, it reads "All todos were already completed." The status clears on the next click.
- **Failure:** `onError` also invalidates `todoListQueryKey`. The update is one SQL statement, so it either ran or did not. A network or response failure cannot tell which, so a refetch shows the truth. The alert sits under the control with `role="alert"` and a "Retry" button. Focus stays on the checkbox after a failure.
- **List and count refresh:** The count above the list comes from the list `totalItems`, which refetches by the prefix. A view that empties uses the existing empty message. A page that empties uses the existing `getPageRedirect`.
- **Visibility:** The control renders only when the summary is in success and `totalCount > 0`. While the summary refetches, the control keeps the last value.

# Certainty checks

### 1. What information enters the system?

The click on the toggle-all checkbox. The desired boolean comes from the summary counts at click time.

### 2. How will you check that information?

The adapter checks the body with `setAllTodosCompletedSchema` before it calls `fetch`. The API checks it again.

### 3. What will the operation return when it succeeds?

`{ updatedCount }`, the number of todos whose state changed. The list page and the summary then refetch.

### 4. What expected failures can happen?

A bad adapter input, a 400, a 500 or other non-2xx status, a network failure, a bad response body, and a summary failure.

### 5. How will each expected failure be represented?

Each request failure is a `TodoApiError` with its type and status. The view maps it to one safe message with a retry. A summary failure hides the control.

### 6. Where will the route, business rules, and database or UI work live?

`todo.toggleAll.ts` holds the rules and text. The adapter makes the requests. The hooks own the keys and the refresh. `TodoToggleAll` draws the control. `HomePage` wires them. The API and database do not change.

### 7. What tests will you write before implementation?

Tests for the toggle rules, adapter, hooks, component, list lock, and route, then a Playwright test. They are listed below.

### 8. How will you prove the whole operation works through its real boundaries?

A Playwright test seeds active and completed todos across two pages, opens a filtered view, uses the control, and checks the request body, the rows, the count, the label, and the focus. It also checks a 500 and its retry.

### 9. Does this change multiple records or call another system? If yes, how will failure be handled safely?

Yes. It changes every todo. The API runs one `UPDATE`, so the change is all or nothing. The client never guesses the result. It refetches the list and the summary after success and after failure. Retry sends the same boolean, and the update is idempotent, so a repeat is safe.

### 10. If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?

Loading: the control is hidden while the summary loads. Empty: the control is hidden when there are no todos. Ready: a checked or unchecked checkbox with the full-collection label. Error: an alert under the control with a retry. Summary error: the control is hidden. Pending: `aria-disabled` control with focus kept, a polite status, and locked rows. Accessibility: a native labelled checkbox, an accessible name with the count and the action, a polite result status, a `role="alert"` failure, and no focus jump.

# Risks and assumptions

- The summary uses two list reads. A write between them can skew one count until the next refresh. The fix would be a counts field from the API, which is out of scope.
- Existing route and browser tests mock `/todos` by URL. The two summary requests will hit those mocks. Some tests may need a matcher that ignores `pageSize=1` requests.
- A row that is being edited stays open during toggle-all. Its save sends the `completed` value it had when editing began, which can undo the bulk change for that row. The row lock blocks the save while toggle-all is pending, but not after.
- `updatedCount` counts only rows that changed. The result message uses it as is, so "Marked 3 todos as completed." can differ from the total.
- The control changes todos the user cannot see. The full-collection label and the view note make this clear. No confirmation dialog is added, to match TodoMVC.
- Another client can change todos at any time. The control shows the last summary, and the API applies the boolean to whatever is there.
