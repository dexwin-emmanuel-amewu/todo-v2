# Objective

Plan how the user deletes all completed todos.

# Included

- Add a "Clear completed" button below the list, in the TodoMVC footer position before the pagination.
- Read the whole-collection completed count from the existing summary query. The completed count is `totalCount - activeCount`.
- Send `DELETE /todos?status=completed` through the browser API adapter.
- Use wording that names the whole collection: "Clear all 4 completed todos" or "Clear the 1 completed todo".
- Show a short note when a status or a search is active: "Applies to all todos, not only this view."
- Show a pending state. The button stays focusable, is `aria-disabled`, and ignores clicks. Row actions and toggle-all are locked. A polite status reads "Clearing completed todos".
- On success, refresh the current list page, the count, and the summary. Announce the result from `deletedCount`.
- On success, move focus to the toggle-all checkbox. If no todos remain, move focus to the empty-list heading.
- On failure, show an alert next to the button with a retry button. Focus stays on the button.
- Hide the button when there are no completed todos, while the summary loads, and when the summary fails.
- Lock the button while a row toggle, edit save, delete, or toggle-all is pending.
- Test the clear rules, adapter, hook, component, route, and browser flow.

# Not included

- Backend, API contract, or database changes. `DELETE /todos?status=completed` and `clearCompletedTodosResponseSchema` already exist.
- Clearing only the completed todos in the current search or page.
- Optimistic removal of the visible rows.
- A confirmation dialog before the deletion.
- Undo.
- Changes to the toggle-all rules.

- `apps/api/src/module/todo.repository.ts` `deleteCompletedTodos` runs one `DELETE ... WHERE completed = true`. It touches every completed todo and ignores any view. `deletedCount` counts the deleted rows.
- `apps/web/src/api/todo.api.ts` has `fetchTodoList`, `fetchTodoSummary`, `setAllTodosCompleted`, `deleteTodo`, and `TodoApiError`. It has no clear-completed call.
- `apps/web/src/hooks/useTodoSummaryQuery.ts` returns `{ totalCount, activeCount }` under `["todos", "list", "summary"]`. Every mutation that invalidates `todoListQueryKey` refreshes it.
- `apps/web/src/hooks/useSetAllTodosCompletedMutation.ts` returns the invalidation promise from `onSuccess` and also invalidates on error. This is the pattern for the new hook.
- `apps/web/src/routes/index.tsx` `HomePage` reads the list, the summary, and four mutations. It passes `bulkPending` to `TodoList` and `locked` to `TodoToggleAll`.
- `apps/web/src/components/TodoToggleAll.tsx` renders the checkbox with no ref from outside.
- `apps/web/src/components/TodoList.tsx` keeps `emptyHeadingRef` inside the component. The empty heading has `tabIndex={-1}`. Delete focus moves only when `document.activeElement` is the body.
- `apps/web/src/module/todo.pagination.ts` `getPageRedirect` already moves to the last valid page when a page empties.
- `e2e/tests/toggle-all-todos.spec.ts` mocks `/todos` with an in-memory list, reads `status`, `page`, and `pageSize`, and records each request.

# Acceptance criteria

[ ] With 12 todos and 4 completed, a button reads "Clear all 4 completed todos".

[ ] With 1 completed todo, the button reads "Clear the 1 completed todo".

[ ] With 0 completed todos, the button is not rendered.

[ ] The count uses the whole collection. On `/?status=active`, with no completed rows visible and 4 completed todos elsewhere, the button reads "Clear all 4 completed todos".

[ ] The count uses the whole collection across pages. On page 2, where no visible row is completed, the button follows the summary and not the page.

[ ] With a status or a search in the URL, the note "Applies to all todos, not only this view." shows under the button. With neither, it is hidden.

[ ] Clicking the button sends `DELETE /todos?status=completed` with no body. No other query parameter is sent.

[ ] While the request is pending, the button is `aria-disabled`, keeps focus, and ignores clicks. Only one request is sent for a double click.

[ ] While the request is pending, a polite status reads "Clearing completed todos". Row checkboxes, Edit, Delete, and toggle-all are locked.

[ ] The rows stay on screen until the server answers and the list refetches.

[ ] On success, the current list page, the count above the list, and the summary refetch. Pending ends only after they refetch.

[ ] On success, a polite status reads "Cleared 4 completed todos." from `deletedCount`. When `deletedCount` is 1, it reads "Cleared 1 completed todo.". When it is 0, it reads "There were no completed todos to clear.".

[ ] On success with todos left, the button is hidden and focus moves to the toggle-all checkbox.

[ ] On success with no todos left, focus moves to the empty-list heading "No todos yet.".

[ ] If the user moves focus away while the request is pending, focus is not moved after success.

[ ] If another client adds a completed todo, so the button is still shown after success, focus stays on the button.

[ ] On `/?status=completed`, clearing refreshes to the existing "No completed todos." message. On a later page that empties, the existing page redirect moves to the last valid page, and focus moves after the new page loads.

[ ] A 400, a 500, a network failure, and a bad response each show an alert next to the button with a safe message and a "Retry" button. The raw error is never shown.

[ ] After any failure, focus stays on the button. The list and the summary refetch, so the view shows the server state.

[ ] If the refetch after a failure shows no completed todos, the button and the alert are hidden, and focus follows the success rule.

[ ] Retry sends the same `DELETE /todos?status=completed` request.

[ ] The alert clears when a later clear succeeds.

[ ] While a row toggle, edit save, delete, or toggle-all is pending, the button is `aria-disabled` and ignores clicks.

[ ] While the summary loads or after it fails, the button is hidden. The list still works.

[ ] Keyboard: Tab reaches the button. Enter and Space activate it. The focus ring is visible.

# Contracts

## Input

The click on the clear-completed button. The request is `DELETE /todos?status=completed` with the `Accept: application/json` header and no body. The adapter takes no argument, so the query is fixed.

The completed count is `totalCount - activeCount` from the existing summary. It is read when the button renders, for the label only. It is never sent.

## Success

The API returns 200 with a body that matches `clearCompletedTodosResponseSchema`. The adapter returns `{ deletedCount }`. The hook invalidates `todoListQueryKey`, which refetches the current list page and the summary.

## Expected failures

| **Failure** | **When it happens** | **How it is represented** |
| --- | --- | --- |
| API rejects the query | The API returns 400. | `TodoApiError` of type `http` with status 400. Alert: "The completed todos could not be cleared. Refresh and try again." |
| Server failure | The API returns 500 or another non-2xx status. | `TodoApiError` of type `http` with that status. Alert: "The server could not clear your completed todos. Try again." |
| Network failure | The browser cannot reach the API. | `TodoApiError` of type `network`. Alert: "Could not reach the server. Check your connection and try again." |
| Bad response | The body is not JSON or does not match the contract. | `TodoApiError` of type `response_validation`. Alert: "The server returned an unexpected response. Refresh to see your todos." |
| Summary failure | Either summary request fails. | The summary query is in error. The button is hidden. The list is not affected. |

## Unexpected failures

Any other thrown error goes through TanStack Query as the mutation error. The hook logs it with `console.error`. The view shows "Something went wrong. Try again." with the retry button. The raw error is never shown.

# Design decisions

- **Visibility:** `getClearCompletedState` returns `hidden` when `totalCount - activeCount` is 0. Otherwise it returns `visible` with `completedCount`. The button renders only when the summary is in success and the state is `visible`. While the summary refetches, the button keeps the last value.
- **Full-collection wording:** The visible text is the accessible name, so the label matches what a screen reader says. "Clear all 4 completed todos" or "Clear the 1 completed todo". The number is the whole-collection completed count. The note "Applies to all todos, not only this view." shows when a status or a search is set, as in M43. It links to the button with `aria-describedby`.
- **No confirmation:** TodoMVC has none, and the single delete in M36 has none. The label names the count and the scope, so the action is clear before the click.
- **Fixed request:** The adapter sends only `status=completed`. It never passes the view search or page, because the API rejects them. Retry sends the same request. The delete is idempotent, so a repeat is safe.
- **Control:** A native `button`. It is not `disabled` while pending, because a disabled control drops focus. It uses `aria-disabled` and returns early from `onClick`.
- **No optimistic update:** The client holds one page, so it cannot remove the rest of the completed todos. It waits for the server and refetches.
- **Pending:** `useClearCompletedTodosMutation` returns the invalidation promise from `onSuccess`, as the existing hooks do. `isPending` covers the request and the refetch. During pending, `bulkPending` becomes `toggleAllMutation.isPending || clearMutation.isPending`. This locks every row and the toggle-all checkbox.
- **Mutual lock:** The button is `aria-disabled` while a row toggle, edit save, delete, or toggle-all is pending. Rows and toggle-all are locked while clear is pending. Two writes never race from this page.
- **Status region:** `TodoClearCompleted` always renders its polite status while the summary is in success. The button and the note render only when the state is `visible`. So the result message can still be read after the button hides.
- **Success:** The polite status reads from `deletedCount`. "Cleared 4 completed todos." or "Cleared 1 completed todo.". When `deletedCount` is 0, it reads "There were no completed todos to clear.". The status clears on the next click.
- **Focus after deletion:** `HomePage` sets a pending-focus flag when the user clicks. A layout effect runs when the summary and the list change. It acts only once the mutation has settled with success. If the button is still rendered, focus stays on it. If focus is on another element than the body, the effect does nothing. Otherwise it focuses the toggle-all checkbox when the summary has todos, or the empty-list heading when it has none. If the target is not on screen yet, for example during a page redirect, the effect waits for the next render. This follows the M36 delete focus rule.
- **Focus targets:** `TodoToggleAll` accepts an `inputRef` for the checkbox. `TodoList` accepts an optional `emptyHeadingRef` from outside and uses it instead of its own ref. The delete focus logic keeps working with the passed ref.
- **Failure:** `onError` also invalidates `todoListQueryKey`. The delete is one SQL statement, so it either ran or did not. A network or response failure cannot tell which, so a refetch shows the truth. The alert sits under the button with `role="alert"` and a "Retry" button. Focus stays on the clear button. If the refetch shows no completed todos, the button and alert hide and focus follows the success rule.
- **List and count refresh:** The count above the list comes from the list `totalItems`, which refetches by the prefix. A view that empties uses the existing empty message. A page that empties uses the existing `getPageRedirect`. The toggle-all label refreshes from the same summary.

# Certainty checks

### 1. What information enters the system?

The click on the clear-completed button. No user value is sent. The completed count from the summary is used only for the label.

### 2. How will you check that information?

The adapter has no input to check. The query is a fixed string. The API checks the query again and rejects anything but `status=completed`.

### 3. What will the operation return when it succeeds?

`{ deletedCount }`, the number of completed todos deleted. The list page and the summary then refetch.

### 4. What expected failures can happen?

A 400, a 500 or other non-2xx status, a network failure, a bad response body, and a summary failure.

### 5. How will each expected failure be represented?

Each request failure is a `TodoApiError` with its type and status. The view maps it to one safe message with a retry. A summary failure hides the button.

### 6. Where will the route, business rules, and database or UI work live?

`todo.clearCompleted.ts` holds the rules and text. The adapter makes the request. The hook owns the refresh. `TodoClearCompleted` draws the button. `HomePage` wires it and moves focus. The API and database do not change.

### 7. What tests will you write before implementation?

Tests for the clear rules, adapter, hook, component, focus refs, and route, then a Playwright test. They are listed below.

### 8. How will you prove the whole operation works through its real boundaries?

A Playwright test seeds active and completed todos across two pages, opens a filtered view, clears completed, and checks the request, the rows, the count, the result status, and the focus. It also checks a 500 and its retry, and the case where no todos remain.

### 9. Does this change multiple records or call another system? If yes, how will failure be handled safely?

Yes. It deletes every completed todo. The API runs one `DELETE`, so the change is all or nothing. The client never guesses the result. It refetches the list and the summary after success and after failure. Retry sends the same request, and the delete is idempotent, so a repeat is safe. The deletion is permanent.

### 10. If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?

Loading: the button is hidden while the summary loads. Empty: the button is hidden when there are no completed todos. Ready: a button with the full-collection label. Error: an alert under the button with a retry. Summary error: the button is hidden. Pending: `aria-disabled` button with focus kept, a polite status, and locked rows and toggle-all. Accessibility: a native button whose text is its name, a polite result status that stays mounted, a `role="alert"` failure, and focus moved to the toggle-all checkbox or the empty heading after success.

# Risks and assumptions

- The deletion is permanent. There is no undo and no confirmation. The full-collection label and the view note are the only guard.
- The completed count comes from two list reads. A write between them can skew the label until the next refresh. The API still deletes whatever is completed at that moment.
- `deletedCount` can differ from the label if another client changed todos. The result message uses `deletedCount` as is.
- A row that is being edited can be a completed todo. The row lock blocks its save while clear is pending. After clear, the row is gone, and a later save would get a 404 from the existing edit flow.
- If the refetch after a failure shows no completed todos, the alert hides with the button. The user does not see the failure message, but the list shows the server state.
- Focus moves up from below the list to the toggle-all checkbox. This is the nearest control that still acts on the collection.
- Existing route and browser tests mock `/todos` by URL and method. The new `DELETE` with a query must not hit the single-delete mocks.
