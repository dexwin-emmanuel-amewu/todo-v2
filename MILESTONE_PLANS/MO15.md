#### Objective:  
Plan how to get one todo by ID.

## Included
- A GET /todos/:todoId route on the API.
- Path param validation: todoId must be a well-formed UUID.
- 200 with the single todo on success, the same shape as todoSchema.
- 404 when the id is well-formed but no row exists.
- 400 when the id is not a well-formed UUID.
- 500 for repository database errors and stored-row validation errors.
- A not-found error response contract in packages/contracts.
- Route-level mapping tests plus integration tests through app.inject.

## Not included
- Changes to getTodoById in the repository. It already exists and is already tested.
- Update, delete, or any other single-todo operation.
- Frontend integration or UI.
- Lookup by any key other than the primary id (no lookup by title or slug).
- Returning related or expanded data alongside the todo.

## Acceptance criteria
- GET /todos/:todoId with the id of an existing todo returns 200 and a body matching `todoSchema` exactly, with the same field values the todo was created with.
- The returned body is the bare todo object, not wrapped in `items` or any envelope.
- GET /todos/:todoId with a well-formed UUID that matches no row returns 404 with a `notFoundErrorResponseSchema` body.
- GET /todos/abc (not a UUID) returns 400 with a `validationErrorResponseSchema` body, and no query reaches the database.
- A malformed id is a 400, never a 404. The two failures are distinct and are never collapsed into one status.
- The 404 body does not echo the requested id back to the client.
- A repository `DatabaseError` maps to 500 with an `internalErrorResponseSchema` body.
- A repository `ValidationError` (a stored row that fails `todoSchema`) maps to 500, not 404 and not 200.
- Adding the route does not shadow or break GET /todos. Existing list, filter, search, and pagination tests all still pass unchanged.
- `getTodoById` in the repository is unchanged, and its existing tests pass without edits.

## Contracts
### Input
#### What information enters the operation?
One path parameter, `todoId`, taken from the URL. Fastify always provides it as a string for a single-segment `:todoId` param. It must be a well-formed UUID. Nothing else enters the operation: no body, no query params, no headers beyond transport defaults.

### Success
#### What exact value or visible result means success?
HTTP 200 with a body matching `todoSchema`: `{ id, title, completed, createdAt }`. The body is the todo itself, unwrapped.

### Expected failures

| Todo not found | todoId is a well-formed UUID but no row has that id | HTTP 404, notFoundErrorResponseSchema body |
| Repository database error | the select query rejects | HTTP 500, internalErrorResponseSchema body |
| Repository validation error | the stored row fails todoSchema | HTTP 500, internalErrorResponseSchema body |

## Certainty checks
### What information enters the system?
A single path parameter, `todoId`, as a raw string from the URL.

### How will you check that information?
A pure function, `parseTodoId(rawId)`, following the same shape as the existing `parseStatusFilter`/`parseSearchQuery`/`parsePagination`. It rejects anything that is not a string, then checks the string against `todoIdParamSchema`. It returns `Result<string, QueryValidationError>` so the route can short-circuit to 400 before touching the database.

### What will the operation return when it succeeds?
HTTP 200 with the todo.

### What expected failures can happen?
A malformed id is a 400. A well-formed id with no matching row is a 404. A database failure or a stored row that fails validation is a 500. See the Expected failures table.

### How will each expected failure be represented?
`parseTodoId` runs first and short-circuits to 400 with a `validationErrorResponseSchema` body. Past that point the repository result is handed to `toGetTodoResponse`, which matches on `result.error.type`: `not_found` becomes 404 with `notFoundErrorResponseSchema`, and `database` or `validation` becomes 500 with `internalErrorResponseSchema`.

### Where will the route, business rules, and database work live?
Path validation and status mapping live in apps/api/src/module/todo.routes.ts. The schemas live in packages/contracts/src/index.ts. The database read is the already-existing `getTodoById` in apps/api/src/module/todo.repository.ts.

### What tests will you write before implementation?
Check "Tests to write first".

### How will you prove the whole operation works through its real boundaries?
Route integration tests through `app.inject` against a disposable Postgres database: create a real todo, fetch it back by its real id, then fetch a random UUID for the 404 and a non-UUID string for the 400.

### Does this change multiple records or call another system?
No.

## Design decisions
This section spells out the mechanics the sections above only reference.

- **Param name**: `:todoId`, not `:id`, matching the milestone wording and reading unambiguously at the call site.
- **Malformed id is 400, not 404**: a non-UUID id is a badly formed request, not a missing resource, so it is rejected before any database work. Some APIs return 404 for both so that the two cases are indistinguishable to a client probing for ids. That hiding is worth nothing here: ids are random v4 UUIDs and the API has no auth, so a 404 leaks nothing a 400 does not. Flagged for review.
- **404 body shape**: `{ "error": { "type": "not_found" } }`, matching the flat, type-tagged shape of the existing validation and internal bodies. The requested id is deliberately not echoed back into the response, keeping the client from reflecting arbitrary input, the same way `internalErrorResponseSchema` carries no detail. The repository's `NotFoundError` still carries the id internally so it can be logged.
- **No service layer**: `createTodoFlow` exists because creating parses a request body first. Reading by id has no such rule, so the route calls `getTodoById` directly. Adding a `getTodoFlow` would be a function that only forwards its arguments.
- **Response is unwrapped**: 200 returns the todo object directly, not `{ item: todo }`. `GET /todos` returns a wrapper because it carries pagination metadata alongside the rows; a single read has no metadata to carry, and `POST /todos` already returns a bare todo, so the bare shape is the consistent choice.
- **Validation before the database**: `parseTodoId` runs first, exactly like the query parsers on `GET /todos`. A malformed id never becomes a Postgres query, which also avoids a driver-level cast error on an invalid uuid literal being surfaced as a 500.
- **Route registration order**: `GET /todos` and `GET /todos/:todoId` are different path depths, so Fastify's router keeps them separate and registration order does not matter. A regression test on `GET /todos` guards this anyway.
- **Success validation**: `toGetTodoResponse` re-parses the value with `todoSchema` before returning it, the same defensive step `toListTodosResponse` already takes with `todoListResponseSchema`. A body that fails that parse becomes a 500.
- **Repository untouched**: `getTodoById` already returns exactly the three error types this route needs to map. Rewriting it would create churn with no behavioural change.

## Risks and assumptions
- Assumes the path is `GET /todos/:todoId` under the existing `/todos` collection, not a separate top-level route.
- Assumes a malformed, non-UUID id is a 400 and a well-formed but unused id is a 404, kept as two distinct statuses rather than collapsing both into 404. Flagging this for review since some APIs deliberately return 404 for both.
- Assumes the 404 body is `{ error: { type: "not_found" } }` with the id deliberately left out. Flagging this for review, since a client debugging a bad id gets less to work with.
- Assumes the 200 body is the bare todo, matching `POST /todos`, rather than an envelope like `{ item: todo }`. If the list response's wrapper is later treated as the house style, this is the endpoint that would need to change.
- Assumes no service-layer function is needed, since there is no rule to enforce between the route and the repository. If a later milestone adds one (ownership, soft-delete visibility), a `getTodoFlow` gets introduced then.
- Assumes `getTodoById` needs no change at all. If the review disagrees on the `NotFoundError` shape carrying the id, that shape is already in use and changing it would touch existing passing tests.
- Assumes Fastify routes `GET /todos` and `GET /todos/:todoId` independently, which its radix-tree router does. A regression test covers it rather than trusting it silently.
- Assumes a stored row failing `todoSchema` is a 500, not a 404. The row exists; the server is at fault for having written something it cannot read back.
