# Objective

Plan frontend status filtering.

# Included

- Add All, Active, and Completed controls above the list.
- Keep the selected filter in the URL as `?status=active` or `?status=completed`. All is the default and has no search param.
- Validate the URL value with `todoStatusFilterSchema`. Fall back to All for a missing or bad value.
- Give each filter its own query key under the existing `["todos", "list"]` prefix.
- Send the selected status to `GET /todos` through the browser API adapter.
- Style the selected control and mark it with `aria-current="page"`.
- Keep the last list on screen while a new filter loads. Show a loading message for it.
- Show a count of matching todos from `totalItems`.
- Show a different empty message for each filter.
- Keep create, toggle, edit, and delete working in every filter view.
- Test the adapter, query hook, view state, list, route, and browser flow.

# Not included

- Backend, API contract, or database changes. `GET /todos?status=` already exists.
- Separate counts for each tab. That needs three requests or a new API field.
- Search and pagination controls.
- Clear completed and toggle all controls.
- Saving the filter in local storage.

# Current repository evidence

- `packages/contracts/src/index.ts` defines `todoStatusFilterSchema` as `"all" | "active" | "completed"`. It also defines `todoListResponseSchema` with `totalItems`.
- `apps/api/src/module/todo.routes.ts` reads `status` in `GET /todos`. A missing value means `all`. A bad value returns 400 with a validation body.
- `apps/api/src/module/todo.repository.ts` `listTodos` filters by status. `totalItems` counts only the filtered rows.
- `apps/web/src/api/todo.api.ts` `fetchTodoList()` takes no arguments and always calls `/todos`.
- `apps/web/src/hooks/useTodoListQuery.ts` exports `todoListQueryKey = ["todos", "list"]` with `staleTime: 30_000`.
- The create, completion, replace, and delete hooks all invalidate `todoListQueryKey`. Prefix matching means they will also refresh every filtered key.
- `apps/web/src/router.tsx` defines the `/` route with TanStack Router. It has no `validateSearch` yet.
- `apps/web/src/routes/index.tsx` builds the view state with `getTodoListViewState` and renders `TodoList`.
- `apps/web/src/module/todo.state.ts` maps the query to `initial_loading`, `initial_failure`, `ready`, `refreshing`, and `refresh_failure`.
- `apps/web/src/components/TodoList.tsx` shows "No todos yet." and focuses that heading when the list becomes empty.
- `apps/web/src/routes/index.test.tsx` renders `HomePage` with only a `QueryClientProvider`. It mocks `fetch`.
- `e2e/tests/delete-todo.spec.ts` mocks the API with `page.route("**/todos", ...)`.
- `pnpm --filter web test` runs Vitest. `pnpm test:e2e` runs Playwright.

# Acceptance criteria

[ ] A filter group labelled "Filter todos" shows All, Active, and Completed.

[ ] Opening `/` selects All and sends `GET /todos` with no status param.

[ ] Opening `/?status=active` selects Active and sends `GET /todos?status=active`.

[ ] Opening `/?status=completed` selects Completed and sends `GET /todos?status=completed`.

[ ] Opening `/?status=done` selects All, replaces the URL with `/`, and sends no bad status to the API.

[ ] Choosing a filter updates the URL. Browser back and forward restore the earlier filter.

[ ] The selected control has `aria-current="page"` and a clear selected style. Other controls do not.

[ ] Each filter uses its own query key. Going back to a filter shows its cached list at once.

[ ] While a new filter loads, the last list stays visible, row actions are disabled, and a status message says the filter is loading.

[ ] The count shows `totalItems` for the selected filter, for example "1 active todo" or "3 completed todos". It is hidden while the shown list is from the previous filter.

[ ] Each filter has its own empty message: "No todos yet.", "No active todos.", or "No completed todos."

[ ] Create, toggle, edit, and delete refresh the current filtered list. A todo that no longer matches leaves the list after refresh.

[ ] Load and refresh failures keep the existing alert and retry behaviour.

# Contracts

## Input

The `status` search param from the URL. It is checked with `todoStatusFilterSchema`. The request is `GET /todos` for All, or `GET /todos?status=<active|completed>` for the other filters. There is no body.

## Success

The API returns 200 with a body that matches `todoListResponseSchema`. The adapter returns the parsed body. The page shows `items` and a count from `totalItems`. The selected control matches the URL.

## Expected failures

| **Failure** | **When it happens** | **How it is represented** |
| --- | --- | --- |
| Bad URL status | The URL has a status that is not all, active, or completed. | The route falls back to All and replaces the URL. No error is shown. |
| Bad adapter status | Code calls `fetchTodoList` with a bad status. | Reject with `TodoApiError` of type `request_validation`. Do not call `fetch`. |
| API rejects the status | The API returns 400. | `TodoApiError` of type `http` with status 400. Show the existing load or refresh alert. |
| Other HTTP failure | The API returns another non-2xx status, such as 500. | `TodoApiError` of type `http` with that status. Show the existing alert with retry. |
| Network failure | The browser cannot reach the API. | `TodoApiError` of type `network`. Show the existing alert with retry. |
| Bad response | The body is not JSON or does not match the contract. | `TodoApiError` of type `response_validation`. Show the existing alert with retry. |

## Unexpected failures

Any other thrown error goes through TanStack Query as the query error. The view shows the same safe alert and retry button. The raw error is never shown to the user. A bad URL value never reaches the adapter because the route parses it first.

# Responsibilities

| **Layer** | **Responsibility** |
| --- | --- |
| Contract | Reuse `todoStatusFilterSchema` and `todoListResponseSchema`. No changes. |
| Route or page | Add `validateSearch` to the `/` route. Parse `status` and fall back to `all`. `HomePage` reads the filter with `getRouteApi("/")` and passes it to the hook and the list. |
| Service or flow | `getTodoListViewState` takes the snapshot with `isPlaceholderData` and returns a loading-filter state. The existing API service already filters. |
| Repository or API adapter | `fetchTodoList(status)` validates the status, builds the URL, and keeps the current error mapping. |
| Hook | `useTodoListQuery(status)` uses `getTodoListQueryKey(status)` and keeps the previous data while the new filter loads. |
| View | Add a `TodoFilters` control group with selected styling and `aria-current`. `TodoList` shows the count, the loading message, and the empty message for the filter. |


# Certainty checks

### 1. What information enters the system?

The `status` value in the URL search params. It comes from a filter link or a typed or shared URL.

### 2. How will you check that information?

The route checks it with `todoStatusFilterSchema` and falls back to `all`. The adapter checks it again before the request. The API checks it a third time.

### 3. What will the operation return when it succeeds?

A `TodoListResponse` with only the matching todos. `totalItems` is the count of matching todos.

### 4. What expected failures can happen?

A bad URL value, a bad adapter value, a 400 or 500 from the API, a network failure, and a bad response body.

### 5. How will each expected failure be represented?

A bad URL value falls back to All. A bad adapter value is a `request_validation` `TodoApiError`. API, network, and body failures use the existing `TodoApiError` types. The view shows the existing alert and retry.

### 6. Where will the route, business rules, and database or UI work live?

The route owns URL parsing. The adapter owns the request. The hook owns the query key and cache. The view state module owns the state choice. `TodoFilters` and `TodoList` own the UI. The API and database stay the same.

### 7. What tests will you write before implementation?

Adapter tests for each status and bad input. Hook tests for keys and kept data. View state tests for the loading-filter state. Component tests for selected styling, count, and empty messages. Route tests for URL parsing and history. A Playwright test for the browser flow.

### 8. How will you prove the whole operation works through its real boundaries?

The Playwright test opens the app, clicks each filter, and checks the request URL, the page URL, the selected control, the rows, and the count. It also opens a bad URL and checks the fallback.

### 9. Does this change multiple records or call another system? If yes, how will failure be handled safely?

No. It only reads from the API. A failed read keeps the last list or shows the retry alert.

### 10. If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?

Loading: the first load shows "Loading todos". A filter change keeps the last list, disables row actions, and announces "Loading active todos" in a polite status region. Empty: one message per filter, with the existing focus behaviour. Ready: rows and count. Error: the existing alerts with retry. Pending: mutations keep their current pending states. Accessibility: the controls sit in a `nav` with `aria-label="Filter todos"`, are reachable by keyboard, and use `aria-current="page"` on the selected one. Selected style is not shown by colour alone.

1. Adapter: `fetchTodoList("all")` calls `/todos` with no query string.
2. Adapter: `fetchTodoList("active")` and `fetchTodoList("completed")` call `/todos?status=active` and `/todos?status=completed`.

6. Hook: switching status keeps the previous data and sets `isPlaceholderData` until the new data arrives.
7. Hook: invalidating `todoListQueryKey` refetches the active filtered query.
8. View state: placeholder data maps to a `loading_filter` state with the old items.
9. Component: `TodoFilters` marks only the selected control with `aria-current="page"` and the selected class.
10. Component: the count reads "1 active todo", "2 active todos", and so on for each filter. It is hidden in `loading_filter`.
11. Component: each filter shows its own empty message.
12. Component: row actions are disabled in `loading_filter`.
13. Route: `/?status=completed` selects Completed and requests `?status=completed`.
14. Route: `/?status=done` selects All, replaces the URL with `/`, and requests `/todos`.
15. Route: clicking Active updates the URL and the request. Going back restores All.
16. Route: toggling a todo in the Active view refreshes the list, and the completed todo leaves.
17. Browser: click through All, Active, and Completed. Check the requests, the URL, the rows, the count, and the selected control.

# Expected first failure

The second adapter test should fail first. `fetchTodoList("active")` still calls `/todos` with no status, so the test sees `/todos` instead of `/todos?status=active`.
