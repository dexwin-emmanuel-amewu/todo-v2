# Objective

Plan a per-row delete action that permanently deletes one todo through the existing API and reconciles the frontend list.

# Included

- Add a labelled delete action to each todo row.
- Validate and pass the selected todo UUID through the browser API adapter.
- Show pending state and prevent repeat requests while that todo is being deleted.
- Handle the API's 204 success, 404 missing-todo response, and other failures.
- Refresh the list after success or 404 so stale rows are removed.
- Define accessible feedback and focus behavior when a row disappears.
- Test the adapter, mutation hook, row, route, and browser flow.

# Not included

- Bulk deletion, undo, or changes to todo creation, completion, or editing.
- Backend, API contract, or database changes.
- Optimistic removal; keep the row visible until the server confirms the deletion or a refresh resolves a 404.

# Acceptance criteria

[ ] Each row has a clearly named Delete action that identifies the todo.

[ ] Activating Delete validates the UUID and sends exactly one `DELETE /todos/:todoId` request with no body.

[ ] While deletion is pending, the selected action is disabled, its pending state is announced, and duplicate pointer or keyboard activation cannot dispatch another request.

[ ] A 204 response is treated as success without attempting to parse a response body; the list is invalidated and the deleted row disappears.

[ ] A 404 invalidates the list to remove a stale row and presents understandable feedback if the row remains after refresh.

[ ] Network, other HTTP, and unexpected failures keep the row visible, clear pending state, provide a safe retryable message, and allow another attempt.

[ ] After successful removal, focus moves to the next row's Delete action, or the previous row's action if there is no next row. If the deleted row was the only row, focus moves to the empty-state heading/container.

[ ] Do not move focus after the request if the user has deliberately moved it elsewhere while deletion was pending.

[ ] Adapter, hook, row, route, and browser tests cover the relevant request, pending, success, failure, reconciliation, and focus behavior.

# Contracts

## Input

The selected todo UUID, checked with `todoIdParamSchema`. The request is `DELETE /todos/:todoId` and has no body.

## Success

The API returns `204 No Content`. The adapter resolves successfully without parsing JSON. The mutation invalidates `todoListQueryKey`; the query refetch removes the deleted row.

## Expected failures

| **Failure** | **When it happens** | **How it is represented** |
| --- | --- | --- |
| Invalid todo ID | The ID fails client-side UUID validation. | Reject with `TodoApiError` of type `request_validation`; do not send a request. |
| Todo missing | The well-formed ID no longer exists; the API returns 404. | Existing `TodoApiError` with type `http` and status 404; invalidate the list to reconcile stale data. |
| Other HTTP failure | The API returns a non-2xx status, including 500. | Existing `TodoApiError` with type `http` and status; keep the row and offer retry. |
| Network failure | The browser cannot reach the API. | Existing `TodoApiError` with type `network`; keep the row and offer retry. |

## Unexpected failures

Normalize malformed adapter usage through the existing request-validation pattern. For unknown runtime errors, log diagnostics as the other mutation hooks do, show a safe retryable message, preserve the row, and clear pending state. Never parse or expose a body from a successful 204 response.

# Responsibilities

| **Layer** | **Responsibility** |
| --- | --- |
| Contract | Reuse `todoIdParamSchema`; no contract changes. |
| API route/service/repository | Existing API validates the ID, deletes one record, and returns the documented 204/400/404/500 responses; no backend changes are planned. |
| API adapter | Add `deleteTodo(todoId)`, validate the ID, send DELETE without a body, and accept 204 without JSON parsing. |
| Mutation hook | Call the adapter, disable automatic retries, invalidate the list on success, and invalidate on 404 to reconcile stale data. |
| Route | Connect the deletion mutation to `TodoList`, including pending/error identity and retry handling. |
| View | Render the accessible per-row action and pending/error feedback; coordinate focus after list reconciliation. |

# Certainty checks

### What information enters the system?
The UUID belonging to the row whose Delete action was activated.

### How will you check that information?
 Validate it with the existing `todoIdParamSchema` before making the request; the API validates it again.

### What will the operation return when it succeeds?
 HTTP 204 with no body. The adapter resolves `void`, then list invalidation fetches the remaining todos.

### What expected failures can happen?
Invalid UUID (400), missing todo (404), internal server failure (500), and network failure.

### How will each expected failure be represented?
Client validation is a request-validation `TodoApiError`; API failures and network failures use existing `TodoApiError` types and status. A 404 triggers list reconciliation; other failures preserve the row and show retry feedback.

### Where will the route, business rules, persistence, and UI work live?
Existing API route/service/repository own validation and persistence. The browser adapter owns HTTP, the hook owns mutation and refresh, the route wires the mutation, and the row/list view owns controls, messages, and focus.

### What tests will you write before implementation?
Adapter tests for valid and invalid IDs, bodyless DELETE, 204, and errors; hook tests for success/404 invalidation and no retries; component and route tests for pending, duplicate prevention, retry, stale-row reconciliation, and focus; a Playwright flow for deletion through the browser.

### How will you prove the whole operation works through its real boundaries?
The browser test will activate a row's Delete control, inspect the DELETE request, return 204, and verify the row is removed and focus is placed appropriately. A 404 browser/component scenario will verify stale-list reconciliation.

### Does this change multiple records or call another system? If yes, how will failure be handled safely?
It calls the API to hard-delete one record. Failure leaves the row available and clears pending state; success refreshes the collection. No multi-record transaction or undo is involved.

### If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?
Existing list loading and empty states remain. Ready rows expose a named Delete button. Pending disables that action and announces deletion. Failure leaves the row and announces a retryable error. After removal, focus moves to a sensible neighboring action or the empty-state heading, unless the user moved focus while waiting.

# Tests to write first

1. Adapter sends `DELETE /todos/:todoId` with no body for a valid UUID and resolves on 204 without reading JSON.
2. Adapter rejects a malformed UUID with request-validation error and makes no fetch call.
3. Adapter maps network and non-2xx responses, including 404 and 500, to `TodoApiError` with the expected type/status.
4. Mutation hook invalidates `todoListQueryKey` after success, invalidates it after 404, and does not retry automatically.
5. Row Delete action has an accessible name that includes the todo title and dispatches that row's UUID.
6. Pending state disables the selected action, announces progress, and repeated click/keyboard activation dispatches only once.
7. Success removes the row after list refresh and focuses the next row action or previous row action when no next row exists.
8. Deleting the only/last row focuses the empty-state heading/container.
9. A 404 refresh removes a stale row; if it remains, the user receives clear feedback.
10. Network/server failure leaves the row visible, announces an error, clears pending state, and supports retry.
11. Focus is not stolen if the user moves it elsewhere while the request is pending.
12. Route test covers row deletion and refreshed list state.
13. Browser test covers delete request and successful row removal, with a missing-row reconciliation case where practical.

# Implementation steps

1. Write adapter tests for bodyless DELETE, 204 handling, invalid UUIDs, and HTTP/network failures.
2. Implement `deleteTodo` with existing validation and error conventions.
3. Write mutation-hook tests, then add the hook with success and 404 list invalidation and `retry: 0`.
4. Write component tests for action semantics, pending/repeat prevention, error/retry, reconciliation, and focus edge cases.
5. Add deletion controls to the row and connect the mutation in the home route.
6. Add route coverage for request and refreshed list state.
7. Add a Playwright test for the browser flow and verify request method, URL, and removal.


# Risks and assumptions

- Deletion is permanent and has no undo because the existing API performs a hard delete.
- A 404 is treated as an instruction to refresh stale list data; if the row remains after refresh, show feedback rather than silently claiming it was deleted.
- Focus restoration needs stable row-action refs and must account for the refresh removing the deleted row before the effect runs.
