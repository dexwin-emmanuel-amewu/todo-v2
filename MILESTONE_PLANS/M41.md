# Objective

Plan how the user moves between todo-list pages and changes page size.

# Included

- Add a pagination bar below the list with Previous page, Next page, a page-size select, and the page metadata.
- Show the metadata from the response: `Page 2 of 5` and `Showing 21 to 40 of 87`.
- Keep the committed page in the URL as `?page=2` and the page size as `?pageSize=50`. Page 1 and page size 20 are the defaults, so they are never written to the URL.
- Offer the page sizes 10, 20, 50, and 100. The default is 20, which matches the API.
- Validate `page` with `todoPageQuerySchema` and `pageSize` with `todoPageSizeQuerySchema`, and keep only the offered sizes. A bad value is dropped and the URL is replaced.
- Put `page` and `pageSize` in the query key, next to the status and the search.
- Send `page` and `pageSize` to `GET /todos` through the browser API adapter, only when they are not the defaults.
- Reset the page when the status, the search, or the page size changes. Keep the page size when the status or the search changes.
- Disable Previous on the first page and Next on the last page.
- Handle a page past the last page by moving to the last page. Handle a page above 1 on an empty list by moving to page 1.
- Hide the bar when the list is empty or has 10 todos or fewer.
- Keep focus on the control the user used. Announce the new page in a polite status.
- Keep the last page on screen while the next page loads, with the existing "Updating results" message.
- Keep create, toggle, edit, and delete working on every page.
- Test the page rules, adapter, query hook, components, route, and browser flow.

# Not included

- Backend, API contract, or database changes. `GET /todos?page=&pageSize=` already exists.
- Numbered page links, first and last buttons, and a jump-to-page box.
- Infinite scroll and load more.
- Saving the page size in local storage.
- Prefetching the next page.
- Keeping a half-edited row open when the page changes.
- Clear completed and toggle all controls.

# Acceptance criteria

[ ] Opening `/` sends `GET /todos` with no page and no page size. The URL stays `/`.

[ ] Opening `/?page=2&pageSize=10` sends `GET /todos?page=2&pageSize=10`.

[ ] With more than 10 todos, a `Pagination` navigation sits below the list. It has Previous page, Next page, and a select labelled "Todos per page".

[ ] The bar shows `Page 2 of 5` and `Showing 21 to 40 of 87` from the response. The numbers come from the response and not from the URL.

[ ] Next page moves to the next page and writes `page` in the URL. Previous page does the same in the other direction. Each move adds a history entry.

[ ] Going to page 1 removes the `page` param.

[ ] Previous page is disabled on page 1. Next page is disabled on the last page. A disabled control is `aria-disabled`, stays focusable, and ignores clicks.

[ ] The select offers 10, 20, 50, and 100, and shows the current size. Choosing a size writes `pageSize`, removes `page`, and sends the new size. Choosing 20 removes `pageSize`.

[ ] Choosing a status or committing a search removes `page` and keeps `pageSize`. Clear search does the same.

[ ] `/?status=active&search=milk&page=2&pageSize=10` sends all four values. Metadata and rows match all four.

[ ] Opening `/?page=0`, `/?page=-1`, `/?page=1.5`, `/?page=abc`, `/?page=true`, and `/?page=` drops the page and replaces the URL with `/`.

[ ] Opening `/?page=1` and `/?pageSize=20` replaces the URL with `/`. Opening `/?pageSize=7`, `/?pageSize=500`, and `/?pageSize=abc` drops the size and replaces the URL.

[ ] Opening `/?page=02` replaces the URL with `/?page=2` and does not loop.

[ ] Opening `/?page=9` when the last page is 3 shows "Updating results", then replaces the URL with `/?page=3`. Back does not return to page 9.

[ ] Opening `/?page=3` on an empty list replaces the URL with `/`, and shows the existing empty message.

[ ] Deleting the only todo on the last page moves to the new last page without an error.

[ ] Toggling a todo off the Active view on the last page, so that the page empties, moves to the new last page.

[ ] The bar is hidden when `totalItems` is 0. It is also hidden when `totalItems` is 10 or fewer.

[ ] While a new page loads, the last page stays visible, row actions are disabled, the count and the range are hidden, and both buttons are `aria-disabled`.

[ ] Each page has its own key. Going back to an earlier page shows its cached list at once.

[ ] Browser back and forward restore the earlier page, the earlier page size, and the select value.

[ ] Focus stays on Next page after Next page is pressed, also when it becomes disabled. The same holds for Previous page and the select.

[ ] A polite status announces `Page 2 of 5` when a page finishes loading. It does not announce while the page is loading.

[ ] A load failure shows the existing alert with retry. Retry refetches the current page. The bar is hidden.

[ ] Create, toggle, edit, and delete refresh the current page.

# Contracts

## Input

The `page` and `pageSize` params from the URL, and the choice from the select. The request is `GET /todos`, with `status`, `search`, `page`, and `pageSize` added only when they are not the defaults, in that order. There is no body.

## Success

The API returns 200 with a body that matches `todoListResponseSchema`. The adapter returns the parsed body. The page shows `items`, the count from `totalItems`, and the bar from `page`, `pageSize`, `totalItems`, and `totalPages`.

## Expected failures

| **Failure** | **When it happens** | **How it is represented** |
| --- | --- | --- |
| Bad URL page | The URL page is not a whole number of 1 or more. | The route drops the page and replaces the URL. No error is shown. |
| Bad URL page size | The URL page size is not 10, 20, 50, or 100. | The route drops the page size and replaces the URL. No error is shown. |
| Page past the end | The page is above `totalPages` and `totalItems` is above 0. | The page replaces the URL with the last page. "Updating results" shows meanwhile. |
| Page on an empty list | The page is above 1 and `totalItems` is 0. | The page replaces the URL with page 1. The existing empty message shows. |
| Bad adapter page | Code calls `fetchTodoList` with a page or size that fails its schema. | Reject with `TodoApiError` of type `request_validation`. Do not call `fetch`. |
| API rejects the query | The API returns 400. | `TodoApiError` of type `http` with status 400. Show the existing load alert. |
| Other HTTP failure | The API returns another non-2xx status, such as 500. | `TodoApiError` of type `http` with that status. Show the existing alert with retry. |
| Network failure | The browser cannot reach the API. | `TodoApiError` of type `network`. Show the existing alert with retry. |
| Bad response | The body is not JSON or does not match the contract. | `TodoApiError` of type `response_validation`. Show the existing alert with retry. |

## Unexpected failures

Any other thrown error goes through TanStack Query as the query error. The view shows the same safe alert and retry button. The raw error is never shown. A bad URL value never reaches the adapter because the route parses it first.

# Design decisions

- **Metadata:** The bar reads `page`, `pageSize`, `totalItems`, and `totalPages` from the response. The range is `(page - 1) * pageSize + 1` to that start plus `items.length - 1`. `getPageRange` computes it as a pure function. The count above the list stays as it is.
- **URL shape:** `?page=` and `?pageSize=` sit beside `status` and `search`. A default value is never written. `getTodoListSearch` accepts only whole numbers and digit-only text, so `true`, `null`, `1e1`, `0x10`, and ` 2` are dropped. The router turns `?page=2` into the number 2, so the route compares parsed values and not strings, as in M39.
- **Page-size choices:** `PAGE_SIZES = [10, 20, 50, 100]` and `DEFAULT_PAGE_SIZE = 20` live in `todo.pagination.ts`. 100 is the API maximum. A size that the API allows but the select does not offer, such as 30, is dropped.
- **Controls:** Previous and Next are buttons, not links, so focus stays on the button after a click and also when it becomes disabled. A disabled button uses `aria-disabled` and ignores clicks. The select is a native `select`. Previous and Next push a history entry. A page-size change pushes one too.
- **Visibility:** The bar renders when `totalItems` is above 10, the smallest page size. Below that, no choice would change the page.
- **Query identity:** The key is `["todos", "list", { status, search, page, pageSize }]`. `page` defaults to 1 and `pageSize` to 20 inside `getTodoListQueryKey`, so `/` and `/?page=1` share one key. It uses only committed URL values. Prefix invalidation refreshes every page.
- **Reset rules:** `getTodoListSearchLink({ status, search, pageSize })` never carries a page. A new `getTodoListPageLink` adds a page to the current link. Status links, search commits, and Clear search keep the page size and drop the page. A page-size change drops the page, because the old page number points at different rows.
- **Out-of-range pages:** `getPageRedirect({ page, totalPages, totalItems })` returns the page to move to, or `undefined`. The target is `max(1, totalPages)`. `HomePage` calls it on a ready response and navigates with `replace: true`. While a redirect is due, `HomePage` passes `loading_query` with no rows, so the empty message does not flash. The loop ends because the next response is in range.
- **Loading and failure:** The existing `loading_query` state covers a page change. The range is hidden and both buttons are `aria-disabled` in it. A failure shows the existing alert and hides the bar, never the old page.
- **Focus and announcements:** Focus never moves on a page change. A visually hidden `role="status"` region inside the bar holds `Page 2 of 5`. It renders only in the ready state, so it is silent while loading.
- **Edit and mutations:** Create, toggle, edit, and delete keep invalidating `todoListQueryKey`. The range rule above handles a page that empties.

# Certainty checks

### 1. What information enters the system?

The `page` and `pageSize` values in the URL, the click on Previous or Next, and the select choice.

### 2. How will you check that information?

`normalizePage` and `normalizePageSize` check the URL values. The adapter checks them again with the contract schemas. The API checks them last.

### 3. What will the operation return when it succeeds?

A `TodoListResponse` with one page of todos that match the status and the search. `page`, `pageSize`, `totalItems`, and `totalPages` describe where that page sits.

### 4. What expected failures can happen?

A bad URL page, a bad URL page size, a page past the end, a page on an empty list, a bad adapter value, a 400 or 500 from the API, a network failure, a bad response body.

### 5. How will each expected failure be represented?

Bad URL values are dropped by the route. Out-of-range pages are replaced with a valid page. A bad adapter value is a `request_validation` `TodoApiError`. Other failures use the existing `TodoApiError` types and the existing alert.

### 6. Where will the route, business rules, and database or UI work live?

The route parses the URL. `todo.pagination.ts` holds the page rules. The adapter makes the request. The hook owns the key and cache. `TodoPagination` draws the bar. The API and database do not change.

### 7. What tests will you write before implementation?

Tests for the page rules, links, adapter, hook, components, and route, then a Playwright test. They are listed below.

### 8. How will you prove the whole operation works through its real boundaries?

A Playwright test opens a long list, presses Next, changes the page size, adds a status and a search, goes back, opens a page past the end, and opens bad URLs. It checks each request, the URL, the rows, and the focus.

### 9. Does this change multiple records or call another system? If yes, how will failure be handled safely?

No. It only reads. A failed read shows the retry alert.

### 10. If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?

Loading: "Loading todos" at first, then "Updating results" over the old page. Empty: the existing messages, with no bar. Ready: rows, the count, and the bar. Error: the existing alert with retry, and no bar. Pending: unchanged. Accessibility: a labelled `Pagination` navigation, named buttons, a labelled select, `aria-disabled` controls that keep focus, a polite page status, and no focus jump on a page change.

# Risks and assumptions

- The router may parse `?page=2` as a number and `?page=02` as text. The plan accepts both and compares parsed values, and tests that `02` does not loop.
- The redirect for a page past the end could loop if the list shrinks between two responses. Each step moves to a smaller page, so the loop ends.
- A todo created on any page refreshes that page. It does not appear there unless that page is the last one, so the user may not see it until they go to the last page.
- A row that is being edited closes when the page changes, and its draft is lost. Locking the pagination during an edit is left for later.
- The page sizes 10, 20, 50, and 100 are chosen defaults. They are one constant and easy to change.
- The API orders by `createdAt` and then `id`, so the order is stable. A new todo always lands at the end, on the last page.
