# Acceptance criteria

## Clean start

[ ] On a fresh clone, `pnpm install --frozen-lockfile` succeeds with no lockfile change.

[ ] `docker compose down -v` followed by `docker compose up --build -d --wait` builds the images, starts Postgres, runs the migration, and starts the API and web. The command is documented in `README.md`.

[ ] After startup, `http://localhost:8080` shows the empty state. `http://localhost:8080/health` returns `{ "status": "ok" }` through the web server.

[ ] The `migrate` service exits `0` and the `todos` table has the `updated_at` column. Running the command a second time applies nothing and still exits `0`.

[ ] The API does not start when the migration fails. Compose reports the failed service.

[ ] Data survives `docker compose down` and `up`. It is gone after `docker compose down -v`.

## Expected failures

| **Failure** | **When it happens** | **How it is represented** |
| --- | --- | --- |
| Port in use | 5432, 3000, or 8080 is taken on the host. | `docker compose up` fails with a bind error. The README names the ports. |
| Postgres not ready | The `migrate` service starts too early. | `depends_on` waits for the `pg_isready` healthcheck. |
| Migration fails | Bad SQL or no database. | `migrate` exits non-zero. `api` depends on `service_completed_successfully`, so it never starts. `--wait` fails. |
| API not healthy | The API crashes or cannot reach Postgres. | The `api` healthcheck on `/health` fails. `web` does not start. `--wait` fails. |
| Stale data | A previous volume is reused. | The plan always runs `docker compose down -v` first. |
| Stack test against nothing | The stack is not running. | Playwright fails on the first `page.goto` with a connection error. |
| Lockfile drift | `pnpm install --frozen-lockfile` sees a change. | The install fails in the Docker build and in CI. |

## Unexpected failures

A failure in any command stops the run. The output is saved into the evidence packet. A real defect becomes a finding with a severity. A critical finding blocks the pull request until it is fixed or the manager accepts it in writing.

# Design decisions

- **One Dockerfile with two targets:** A root `Dockerfile` installs the pnpm workspace once. Target `api` builds `@todo/contracts` and `apps/api`. Target `web` builds `apps/web` and copies `dist` into `nginx:alpine`. The workspace needs the root lockfile, so the build context is the repository root.
- **Migration as its own service:** `migrate` uses the `api` image and runs `pnpm --filter api db:migrate`. `api` waits for it to finish. A failed migration then blocks the API instead of leaving it half ready. It reuses the existing script and needs no new code.
- **API image keeps dev dependencies:** `drizzle-kit` is a dev dependency and `migrate` needs it. Pruning is out of scope.
- **Web serves on 8080 and proxies:** An `nginx.conf` serves the SPA with a fallback to `index.html` and proxies `/todos` and `/health` to `api:3000`. `VITE_API_URL` stays empty, so the built app keeps using its own origin, as in dev.
- **One command:** `docker compose up --build -d --wait`. `--wait` returns only when every service is healthy, so scripts and CI can rely on it. `pnpm docker:up` changes to `docker compose up -d postgres` so `pnpm dev` and the API tests keep working on ports 3000 and 5173. A new `pnpm docker:app` runs the full command.
- **Real-stack Playwright is separate:** The existing mocked specs stay as they are. They cover error and pending states that a real server cannot produce on demand. A new `e2e/stack/journey.spec.ts` runs against `http://localhost:8080` with a second config, `playwright.stack.config.ts`, that has no `webServer` and no `page.route`. A new `test:stack` script runs it. The default config sets `testIgnore` for `stack/**`.
- **Serial journey:** The stack spec runs in one worker. It starts with a clean database, so it deletes every todo through the API in `beforeAll`. The stale-selection step uses `request.delete` to remove a row behind the UI.
- **Clean database in CI:** A new `stack` job runs `docker compose down -v`, then `docker compose up --build -d --wait`, then `pnpm test:stack`. On failure it prints `docker compose logs`.
- **Orphan migration:** `0001_glorious_silvermane.sql` is not in the journal, so drizzle never runs it. It is removed as an approved correction. The journal is not touched.
- **README:** The out-of-date frontend paragraph is replaced. The Docker command, ports, and the clean-start steps are added.
- **Evidence in one file:** `VERIFICATION.md` at the root holds the architecture, the journey and state matrix, the keyboard results, command results, findings, and the manager-selected change. The pull request links it.

# Architecture explanation outline

1. **Packages:** `packages/contracts` holds the Zod schemas shared by API and web. `apps/api` is Fastify with Drizzle on Postgres. `apps/web` is React with TanStack Router, Query, and Form. `e2e` is Playwright.
2. **API layers:** route in `todo.routes.ts` maps a `Result` to a status with an exhaustive `match`. Service in `todo.service.ts` parses input with the contract schemas. Repository in `todo.repository.ts` runs Drizzle queries and returns `neverthrow` results.
3. **Errors:** `ValidationError` is `400`. `NotFoundError` is `404`. `BatchConflictError` is `409` with `missingIds`. `DatabaseError` is logged and returned as `500` with the internal body.
4. **Batch safety:** `PATCH /todos/batch` and `POST /todos/batch-delete` run in one transaction and roll back on any missing id.
5. **Web layers:** adapter in `todo.api.ts` parses input and output with the contracts and throws `TodoApiError`. Hooks wrap TanStack Query and invalidate the list and summary keys. Module files build labels and messages. Components draw. `HomePage` wires them and owns focus.
6. **State:** list scope lives in the URL search params. Selection lives in a reducer scoped to the query.
7. **Contracts to explain:** `todoSchema`, `createTodoSchema`, the list query and response, `updateSelectedTodosSchema`, `deleteSelectedTodosSchema`, and `batchConflictErrorResponseSchema`.

# Keyboard smoke test

Run on `http://localhost:8080` in Chromium with an empty database. Use only Tab, Shift+Tab, Enter, Space, and Escape. Record pass or fail for each step.

1. Tab to the new todo field. Type three titles, each with Enter.
2. Tab to the first row toggle. Press Space. It becomes completed.
3. Tab to Edit on the second row. Press Enter. Change the title. Press Enter to save.
4. Start another edit and press Escape. The title is unchanged.
5. Tab to the Active filter. Press Enter. Only active rows show.
6. Tab to the search field and type part of a title. The list narrows.
7. Clear the search. Tab to the toggle-all control. Press Space.
8. Tab to "Clear completed". Press Enter. The list is empty and focus is on the empty heading.
9. Add two todos. Enter selection mode with Enter. Select both rows with Space.
10. Tab to "Mark selected as completed". Press Enter. The status announces the count.
11. Select both again. Tab to the delete button. Press Enter. The status announces the count.
12. Press Escape to leave selection mode.
13. At every step the focus ring is visible and no step needs the mouse.

# Certainty checks

### 1. What information enters the system?

A fresh clone, the lockfile, the environment values in `docker-compose.yml`, and user input in the browser.

### 2. How will you check that information?

`--frozen-lockfile` refuses lockfile drift. `config.ts` parses the environment with Zod. The contracts check every request and response.

### 3. What will the operation return when it succeeds?

`docker compose up --build -d --wait` exits `0` with every service healthy. Every check command exits `0`. The stack test passes. The evidence packet is complete.

### 4. What expected failures can happen?

A port in use, Postgres not ready, a failed migration, an unhealthy API, stale data, a stack that is not running, and lockfile drift.

### 5. How will each expected failure be represented?

Each is a non-zero exit with the cause in the output. The table above lists them.

### 6. Where will the route, business rules, and database or UI work live?

No new route, rule, or UI. Containers live in `Dockerfile` and `docker-compose.yml`. The proxy lives in `apps/web/nginx.conf`. The stack test lives in `e2e/stack`. Evidence lives in `VERIFICATION.md`.

### 7. What tests will you write before implementation?

The real-stack Playwright journey. It is listed below.

### 8. How will you prove the whole operation works through its real boundaries?

The stack test drives a real browser against nginx, the API, and Postgres built by Docker Compose from a clean volume. CI does the same on every pull request.

### 9. Does this change multiple records or call another system? If yes, how will failure be handled safely?

The stack test changes many records, but only in the Docker database. It never runs against a developer database. `docker compose down -v` resets it.

### 10. If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?

No new UI. The state matrix maps empty, loading, ready, error, pending, and recovery to existing tests. The keyboard smoke test covers focus and keyboard use.
